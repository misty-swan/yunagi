# YUN-2 結果：Svelte と SolidJS の比較

> 比較用の使い捨ての試作に対する計測です。決定は YUN-3 で行います。この文書は決定の材料で、仕様ではありません（仕様の正本は `docs/`）。

## 1. 要点

- **自動で測れる性能（起動時間・メモリ・入力の反応）では、両者に意味のある差はなかった。** どの項目も、差はばらつきの範囲に収まっている。
- 差が出たのは周辺の項目だけだった。
  - フレームワーク部分の JS は Solid のほうが小さい（gzip 後 9.0 KB と 16.2 KB）。ただし両版に共通の CodeMirror が 199 KB あるので、合計では約 3% の差にとどまる（208 KB と 215 KB）。
  - 依存パッケージは Svelte のほうが少なく（74 個と 96 個）、画面のコードも短い（74 行と 91 行）。
- **現時点の推薦は Svelte（暫定）。** 理由と、覆りうる点は 5章に書いた。
- **IME（日本語入力）の実際の挙動は、まだ誰も確かめていない。** 合成イベントで判定の論理が正しいことだけを確認した。オーナーの実機確認（4章）の結果しだいで推薦が変わりうる。

## 2. 計測した環境と方法

| 項目 | 値 |
| --- | --- |
| マシン | Intel Core i7-11850H、メモリ 32 GB |
| OS・画面 | Linux 7.2.8（Omarchy）、Hyprland 0.56.2（Wayland） |
| WebView | WebKitGTK 2.54.1 |
| ツール | Rust 1.99.1、Node.js 26.8.2、pnpm 12.14.0、Vite 8.3.5、Tauri 2（CLI 2.12.4） |
| フレームワーク | Svelte 5.57.3 ／ SolidJS 1.9.18 |
| 共通部品 | CodeMirror 6（`codemirror` 6.0.2 ＋ Markdown） |

公平に比べるための工夫：

- IME の判定・エディタの生成・計測コード・スタイルは `shared/` の同じファイルを両版にコピーして使った。コピーが同一であることは `scripts/static_metrics.py` で確認している（`shared_identical: true`）。CodeMirror の出力ファイルは、両版でハッシュ（中身から作る識別子）まで一致した。
- Rust 側（`src-tauri/`）はパッケージ名以外を同じにし、ライブラリの版も同じ `Cargo.lock` で揃えた。
- 起動の計測は両版を交互に行った。どちらも1回の捨て回しでディスクのキャッシュを温めてから測っている。

### 2.1 アプリの開き方（途中で変えた）

- 最初の起動計測（10回ずつ）は、ウィンドウをオーナーの画面に開いて行った。画面の邪魔になるとの指摘を受け、以後は Hyprland の見えない特別ワークスペース `special:yunagi-bench` に開くように変えた。
- 見えないワークスペースでは**描画そのものが行われない**（描画完了の合図が来ない）ことを確認した。そのため次のように測り分けている。
  - **描画完了まで**（READY）：最初の計測（画面に表示）の値だけがある。
  - **画面の組み上げ完了まで**（MOUNTED）：画面の部品を作り、レイアウト計算を終えた時点。描画の直前にあたる。見えないワークスペースで測った。
- ウィンドウを開いたときは毎回、表示先が `special:yunagi-bench` であることを確かめた（Hyprland のイベントと `hyprctl clients -j` で確認）。終了は PID（プロセス番号）を指定して行い、毎回プロセスが残っていないことも確かめた。

## 3. 計測結果（自動）

表の値は中央値です。かっこ内は最小〜最大。

### 3.1 本番ビルドの起動時間

起点は起動コマンドを出した時刻。

| 項目 | Svelte | Solid | 計測の条件 |
| --- | --- | --- | --- |
| ウィンドウが作られるまで | 140 ms（125〜164） | 141 ms（124〜157） | 画面に表示・10回 |
| **最初の描画完了まで**（READY） | **387 ms**（372〜431） | **389 ms**（378〜461） | 画面に表示・10回 |
| ウィンドウが作られるまで | 139 ms（131〜152） | 135 ms（133〜156） | 見えない場所・10回 |
| **画面の組み上げ完了まで**（MOUNTED） | **300 ms**（294〜313） | **294 ms**（289〜317） | 見えない場所・10回 |
| うち WebView 内で費やした時間（ページの読み込み開始〜組み上げ完了） | 75 ms | 73 ms | 見えない場所・10回 |

- 起動時間の大半は、Tauri・WebKit の立ち上げとページの読み込みが占めている。フレームワークの違いが出る部分は数 ms 以下で、ばらつきより小さい。
- 見えない場所での計測の起点には、`hyprctl` と `sh` の起動時間（数 ms）が含まれる。

### 3.2 メモリ

起動して 1.5 秒後に、アプリ本体と WebKit の子プロセス（描画用・通信用）の PSS を合計した値。PSS は、共有ライブラリの分を各プロセスで按分したメモリ量。

| Svelte | Solid |
| --- | --- |
| 307 MB（302〜313） | 304 MB（302〜311） |

ほとんどは WebKit の分で、差はばらつきの範囲。

### 3.3 入力の反応

WebView の中で合成イベント（プログラムから作ったキー入力・クリック）を送り、DOM への反映とレイアウト計算が終わるまでを測った。見えない場所で3回ずつ。実際のキーボードから画面に出るまでの時間ではない（4章の体感確認で補う）。

| 操作 | Svelte | Solid |
| --- | --- | --- |
| TODO を1件追加（一覧が 0〜100 件のとき） | 0.65 ms | 0.73 ms |
| TODO を1件追加（一覧が 900〜1000 件のとき） | 5.19 ms | 5.24 ms |
| 完了の切り替え1回（1000 件あるとき） | 4.97 ms | 5.03 ms |
| 1000 件を一度に消す | 5 ms | 4 ms |
| CodeMirror に1文字挿入（両版で同じエディタ。参考値） | 0.81 ms | 0.81 ms |

- 両者の差は、どの操作でも 0.1 ms 前後だった。
- 1件追加の時間は、一覧の件数にほぼ比例して増えた（両版とも同じ傾き）。原因は切り分けていない。両版に共通なので、フレームワークの差ではない。1日の TODO が数十件の範囲なら 1 ms 未満で収まる。
- WebKit の `performance.now()` は 1 ms 単位でしか時刻を返さないため、1回ごとではなく 100〜500 回の平均で測った。

### 3.4 IME 判定の論理（合成イベント）

`docs/design/04-interaction-spec.md` 3章の規則を、合成イベントで確かめた。両版とも3回すべて合格。

| 確認したこと | Svelte | Solid |
| --- | --- | --- |
| 変換中（`isComposing=true`）の Enter では追加しない | 合格 | 合格 |
| `keyCode 229` の Enter では追加しない | 合格 | 合格 |
| `compositionend` 直後（同じタスク内）の最初の Enter では追加しない | 合格 | 合格 |
| その後の普通の Enter では追加する | 合格 | 合格 |
| `compositionend` の後、次のタスクに入ってからの Enter では追加する | 合格 | 合格 |

これは**判定のプログラムが規則どおりに書けているか**の確認にすぎない。本物の IME（fcitx5-mozc など）が実際にどんな順番・値でイベントを送ってくるかは確かめていない（4章）。

### 3.5 サイズ

| 項目 | Svelte | Solid |
| --- | --- | --- |
| アプリ本体の JS（フレームワーク＋画面＋共通の小物） | 41.7 KB（gzip 16.2 KB） | 23.1 KB（gzip 9.0 KB） |
| CodeMirror の JS（両版で同一） | 593 KB（gzip 199 KB） | 593 KB（gzip 199 KB） |
| JS の合計 | 634.8 KB（gzip 215.3 KB） | 616.2 KB（gzip 208.1 KB） |
| 実行ファイル（JS 等を内蔵。strip 済み） | 4.57 MB | 4.56 MB |
| 配布用パッケージ（.deb） | 1.85 MB | 1.84 MB |

### 3.6 ビルド時間

| 項目 | Svelte | Solid |
| --- | --- | --- |
| 本番ビルド、まっさらな状態から（Rust の依存のダウンロードは除く） | 102.3 秒 | 98.8 秒 |
| 本番ビルド、2回目以降（フロントエンドと Rust を少し変えた後） | 41.8 秒 | 44.5 秒 |
| フロントエンドだけのビルド（`vite build`、5回の中央値） | 425 ms | 402 ms |
| 依存パッケージの導入（`pnpm install`、初回） | 6.7 秒 | 5.7 秒 |

- 本番ビルドの時間は、ほぼすべて Rust（Tauri）のコンパイルが占める。2回目以降も約 40 秒かかるのは、リンク時の最適化（LTO）を有効にしているため。フレームワークの差ではない。
- `pnpm install` の時間は回線とキャッシュの影響が大きく、参考値。

### 3.7 コード量と依存

| 項目 | Svelte | Solid |
| --- | --- | --- |
| 画面のコード（`App.svelte` ／ `App.tsx`。空行とコメントを除く） | 74 行 | 91 行 |
| 起動コード・設定ファイルを含む合計 | 113 行 | 143 行（JSX の型設定 `tsconfig.json` の 13 行を含む） |
| npm の依存パッケージ（間接的なものを含む） | 74 個 | 96 個 |
| `node_modules` の大きさ | 63.5 MB | 73.6 MB |

Solid の依存が多いのは、JSX の変換に Babel（コードを書き換える道具）を使うため。

### 3.8 測れていないこと

- **型チェック**（型の食い違いを自動で見つける検査）：どちらの版でも実行していない。Svelte には `svelte-check`、Solid には TypeScript の標準の検査が必要になる。npm にある最新の TypeScript は 7.0.2 で、これらの道具と組み合わせて動くかは確かめていない。
- 開発中の画面の自動更新（`pnpm tauri dev`）の速さと使い心地。
- macOS（WebKit）と Windows（WebView2）での計測。今回は Linux の WebKitGTK だけ。

## 4. オーナーによる実機確認の手順

以下は人が実機で触らないと分からないため、結果はまだありません。各項目について、両版それぞれ「○ 問題なし／× 問題あり（内容）」を記入してください。

### 4.1 起動のしかた

ターミナルで次を実行します。本番ビルド済みのアプリが、いま見ている画面に開きます。

```sh
cd ~/Work/yunagi-wt/yun-2/experiments/yun-2-frontend

# Svelte 版を開く（閉じるにはウィンドウを閉じる）
./svelte/src-tauri/target/release/yun2-svelte

# Solid 版を開く
./solid/src-tauri/target/release/yun2-solid
```

- 日本語入力は fcitx5-mozc（このマシンの既定）で確かめてください。
- 左下の「Event log」には、キー入力や変換のイベントと、判定の結果（「追加」「無視（isComposing）」など）が新しい順に出ます。おかしな動きがあったら、その数行を書き写すかスクリーンショットを残してください。WebKitGTK で実際に届いたイベントの順番は、YUN-3 と `docs/design/04-interaction-spec.md` 6章の未決事項の判断材料になります。

## 5. 推薦（暫定）

**Svelte を推します。** ただし差は小さく、オーナーの実機確認で覆りうる程度のものです。

### 理由

1. Yunagi が優先する起動と入力の速さについて、今回の計測では両者に差がなかった（3.1〜3.3章）。速さで決まらない以上、日々の作りやすさと保守のしやすさで選ぶのが妥当と考えた。
2. 同じ画面を書いたとき、Svelte のほうが短かった（74 行と 91 行）。入力欄の値の双方向の結び付け（`bind:value`、`bind:checked`）を1行で書ける。
3. 依存パッケージが少ない（74 個と 96 個）。外部ライブラリの更新と脆弱性の確認にかかる手間は、依存の数に応じて増える。
4. Solid の強みであるサイズの小ささは、今回の構成では効きにくい。差は gzip 後で約 7 KB で、CodeMirror の 199 KB と比べると約 3%。しかもアプリに同梱して手元から読み込むので、通信時間は発生しない。起動時間にも差は表れなかった。

### オーナーの実機確認で覆りうる点

- **IME の挙動**（4.2・4.3章）：Svelte 版だけで変換中の不具合（文字の抜け、意図しない確定、Enter での追加）が起き、Solid 版では起きない場合は、Solid を採るべきです。逆の場合は Svelte の推薦がより強まります。
- **体感の差**（4.4章）：計測では見えない差を Svelte 版で感じる場合。
- **書き方の好み**：Solid は JSX（JavaScript の中に HTML のような記法を書く方式）、Svelte は専用の `.svelte` ファイルを使います。オーナーやエージェントが読み書きしやすいのはどちらか。両版の `App.svelte` と `App.tsx` を見比べてください。

### 計測では決められない残り

- 型チェックの道具が TypeScript 7 と組み合わせて動くか（3.8章）。本番の着手前に確認が要る。
- macOS・Windows での挙動。特に Windows は WebView2（Chromium 系）なので、IME のイベントの順番が WebKit と違う可能性がある。テスト計画の IME 試験で確かめる。
