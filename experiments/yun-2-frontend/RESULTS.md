# YUN-2 結果：Svelte と SolidJS の比較

> 比較用の使い捨ての試作に対する計測です。決定は YUN-3 で行います。この文書は決定の材料で、仕様ではありません（仕様の正本は `docs/`）。

## 1. 要点

- **自動で測れる性能（起動時間・メモリ・入力の反応）では、両者に意味のある差はなかった。** どの項目も、差はばらつきの範囲に収まっている。
- 差が出たのは周辺の項目だけだった。
  - フレームワーク部分の JS は Solid のほうが小さい（gzip 後 9.0 KB と 16.2 KB）。ただし両版に共通の CodeMirror が 199 KB あるので、合計では約 3% の差にとどまる（208 KB と 215 KB）。
  - 依存パッケージは Svelte のほうが少なく（74 個と 96 個）、画面のコードも短い（74 行と 91 行）。
- **その場で編集する項目の一覧（prototype と同じ contenteditable の一覧）を足して比べた結果（3.9章）：** 各フレームワークで自然に書けば、分割・削除・移動も、読み込み直しの後にフォーカス・選択範囲・テキストノードが保たれることも、両版で同じように合格した。速さも同じだった。差は書きやすさに出た。
  - Svelte は標準の `bind:textContent` とキー付きの `{#each}` で済み、読み込み直しは配列を代入するだけ。
  - Solid は `reconcile` を使い、contenteditable の中身を書き換えるかどうかの比較を自分で書く必要があった。一覧の部品は Svelte 105 行、Solid 137 行。
  - それぞれの工夫を省くと壊れることも確かめた。特に Solid で `reconcile` を省くと、読み込み直しのたびに入力中の項目からフォーカスが外れる。
- **推薦は Svelte。** オーナーの実機確認で、推薦を覆す問題は見つからなかった。理由は 5章に書いた。
- **IME（日本語入力）の実機確認（4章）：** 2026-11-02、オーナーが Linux（fcitx5-mozc）で両版を触り、問題はなかった。結果は「両版とも問題なし」の一言で受け取っており、項目ごとの ○／× の記録はない。

## 2. 計測した環境と方法

| 項目 | 値 |
| --- | --- |
| マシン | Intel Core i7-11850H、メモリ 32 GB |
| OS・画面 | Linux 7.2.8（Omarchy）、Hyprland 0.56.2（Wayland） |
| WebView | WebKitGTK 2.54.1 |
| ツール | Rust 1.99.1、Node.js 26.8.2、pnpm 12.14.0、Vite 8.3.5、Tauri 2（CLI 2.12.4） |
| フレームワーク | Svelte 5.57.3 ／ SolidJS 1.9.18 |
| 共通部品 | CodeMirror 6（`codemirror` 6.0.2 ＋ Markdown） |

公平に比べるための工夫：

- IME の判定・エディタの生成・計測コード・スタイルは `shared/` の同じファイルを両版にコピーして使った。コピーが同一であることは `scripts/static_metrics.py` で確認している（`shared_identical: true`）。CodeMirror の出力ファイルは、両版でハッシュ（中身から作る識別子）まで一致した。
- Rust 側（`src-tauri/`）はパッケージ名以外を同じにし、ライブラリの版も同じ `Cargo.lock` で揃えた。
- 起動の計測は両版を交互に行った。どちらも1回の捨て回しでディスクのキャッシュを温めてから測っている。

### 2.1 アプリの開き方（途中で変えた）

- 最初の起動計測（10回ずつ）は、ウィンドウをオーナーの画面に開いて行った。画面の邪魔になるとの指摘を受け、以後は Hyprland の見えない特別ワークスペース `special:yunagi-bench` に開くように変えた。
- 見えないワークスペースでは**描画そのものが行われない**（描画完了の合図が来ない）ことを確認した。そのため次のように測り分けている。
  - **描画完了まで**（READY）：最初の計測（画面に表示）の値だけがある。
  - **画面の組み上げ完了まで**（MOUNTED）：画面の部品を作り、レイアウト計算を終えた時点。描画の直前にあたる。見えないワークスペースで測った。
- ウィンドウを開いたときは毎回、表示先が `special:yunagi-bench` であることを確かめた（Hyprland のイベントと `hyprctl clients -j` で確認）。終了は PID（プロセス番号）を指定して行い、毎回プロセスが残っていないことも確かめた。

## 3. 計測結果（自動）

3.1〜3.8 は初版（TODO の入力欄・一覧と CodeMirror だけ）での値です。その場で編集する一覧を足した後の結果は 3.9 にまとめました。

表の値は中央値です。かっこ内は最小〜最大。

### 3.1 本番ビルドの起動時間

起点は起動コマンドを出した時刻。

| 項目 | Svelte | Solid | 計測の条件 |
| --- | --- | --- | --- |
| ウィンドウが作られるまで | 140 ms（125〜164） | 141 ms（124〜157） | 画面に表示・10回 |
| **最初の描画完了まで**（READY） | **387 ms**（372〜431） | **389 ms**（378〜461） | 画面に表示・10回 |
| ウィンドウが作られるまで | 139 ms（131〜152） | 135 ms（133〜156） | 見えない場所・10回 |
| **画面の組み上げ完了まで**（MOUNTED） | **300 ms**（294〜313） | **294 ms**（289〜317） | 見えない場所・10回 |
| うち WebView 内で費やした時間（ページの読み込み開始〜組み上げ完了） | 75 ms | 73 ms | 見えない場所・10回 |

- 起動時間の大半は、Tauri・WebKit の立ち上げとページの読み込みが占めている。フレームワークの違いが出る部分は数 ms 以下で、ばらつきより小さい。
- 見えない場所での計測の起点には、`hyprctl` と `sh` の起動時間（数 ms）が含まれる。

### 3.2 メモリ

起動して 1.5 秒後に、アプリ本体と WebKit の子プロセス（描画用・通信用）の PSS を合計した値。PSS は、共有ライブラリの分を各プロセスで按分したメモリ量。

| Svelte | Solid |
| --- | --- |
| 307 MB（302〜313） | 304 MB（302〜311） |

ほとんどは WebKit の分で、差はばらつきの範囲。

### 3.3 入力の反応

WebView の中で合成イベント（プログラムから作ったキー入力・クリック）を送り、DOM への反映とレイアウト計算が終わるまでを測った。見えない場所で3回ずつ。実際のキーボードから画面に出るまでの時間ではない（4章の体感確認で補う）。

| 操作 | Svelte | Solid |
| --- | --- | --- |
| TODO を1件追加（一覧が 0〜100 件のとき） | 0.65 ms | 0.73 ms |
| TODO を1件追加（一覧が 900〜1000 件のとき） | 5.19 ms | 5.24 ms |
| 完了の切り替え1回（1000 件あるとき） | 4.97 ms | 5.03 ms |
| 1000 件を一度に消す | 5 ms | 4 ms |
| CodeMirror に1文字挿入（両版で同じエディタ。参考値） | 0.81 ms | 0.81 ms |

- 両者の差は、どの操作でも 0.1 ms 前後だった。
- 1件追加の時間は、一覧の件数にほぼ比例して増えた（両版とも同じ傾き）。原因は切り分けていない。両版に共通なので、フレームワークの差ではない。1日の TODO が数十件の範囲なら 1 ms 未満で収まる。
- WebKit の `performance.now()` は 1 ms 単位でしか時刻を返さないため、1回ごとではなく 100〜500 回の平均で測った。

| 変換中（`isComposing=true`）の Enter では追加しない | 合格 | 合格 |
| `keyCode 229` の Enter では追加しない | 合格 | 合格 |

これは**判定のプログラムが規則どおりに書けているか**の確認にすぎない。本物の IME（fcitx5-mozc など）が実際にどんな順番・値でイベントを送ってくるかは確かめていない（4章）。

### 3.8 測れていないこと

- **型チェック**（型の食い違いを自動で見つける検査）：どちらの版でも実行していない。Svelte には `svelte-check`、Solid には TypeScript の標準の検査が必要になる。npm にある最新の TypeScript は 7.0.2 で、これらの道具と組み合わせて動くかは確かめていない。
- 開発中の画面の自動更新（`pnpm tauri dev`）の速さと使い心地。
- macOS（WebKit）と Windows（WebView2）での計測。今回は Linux の WebKitGTK だけ。

### 3.9 その場で編集する項目の一覧（追加の比較）

本番の整理モードの一覧は、prototype/app.js と同じく、各項目を contenteditable（その場で文字を編集できる要素）にする見込みです。初版は `<input>` の入力欄しか比べていなかったので、この一覧を両版に足して比べました。画面の真ん中の「Board」列です。

#### 3.9.1 作ったもの

- 各項目は `contenteditable="plaintext-only"`（書式なしの文字だけを編集できる設定）。キー操作は prototype と同じ考え方にした。
  - 行の途中の Enter：カーソル位置で2件に分ける。行頭の Enter：直上に空の項目を足す。行末の Enter：直下に空の項目を足す。どれも新しい項目の先頭へ移る。
  - 空の項目の Backspace：その項目を消して、直前の項目の末尾へ移る。
  - 先頭の行の ↑・末尾の行の ↓：隣の項目へ移る（何文字目かを保つ）。
  - IME の判定は初版と同じ `shared/ime-guard.ts`。`compositionend` 直後の Enter は、改行も入らないよう止める。
- カーソル操作（`shared/caret.ts`）は両版共通で、prototype の `setCaretIn`・`caretOffset`・`onFirstLine`・`onLastLine` と同じ考え方で書いた。
- **読み込み直し**：`shared/core.ts` に、コアの代わりとなるメモリ上のデータを置いた。入力のたびにここへ保存し、「読み込み直す」ボタンで、ID は同じで中身は新しいオブジェクトの配列を受け取って画面のデータを置き換える（`docs/design/01-architecture.md` 4章 6 の模擬）。
  - 「3秒ごと」：自動で読み込み直す。
  - 「エージェントの変更を混ぜる」：読み込み直しの直前に、フォーカスのある項目以外の1件の末尾に「◆番号」を付ける。

#### 3.9.2 それぞれの自然な書き方と、必要だった工夫

| 場面 | Svelte | Solid |
| --- | --- | --- |
| 一覧の描画 | キー付きの `{#each items as item, i (item.id)}` | `<For each={items}>` |
| 本文とデータの結び付け | 標準の `bind:textContent={item.text}`。DOM の中身と値が違うときだけ書き換える（Svelte のソースで確認） | 同等の機能がないので自分で書いた。値が違うときだけ `el.textContent` を書き換える `createEffect`（3行）と、入力を受けてデータに入れる `onInput`（4行） |
| 読み込み直し | `items = core.load()`（代入するだけ） | `setItems(reconcile(core.load(), { key: 'id' }))`。ID で突き合わせて、変わった値だけを更新する |
| 分割・削除 | 配列をそのまま `splice` | `produce` の中で `splice` |
| 変更後のフォーカス | `await tick()` で DOM の更新を待ってから。Svelte は更新を次のマイクロタスク（今の処理が終わった直後）にまとめるため | すぐにできる。Solid は DOM を同期的に更新するため |
| 一覧の部品のコード量（空行とコメントを除く） | 105 行（空白を除いて 2,900 字） | 137 行（同 3,364 字。約 16% 多い） |
| 画面全体のコード量 | 223 行 | 285 行 |

行数には書式の違いも混ざっています（Solid 版はチェック欄の属性を複数行に分けて書いた）。そのため、空白を除いた文字数も載せました。

合成イベントで確かめた結果。見えない場所で両版を3回ずつ実行し、3回とも同じ結果だった。

| 確認したこと | Svelte | Solid |

| 入力した文字がコアまで届く／1文字入力した後もカーソルとテキストノードが保たれる／空の項目に入力して画面・データ・カーソルが一致する | すべて合格 | すべて合格 |
| 1文字入力したときの DOM の書き換え回数（ブラウザ自身の分だけなら 1。空の項目への入力は 2） | 1 ／ 2 | 1 ／ 2 |

「変換を始めた状態」の確認は、本物の変換ではありません。分かるのは、読み込み直しで入力中の項目の DOM に触れていないことまでです。本物の変換が壊れないかはオーナーの実機確認（4.4章）で見てください。

#### 3.9.4 1000 件あるときの速さ

中央値（かっこ内は最小〜最大）。WebKit の時計は 1 ms 単位なので、読み込み直しの値は 1 ms 単位でしか差が分かりません。

| 操作 | Svelte | Solid |
| --- | --- | --- |
| 5件から約 1000 件に増やす読み込み直し | 37 ms（37〜37） | 34 ms（31〜35） |
| 中身が同じ読み込み直し（1000 件） | 7 ms（6〜7） | 6 ms（6〜6） |
| 1件だけ変わった読み込み直し（1000 件） | 7 ms（6〜7） | 6 ms（6〜6） |
| 一覧の中ほどでの分割1回 | 6.58 ms | 6.78 ms |
| 1文字入力1回 | 5.43 ms | 5.41 ms |

両者の差は 1 ms 前後で、1日の項目数（数十件）なら体感できる差にはならない見込みです。

#### 3.9.5 工夫を省いた書き方（変種）の結果

各工夫が本当に必要かを確かめるため、一時的に書き換えた版で1回ずつチェックした（`scripts/variants.py`）。書き換えはコミットしておらず、計測の後は通常版でビルドし直して、チェックに合格することを確かめた。

| 変種 | 結果 |
| --- | --- |
| A：Solid で `reconcile` を使わず、配列をそのまま渡す（`setItems(core.load())`） | 読み込み直しのたびに、全行（8行）の DOM が作り直された。フォーカスと選択範囲は4つの場面すべてで消えた。3秒ごとの自動読み込み直しでは、入力中の項目から3秒ごとに追い出されることになる。1000 件での読み込み直しも 6 ms から 26 ms に遅くなった |
| B：Solid で比較処理を書かず、`textContent={item.text}` と書く | 1文字入力するたびに DOM の書き換えが1回余分に起きた（1→2）。入力後のカーソルかテキストノードが保たれず、空の項目への入力でも画面・データ・カーソルが一致しなかった。読み込み直しは合格 |
| C：Svelte で `{#each}` のキーを省く | チェックはすべて合格。ただし 1000 件での分割が 6.6 ms から 16.7 ms に遅くなった（キーがないと、位置で対応付けて後ろの行の中身を書き換えるため） |
| D：Svelte で `bind:textContent` を使わず、`{item.text}` と書いて `oninput` でデータに入れる | B と同じ失敗（余分な書き換え 1→2、入力後のカーソル・テキストノード、空の項目への入力） |
| E：Svelte で `await tick()` を省く | 分割・追加・削除の後に、新しい項目へフォーカスが移らなかった（あとに続くチェックも連鎖して失敗） |

分かったこと：

- 自然な書き方をすれば、両版とも同じように正しく、同じ速さで動く。フレームワークの性能の差は出なかった。
- 差は「正しい書き方にたどり着くまでに知っておくべきこと」に出た。
  - Svelte で要るのは、キー付きの `{#each}`、`bind:textContent`、`await tick()` の3つ。どれも Svelte の基本機能で、追加の API はない。
  - Solid で要るのは、`reconcile`（ストアの追加機能）と、contenteditable の中身を比べて書き換える処理の自作。
- どちらも、本文を素直に式で書く（B・D）と同じように壊れる。本番では、フレームワークに関係なく、contenteditable の項目を1つの部品にまとめ、このチェックのようなテストで守るのがよい。
- 壊れ方の重さは違った。A（`reconcile` 忘れ）は、読み込み直しが起きるたびに入力中の項目から追い出される。Yunagi はエージェントの変更のたびに読み込み直す設計（01 4章 6）なので、利用者への影響が大きい。E（`tick` 忘れ）は、分割・追加の直後にすぐ気づく壊れ方。

## 5. 推薦

**Svelte を推します。** 一覧の比較（3.9章）を足して見直した結果も、推薦は変わりません。推す理由は1つ増えました。オーナーの実機確認（4章）でも、推薦を覆す問題は見つかりませんでした。決定は YUN-3 で行います。

### 理由

1. Yunagi が優先する起動と入力の速さについて、今回の計測では両者に差がなかった（3.1〜3.3章）。速さで決まらない以上、日々の作りやすさと保守のしやすさで選ぶのが妥当と考えた。
2. 同じ画面を書いたとき、Svelte のほうが短かった（74 行と 91 行）。入力欄の値の双方向の結び付け（`bind:value`、`bind:checked`）を1行で書ける。
3. 依存パッケージが少ない（74 個と 96 個）。外部ライブラリの更新と脆弱性の確認にかかる手間は、依存の数に応じて増える。
4. Solid の強みであるサイズの小ささは、今回の構成では効きにくい。差は gzip 後で約 7 KB で、CodeMirror の 199 KB と比べると約 3%。しかもアプリに同梱して手元から読み込むので、通信時間は発生しない。起動時間にも差は表れなかった。
5. Yunagi の中心になる「その場で編集する一覧」と「読み込み直し」を、Svelte は基本機能だけで正しく書けた（3.9.2章）。Solid は `reconcile` と比較処理の自作が要った。工夫を省いたときの壊れ方も、Solid の `reconcile` 忘れが最も重かった（読み込み直しのたびに入力中の項目から追い出される。3.9.5章）。エージェントが手伝って書くことを考えると、正しい書き方が基本機能で済むほうが、間違いが入りにくいと考えた。

Solid に有利な点もありました。DOM が同期的に更新されるので、分割・追加の直後にそのままフォーカスを移せます。Svelte では `await tick()` を忘れると、新しい項目へフォーカスが移りません（3.9.5章の E）。ただし、この壊れ方は操作した直後に気づけます。

### オーナーの実機確認で覆りうる点

（2026-11-02 の確認では、以下のどれにも当たらなかった。）

- **IME の挙動**（4.2・4.3章）：Svelte 版だけで変換中の不具合（文字の抜け、意図しない確定、Enter での追加）が起き、Solid 版では起きない場合は、Solid を採るべきです。逆の場合は Svelte の推薦がより強まります。
- **一覧での日本語入力**（4.4章）：変換中の読み込み直し（19〜21）などで、片方の版だけが壊れる場合は、壊れなかったほうを採るべきです。自動チェックでは、両版とも入力中の項目の DOM に触れていないことまでしか確かめられていません。
- **体感の差**（4.5章）：計測では見えない差を Svelte 版で感じる場合。
- **書き方の好み**：Solid は JSX（JavaScript の中に HTML のような記法を書く方式）、Svelte は専用の `.svelte` ファイルを使います。オーナーやエージェントが読み書きしやすいのはどちらか。両版の `App.svelte`・`ItemList.svelte` と `App.tsx`・`ItemList.tsx` を見比べてください。

### 計測では決められない残り

- 型チェックの道具が TypeScript 7 と組み合わせて動くか（3.8章）。本番の着手前に確認が要る。
- 入力中の項目そのものをエージェントが書き換えたときの扱い（3.9.7章）。フレームワークの選択とは別に、設計で決める必要がある。
- macOS・Windows での挙動。特に Windows は WebView2（Chromium 系）なので、IME のイベントの順番が WebKit と違う可能性がある。テスト計画の IME 試験で確かめる。
