# テスト計画書

## 1. 目的と範囲

MVP の機能要件（F-01〜F-12、A-01〜A-08、Vimモード）と非機能要件を、Windows・macOS・Linux の3 OS で満たしていることを確認する。特に、軽さ、データを失わないこと、IME との両立を重点項目とする。

## 2. テストの層

| 層 | 対象 | 手段 | 実行時期 |
| --- | --- | --- | --- |
| 単体 | コアのドメイン層（論理日付、持ち越し、権限、変更履歴） | Rust のテスト | 毎コミット |
| 結合 | コア＋SQLite、ローカル API、CLI、MCP | テスト用データディレクトリでの自動テスト | 毎コミット |
| E2E | 画面操作の主要シナリオ | WebDriver（tauri-driver）による自動化（Windows・Linux）。tauri-driver は macOS に対応しないため、macOS は手動チェックリストで確認する | 毎日・リリース前 |
| 手動 | IME、グローバルショートカット、インストール、更新、macOS の E2E 主要シナリオ | チェックリスト | リリース前 |
| 性能 | 起動、入力応答、検索 | 計測スクリプト | 週次・リリース前 |

「毎コミット」の層は、開発用 CI（GitHub Actions の `.github/workflows/ci.yml`）で、PR と main への push のたびに走らせる。検査するのは push の時点の最新のコミットで、1回の push に含まれる途中のコミットは個別には検査しない。CI は手元の検査コマンド `pnpm check`（`package.json`）をそのまま実行し、Rust の書式の検査（`cargo fmt --check`）・ワークスペース全体のテスト（`cargo test --workspace`）・clippy（警告も失敗として扱う）・コード中の説明からの文書の生成（`cargo doc`。リンク切れなどの警告も失敗として扱う）・画面の型チェックとテストを行う。結合の層のテストは、`pnpm check` に入れて毎回走らせるか、別の手順で走らせるかを、結合テストを作るときに所要時間を見て決める。失敗は PR の検査結果に表示される。Linux では `pnpm check` をすべて走らせ、macOS・Windows では Rust のテスト・clippy・`cargo doc` だけを走らせる（2026-11-05 決定。YUN-102）。OS ごとに分かれたコード（`yunagi.lock` のロック、Markdown 書き出しの Windows だけの再試行など。Linux の CI ではコンパイルもされない）が、各 OS でコンパイルとテストを通ることを確かめるため。ただし**リポジトリが非公開の間、macOS・Windows は自動では回らない**（費用のため。公開後は自動。手動の実行の手順は下の「macOS・Windows での開発用 CI」）。

#### macOS・Windows での開発用 CI

- **範囲（2026-11-05 決定）**：macOS（`macos-15`）と Windows（`windows-2025`）で、`pnpm run check:rust`（Rust のテスト全部。コアの単体・結合、CLI、ローカル API、画面とコアの結合）・`check:clippy`・`check:doc`（`package.json` の同じ名前のものを呼ぶので、手元・Linux の CI と検査の中身がずれない）を走らせる。clippy と `cargo doc` も走らせるのは、`cfg(windows)` などの OS 別のコードは、その OS でないと検査されない（警告も、文書のリンク切れも見えない）ため。走らせないもの：書式（`cargo fmt --check`。`cfg` で外れるコードの `mod` も整形の対象なので、OS で変わらない）・画面の型チェック（`svelte-check`）・画面のテスト（`vitest`）・許可リストの検査。どれも OS で結果が変わらない（画面のテストは WebView ではなく Node.js 上で動く）ので、Linux だけで足りる。`rust-test` ジョブは `ci.yml` に置き、どれかが落ちても残りの検査を走らせて、OS ごとの失敗を 1 回の実行で全部出す（`pnpm` を動かすために Node.js と依存を入れる。1 分ほど）。
- **走らせる条件（2026-11-05 決定。オーナーの判断。案C）**：**リポジトリが公開のとき**（PR・main への push とも自動）と、**手動で実行したとき**（`workflow_dispatch`）だけ走らせる。**非公開の間は、macOS・Windows の CI は自動では回らない**。`ci.yml` の `rust-test` ジョブの条件は `github.event_name == 'workflow_dispatch' || github.event.repository.private == false` で、公開した時点で、ワークフローを直さなくても自動で回り出す。Linux の `pnpm check` は今までどおり毎回走る。
  - 理由：非公開のリポジトリは、GitHub の月の無料枠（Free は 12 ドル分。GitHub の公式の案内）で、macOS・Windows・Linux の分を合わせて数える。使い切ると**全ジョブが止まる**（Linux の `pnpm check` も。2026-11-05 に実際にこの作業で当たった）。標準のランナーは、公開リポジトリなら無料。
  - 手動の実行（`workflow_dispatch`）は、そのワークフローのファイルが**既定のブランチ（main）に入った後**でないと使えない（GitHub の決まり）。YUN-102 の PR（#83）では、非公開の間は `rust-test` が走らないため、最終の形（条件・手動の実行）は、マージ前には動かして確かめられていない。確かめられたのは、条件を足す前の版（97dc791）で Linux・macOS・Windows が全部成功したことまで。マージ後に最初の手動の実行で確かめること（YUN-87 の公開前の確認と同じ手順）。
  - 手動で実行する手順（非公開の間に macOS・Windows を確かめたいとき）：`gh workflow run CI --ref <ブランチ名>`（または GitHub の Actions 画面で CI を選び、「Run workflow」でブランチを選ぶ）。終わったら `gh run list --workflow CI --branch <ブランチ名>` で結果を見る。全ブランチの全コミットではなく、確かめたいコミットの先頭のブランチを 1 回だけ選ぶこと（1 回で macOS 約 2 分・Windows 約 15 分の料金がかかる）。配布用のビルドの試運転も同じ（`gh workflow run Release --ref <ブランチ名>`。ビルド・配布手順書 3.2）。
- **利用時間と費用の見込み**：非公開リポジトリでは、GitHub-hosted のランナーは料金（1 分あたり、2026-11-05 時点の GitHub の公式の案内：Linux 2 コア 0.006 ドル、Windows 2 コア 0.010 ドル、macOS 0.062 ドル。macOS は Linux の約 10 倍、Windows は約 1.7 倍）で数え、月の無料枠は Free が 12 ドル、Pro・Team が 18 ドル。下の数字は、**自動で回した場合**（公開後は無料なので、非公開の間に手動で回す分と、枠を見積もる目安）。実測（2026-11-05、キャッシュなし。`cargo doc` と Node.js の用意を足す前）：Linux の `pnpm check` 約 6〜7 分、macOS の `cargo test` と clippy 約 2 分、Windows 約 13〜15 分（コンパイルが約 5 分、`yunagi-core` のテストが SQLite の書き込みで約 3 分、clippy が約 3 分）。1 回の実行で、macOS 約 0.12 ドル、Windows 約 0.14 ドルの計約 0.26 ドル（Linux の `pnpm check` は別に約 0.04 ドル）。毎回自動で回すと、PR で push を平均 5 回として 1 PR あたり約 1.3 ドル、月に 8 PR で約 10 ドルになり、Free の枠（12 ドル）をほぼ使い切って全部止まる。これが非公開の間は自動で回さない理由。`Swatinem/rust-cache` は main への push と手動の実行が保存する（PR は main のキャッシュを使う）。非公開の間は main で走らないので、手動の実行が保存し、同じブランチの 2 回目以降はコンパイルの時間が減る見込み（まだ測っていない）。
  - 配布用 CI の試運転（`release.yml`。ビルド・配布手順書 3.2）も同じ考え方にした：1 回で macOS 2 組（各約 3 分）・Windows 2 組（約 10〜14 分）・Linux 約 13 分・検査約 13 分で、約 0.8 ドル。ビルドの成否を決めるファイルを変えた PR のたびに走っていたため、**非公開の間は PR で自動では走らせず**（`build` ジョブの `if`。検査の `verify` は Linux だけなので走る）、公開後は自動、手動はいつでも。タグの push の動きは変えない。
  - 非公開の間に、macOS・Windows を使う分を減らす手：Windows の `yunagi-core` のテストの待ち時間（約 3 分）を詰める（原因は未調査。1 件ずつ測ると 6〜11 秒のテストが、並行して走らせると 60 秒を超えたので、ディスクの待ちの競合が疑わしい）。リポジトリを公開すれば（2026-11-06 に公開と決まった。切り替えは YUN-109）、標準のランナーは無料になるので、費用の心配は無くなる。
  - **公開前の確認（最初のタグを打つ前に必ず行う。YUN-87 と公開準備の確認項目）**：公開前は macOS・Windows の CI は自動では回らないので、**直前に手動で全部通す**：公開するコミットで `gh workflow run CI --ref <ブランチ>` と `gh workflow run Release --ref <ブランチ>` を実行し、macOS・Windows の `cargo test`・clippy・`cargo doc` と、配布用 5 組のビルドがすべて成功することを確かめる。6 章のリリース判定にも入れる。
- **直したもの（2026-11-05。初めて macOS・Windows で走らせて分かったもの）**：
  - macOS：テストの一時フォルダ（`/var/folders/…`）が長く、UNIX ドメインソケットのパスが上限（macOS は 103 文字）を超えた。ソケットを使う結合テスト（`crates/cli/tests/cli/unix.rs`・`src-tauri/tests/api/unix.rs`）は、`/tmp` の下の短い一時フォルダを使う。CLI の結合テストが Linux の決まり（`XDG_DATA_HOME`、別の候補の既定ディレクトリ `.local/share/yunagi`）に寄っていたので、既定ディレクトリを求める環境変数の名前（`default_dir_vars`）と別の候補の場所を OS ごとに求める形にした（macOS は `HOME` だけで決まり、`Library/Application Support/Yunagi`）。`yunagi uninstall` の結合テストの既定ディレクトリは、動いている OS のものを使う。
  - Windows：①`tauri::test` で窓を作る結合テスト（`src-tauri/tests/bridge.rs`）の実行ファイルが、起動前に `STATUS_ENTRYPOINT_NOT_FOUND` で落ちた。Tauri が実行ファイルに埋めるマニフェスト（Common Controls v6 の指定）は本体にだけ入り、テストの実行ファイルには入らないため。`src-tauri/build.rs` でテストにも埋める。②`default_dir_macos` が Unix 形式の `/Users/a` を絶対のパスと見なせず落ちた（Windows 用に絶対のパスにした）。③`change_moves_database_and_backups`：Windows は開いたままのファイルを消せないので、閉じていない接続の元のデータベースが「消せなかったもの」（`ChangeReport::leftovers`）に残る。本番はコアを閉じてから呼ぶので起きない。テストは Windows ではそれを期待する形にした。④clippy の `result_large_err`：Windows だけ `StorageError` などが 128 バイト以上になり 99 か所で落ちた。`clippy.toml` で目安を 192 バイトに上げた（エラーは例外的な経路で、全部を `Box` にして OS の差に合わせるより、目安を上げるほうが小さい変更のため）。⑤テストの未使用変数（`cfg(unix)` の中でしか使わない）を直した。
- **自動テストで確かめられていないこと（既知の穴。YUN-87 が拾う）**：
  - Windows では、`crates/cli/tests/cli.rs`（直接モード・接続の手順・`doctor`・MCP・`yunagi uninstall` の結合テスト）と `src-tauri/tests/api.rs`（ローカル API の結合テスト）は、ロックと UNIX ドメインソケットを使うため `cfg(unix)` で、何も走らせない（`skipped:` と出る）。Windows の名前付きパイプ・CLI の結合の経路は、`crates/api` と `crates/cli` の単体テストと、実機でしか確かめられていない（4.5 の Windows の項目）。
  - macOS・Windows の CI は、窓（WebView）を開かない。画面の描画・IME・ショートカット・インストールは、実機のチェックリストで確かめる（2章の「手動」）。
  - macOS・Windows のテストの時間（Windows の `yunagi-core` が約 3 分）は、ランナーの混み具合で変わる。タイミングに依存するテストは、強制終了のテスト（4.1）のとおり、最大ではなく 90 パーセンタイルで判定する。macOS・Windows でこのテストが落ちたら、まず製品の変化かランナーの混雑かを見る。
  - 実際に Windows で 1 回落ちた（2026-11-05。同じコードの 4 回の実行のうち 1 回）：強制終了の試験（4.1。`src-tauri/tests/crash.rs`）の 6 番目で、保存を送ってから 1.7 秒たっても書き終えた知らせが 1 件も届かず、0.5 秒より前に打った文字が残らなかった。失敗したジョブだけを再実行すると通った。ランナーの一時的な停止（最初の保存の書き込みか子プロセスの起動）と見ているが、原因は確かめていない。切り分けのため、失敗の表示に、書き終えた保存の数と、送ったまま書き終えていない保存の経過時間を足した。再び起きたら、それを見て停止か製品の遅さかを決める（判定は緩めない。4.1）。

## 4. 重点テスト

### 4.1 データ保全

- 入力停止から 1 秒経過後にプロセスを強制終了（`kill -9`、タスクマネージャー）しても、その入力が失われないこと。入力中に強制終了しても、失われるのは直前 0.5 秒分以内であること。
  - 毎コミットの試験（2026-11-03 決定）：画面の部分（打った文字を保存として送るまで。`src/lib/autosave.test.ts`）と、コアの部分（コアを子プロセスで動かし、画面と同じ IPC の経路で保存し、途中で SIGKILL で止めてからデータベースを開き直す。`src-tauri/tests/crash.rs`）に分けて確かめる。送るまでの 0.25 秒と、1回の書き込みにかかる時間（0.25 秒未満を確かめる）を合わせて 0.5 秒以内とする（アーキテクチャ設計書 4.1「自動保存」）。
    - 判定の決まり（2026-11-03 決定）：失われないこと（打ち止めて 1 秒後に止めたら打ったものがすべて残る、打っている途中に止めたら止める 0.5 秒より前に打った文字がすべて残る）は、強制終了のたびにそのまま確かめ、緩めない。1回の書き込みの時間（送ってから書き終えた知らせが届くまで）は、すべての試験の保存（7回の試験で 30 回あまり）を合わせた 90 パーセンタイルが 0.25 秒未満であることで確かめ、最大は記録として出す。混んだ CI の機械では、ほかの処理に CPU やディスクを取られて、まれに1回だけ長くかかり（0.27 秒の例があった）、最大で判定すると、製品の変化と関係なく落ちるため。書き込みが遅くなる変更（全体が 0.25 秒を超える）は、90 パーセンタイルでも落ちる。10 回に1回だけ遅くなるような変更は 90 パーセンタイルでは落ちないが、その遅い保存の間に止めると失われる文字が出るので、失われないことの確かめ（止める時点を 6 通りにずらしている）で見つける。強制終了で止めた、まだ書き終えていない保存の時間は数えない（書き終えていないので測れない。失われたかは強制終了の結果で確かめる）。手元の測定（2026-11-03、Intel Core i7-11850H）は、38 回で 90 パーセンタイル約 4.3ms、最大約 6.4ms。本番ビルドを窓ごと動かして打鍵する試験は、画面にエディタができてから E2E（2章）で行う。
- 電源断を模擬した書き込み中断のあとでも、データベースが壊れずに起動できること。
- 自動バックアップが作成され、バックアップから復元できること。7日分を超えたら古いものから削除されること。
- 旧版で作ったデータを新版で開いたとき、マイグレーションが成功すること。失敗を模擬した場合に、自動でバックアップに戻ってデータが変更されず、旧版の再導入方法が案内されること（ビルド・配布手順書 5章）。新版で作ったデータを旧版で開いたとき、データに触れずに新しい版の入れ方が案内されること。壊れたデータベースを、起動時の画面から定期バックアップに戻せ、壊れたものが `backups/` に残ること（画面設計書 10.1、アーキテクチャ設計書 6.2）。

### 4.2 IME

各 OS の主要 IME で、次を確認する。

- 変換確定の Enter で TODO が追加されない、または誤って確定されないこと。
- 変換中の Esc、Mod 系ショートカットが誤動作しないこと。
- macOS（WebKit）で、変換確定（compositionend）の直後に届く Enter が項目の追加として扱われないこと（判定方法は操作仕様書 3章）。
- IME による誤操作は重大度「高」として扱う（support-runbook.md 3章）。
- Vimモードで、挿入モードからノーマルモードに戻ると英数入力に切り替わること。
- ノーマルモード中に IME がオンでも、キーが Vim の操作として扱われること。

Vimモードと IME の両立（操作仕様書 4.4。方式はアーキテクチャ設計書 3.4）。整理モードのリスト（4.3）とノート・振り返りのエディタ（4.2）の両方で、各 OS の主要 IME で確かめる。自動テストで確かめているのは、画面側の呼び出し（挿入モードの出入りで切替を呼ぶ条件、変換中のキーを物理キーから読み直すこと、設定画面の欄と制約の表示）と、コア側の切替の手順（入力状態を覚えて戻す順序、`fcitx5-remote`・`ibus engine` を呼ぶ引数と出力の読み方。呼び出しは偽のものに差し替えている）まで。OS の入力状態を実際に切り替えることは、次の項目を実機で確かめる。

- 切替（4.4 の 1）：日本語入力をオン（ひらがな入力）にして挿入モードで文字を打ち、Esc で抜けると英数入力になること。Ctrl+[（Windows・Linux）でも同じこと。変換中の Esc は、変換を取り消すだけで、挿入モードを抜けず、切り替えないこと。
- 復元（4.4 の 3）：挿入モードを抜けた時点の入力状態（ひらがな入力・英数入力）に、`i` `a` `o` などで挿入モードに入ったとき戻ること。ノーマルモード中に手で入力状態を変えても、戻すのは抜けた時点のものであること。設定「挿入モードで入力状態を戻す」を無効にすると戻さず、抜けたときの英数への切替は続くこと。窓が前面にないとき（別のアプリを使っているとき、日の切り替わり）に、別のアプリの入力状態が変わらないこと。
- ノーマルモード中の変換中のキー（4.4 の 2）：ノーマルモードのまま日本語入力を手でオンにして、`j` `k` `w` `a`（かなの母音）`i` `o` `dd` `3j` が Vim の操作になり、本文に文字が入らないこと。整理モードのリストでも同じこと。Shift 付きの `G` `A` も同じこと。
- 確認が済んでいないもの（Linux 以外では実機で動かしていない。Linux の fcitx5 は、実装時に、切替の手順を実機の fcitx5 に対して動かし、英数への切替と復元を確かめたが、アプリの窓を通した確認はしていない）：
  - AppImage 版（Linux）：AppImage から起動したアプリが、ホストの `fcitx5-remote`・`ibus engine` を呼べること（AppImage が足す環境変数で、子プロセスのコマンドが動かなくならないこと）。呼べなければ、子プロセスの環境変数を整える。
  - macOS（日本語入力・Google 日本語入力）：入力ソース API で ASCII 入力に切り替わり、抜けた時点の入力ソース（日本語入力の各モードを含む）へ戻ること。切替はメインスレッドで行い、止まったり異常終了したりしないこと。
  - Windows（Microsoft IME・Google 日本語入力）：WebView2 のフォーカスのある窓の IME に IMM の指示が届き、IME のオン・オフが切り替わること。届かなければ、実装（`src-tauri/src/ime.rs` の `win`）を直す。
  - Linux の fcitx5-mozc：アプリを通して、切替と復元が働くこと（X11・Wayland）。
  - Linux の IBus-mozc：`ibus engine` で英数（`xkb:us::eng`）に切り替わり、元のエンジンに戻ること。
  - Linux で fcitx5 も IBus も動いていない環境：設定の操作区分に制約の文が出て、ノーマルモード中のキーは Vim の操作になること（4.4 の 4）。

### 4.3 Vimモード

- 操作仕様書 4章に記載した全キーの動作。
- `<Space>t` / `<Space>b` による行送り（単一行・ビジュアル選択の複数行）。
- Vimモードの有効・無効の切替が即時に反映されること。
- ノート・振り返りのエディタ（操作仕様書 4.2）：4.2 の表のモード・移動・編集・検索が動くこと（画面の配置が要る j / k は実機で確かめる。自動テストの jsdom には配置が無く、動かない）。モード（NORMAL / INSERT / VISUAL）が右下に出ること。`<Space>t` `<Space>b` `<Space>h` がノートでだけ動き、振り返り欄では何も起こらないこと。`/` `?` の検索欄が下端に出て、ライト・ダークの両方で読めること。ブロックのカーソルがライト・ダークの両方で見えること。
- Vimモードでも、Mod を使う標準のショートカット（Mod+Z の取り消し、コピー・貼り付け・切り取り・全選択、割当を変えたキー）が動き、Vim が横取りしないこと。Windows・Linux では Ctrl+R がやり直し、Ctrl+V / A / X / D / U などが Vim の操作にならないこと。
- 整理モードのリストから Tab で振り返りの欄に移ったとき、Vim のキーで操作できること。ノーマルモードの Space や Vim に無いキーが、本文に文字を入れないこと。
- Windows・Linux の Vimモード有効時、Ctrl+[ が Esc として動作し日付移動が起きないこと、前日・翌日への移動が Alt+[ / Alt+] で行えること。ふりかえり（S-08）の週の移動も Alt+[ / Alt+] で行え、Ctrl+[ では動かないこと。Vimモード無効時は Ctrl+[ / Ctrl+] で日付移動できること。
- 整理モードのリスト（操作仕様書 4.3）：ノーマルモードで本文が入力欄にならず、j / k / gg / G / Tab で移り、o / O・i / a で挿入モードに入り、Esc（Windows・Linux は Ctrl+[ も）でノーマルモードに戻ること。持ち越し済みの項目と取りやめた TODO で、i / a / x が本文・状態を変えず、上部のバーに知らせること（o / O は足すだけで知らせないこと）。
- ショートカット割当（操作仕様書 1章「割当の変更」）：キーを変えると、そのキーで動き、古いキーでは動かないこと。キーの案内・サイドバー・パレット・ノートの行のメニューのキーの表記が変わること。重なる範囲の別の操作と同じキー、Mod も Alt も付かないキー、Ctrl+Alt（AltGr）、Mod+Z・C・V・X・A は断られること。初期割当と同じキーにすると、Vimモードの切替で初期割当に従うこと。3 OS のキー配列（US・JIS・ドイツ語）で、記号のキー（`[` `]` `\` `,`）の割当が押した文字で動くこと。

### 4.4 持ち越し

- 日付の切り替わり時刻をまたいだ利用（深夜 3:59 と 4:01）で、論理日付が正しく切り替わること。
- 数日空けて起動した場合に、「前回の日」（今日より前で、項目またはノートが存在する直近の日）から持ち越しが提示されること。それより前の日の項目は提示されないこと。
- 持ち越し回数がしきい値（既定3回、設定で変更可）以上の TODO に見直しの選択肢（分割する／やめる）が出ること。「外部ツールへ戻す」は外部連携が有効で外部課題と紐付いた TODO にだけ出ること。障害には回数 `↻n` が表示され、見直しの選択肢は出ないこと。
- 分割した場合、元の項目が `dropped`（`close_reason=split`）になり、今日に作った子 TODO が `split_from_id` で元を指し、`carry_count` が 0 であること。「やめる」を選んだ TODO が `dropped`（`close_reason=dropped`）になること。
- 持ち越しの確定（3つのボタンのどれでも）は Mod+Z で取り消せないこと：確定の直後に Mod+Z を押しても、持ち越した項目・分割の子・取りやめた項目・持ち越しの記録が変わらないこと。確定の前に同じ日で行った操作（項目の追加・削除・並べ替えなど）は、確定の後の Mod+Z で戻せること。持ち越した項目や分割の子の削除は Mod+Z で戻せること（持ち越し先の削除は、元の項目が削除の後に変わっていたら戻せず、理由が表示される。データモデル設計書 3章 item、操作仕様書 2章）。持ち越しの画面を出している間は Mod+Z が背後の履歴を動かさないこと（操作仕様書 2章「取り消し・やり直し」）。
- 過去日のボードが、持ち越し後も当時の状態のまま残ること。
- 過去日のボードで、持ち越し済みの項目の行末に「→ 持ち越し先の日付」が表示され、クリックで持ち越し先の日が開いてその項目が選ばれること。持ち越し済みの項目への完了・解消の切替（Mod+Enter・x・チェック欄のクリック）と本文・解消メモの編集が受け付けられず、上部のバーに持ち越し済みである旨が表示され、Mod+Z でもその項目の状態・本文が変わらないこと。削除と並べ替えはできること。持ち越し先を削除すると、元の項目が通常どおり操作できるようになること。A→B→C と2日続けて持ち越して B を削除しても、A が C へ持ち越し済みのまま（`carried_to_id` が C）で、操作できないこと。削除の後に元の項目を完了にした場合は、持ち越し先の削除を Mod+Z で取り消せず、理由が表示されること。元の項目を変えていなければ取り消せること。持ち越し先を削除してその日に項目もノートも無くなった場合、次の日の持ち越しで元の項目がもう一度提示され、持ち越した後は、前の持ち越し先の削除を Mod+Z で取り消せないこと（操作仕様書 2章、データモデル設計書 3章）。
- 過去日のボードで、持ち越し済みの項目と取りやめた TODO の本文が、入力欄でなく読み取り専用で表示されること。次の操作が、本文・状態・解消メモ・完了時刻を変えず、保存も送られず、上部のバーに持ち越し済みである旨（取りやめた TODO は変更できない旨）が表示されること：文字を打つキー（英小文字・Shift 付きの大文字・Space・日本語入力の変換の開始）、Backspace・Delete、貼り付け（Mod+V）、切り取り（Mod+X）、ほかのアプリや行の本文からの文のドロップ、解消メモの文を押す操作（持ち越し済みの障害）、Vim モードの `i`・`a`・`x`（Vim モードを作った後）。Enter が、行のどこでも本文を変えず（分けずに）直下に空の項目を足し、知らせを出さないこと。Windows・Linux の Alt+文字（Alt+F など）が知らせを出さず、OS・WebView のキーを妨げないこと。Mod+C・削除・並べ替え・項目間の移動は通常どおりできること。Mod+Z・`u` は、その項目の本文・状態を戻さず、履歴の1つ前の記録（別の項目の操作）を取り消すこと。過去の日のノート・振り返りは通常どおり編集できること（操作仕様書 2章「本文を変える操作の範囲」）。
- 過去日のボードで、取りやめた TODO（「やめる」「分割する」）が取り消し線と破線のチェック欄で表示され、行末に「やめた」「分割した」が出ること（「外部ツールへ戻す」は外部連携の試験で確かめる）。件数（TODO 数・残り）に数えられないこと。完了・未完了の切替（Mod+Enter・x・チェック欄のクリック）と、本文を変える操作が、直前の項目の試験（持ち越し済みの項目）と同じ範囲で受け付けられず、上部のバーに変更できない旨が表示され、Mod+Z でもその項目の状態・本文が変わらないこと。削除と並べ替えはできること（画面設計書 3章、操作仕様書 2章「本文を変える操作の範囲」）。
- 持ち越しの画面を表示している間に、エージェントが前回の日の TODO を `complete_todo` で完了にした場合、その項目が一覧から外れ、「すべて持ち越す」を選んでも持ち越されないこと。同じ間に `reopen_todo` で未完了に戻した TODO がチェックの無い状態で一覧に加わり、`edit_todo` で変えた TODO の本文と `edit_blocker` で変えた障害の本文が一覧に表示されて、持ち越した項目に写ること。`add_todo --date` で前回の日に足した TODO がチェックの無い状態で加わり、「すべて持ち越す」では持ち越され、「選んだものを持ち越す」ではチェックを付けたときだけ持ち越されること。「分割する」を選んで子を入力していた TODO をエージェントが完了にすると、その TODO が一覧から外れ、確定しても分割されず子も作られないこと（画面設計書 5章）。

### 4.5 エージェント連携

- 各スコープの許可・不許可で、操作の成否とエラー内容が仕様どおりであること。
- CLI からの書き込みが `cli` クライアントとして記録され、既定では `read` のみであること。スコープ変更と `agent revert` が、非対話の実行では `permission_denied`（終了コード 3）になること。
- 識別子のない MCP 接続が `unknown` として `read` のみで扱われること。`unknown` に `read` 以外のスコープを足す指定が `invalid_argument` になること。
- 権限の管理と変更履歴（A-08。YUN-94。コアの `domain::agent_admin`・`domain::history`、API の管理の操作、CLI。自動テスト）：
  - 権限の一覧（`agent permissions`、`--json`）と履歴（`agent history`。新しい順、`--client`・`--unseen`・`--limit`・`--before`、人の取り消しの記録を含む）が、端末でなくても読めること。確認済みの印を付けないこと。`--allow`・`--deny` の追加・除去で、結果が 2章の表の順になること。同じスコープを足すと外すの両方、知らないスコープ名、登録のないクライアント（`not_found`）の扱い。
  - 変更（`--allow`・`--deny`）と `agent revert` が、端末でない実行では、何も書かず `permission_denied`（`required_scope` なし、終了コード 3）になり、データベース（権限・change_log）が変わらないこと。ID の形の誤りと CLIENT の欠けは、端末の判定より先に 2 になること。端末では、変更内容と `[y/N]` が表示され、`y`・`yes` だけが承諾になり、ほかは取りやめ（0）、入力が閉じていれば失敗（1）になること。`--json` が確認の要る形で断られること。
  - 取り消しの判定：記録の操作が変えた欄だけを戻し、ほかの欄に人が加えた変更が残ること。人が同じ欄を変えていれば `conflict`（`changed`、`changed_fields`、終了コード 5）で、`--force` で上書きできること。確認の後に変わった（`expect` が合わない）ときは、`--force` でも書かず止まること。追加の取り消しが項目の削除で、並べ替えだけでは `changed` にならず、人が本文を変えていれば `changed` になること。ノート・振り返りは本文全体で判定し、`--force` が本文全体を戻して、差分が「いまの本文 → 戻す本文」で出ること。
  - 持ち越し済みの項目の欄の取り消しは `carried_over`（`carried_to_id` つき）、取りやめた TODO の欄の取り消しは `invalid_argument`（`close_reason` つき）で、`--force` でも通らないこと。追加の取り消しは、どちらの項目でも削除として通ること。削除済みの項目の欄の取り消しは `not_found`、追加の取り消しはすでに戻っている扱いで成功すること。
  - すでに取り消し済みの記録、いまの値がすでに戻したい値の記録が、何も書かずに成功し（後者は記録を取り消し済みにし）、取り消しの記録が増えないこと。取り消しの記録（`agent.revert`）や存在しない記録は取り消せないこと（2・4）。取り消しの記録が `actor = human`・クライアントなし・`revert_of_id` つきで、`before`/`after` が欄ごとのオブジェクトであり、取り消しの後に画面が同じ状態を保存しても行き違いと判定されないこと。
  - アプリ経由（`src-tauri/tests/api.rs`）：管理の操作が `read` を外したクライアントでも使え、一覧・計画では `changed` が出ず、権限の変更と取り消しで `changed`（`by: agent`）が出ること。取り消しが、画面の入力中（`user_editing`）・保存の失敗中（`storage_unavailable`）で書かないこと。
- **`yunagi uninstall` の自動テスト（YUN-99。ビルド・配布手順書 4.4、アーキテクチャ設計書 6.5、CLI・MCP 仕様書 3.1）**：結合テストは `crates/cli/tests/cli/uninstall.rs`、場所の計算・消す層・Windows の文字列は `crates/cli/src/uninstall/` の単体試験、`XDG_DATA_HOME` の 4 通りと識別子の一致はコアの `data_dir.rs`。**利用者の実際の環境には触れない**：`HOME`・`XDG_DATA_HOME` を一時フォルダに差し替え、動かす前に毎回、差し替えが効いていること（`HOME`・`XDG_DATA_HOME`・既定ディレクトリ・実行ファイル・Homebrew の場所がすべて一時フォルダの下）を表明する。消す層は、一時フォルダの外を消そうとしたら消さずに panic し（保存先を外に向けた `config.json` で確かめる）、本番の決まり（相対パス・`..`・ルート・ホームそのものを断る）も単体で確かめる。確かめていること：`--purge` なしでデータと WebView のデータが残ること、`--purge` で Yunagi のものだけが消え（利用者のほかのファイル・ほかのアプリのフォルダ・`~/.local/bin` のほかのコマンドが残る）、保存先を変えているときは保存先のデータベースのファイルと `backups/` だけが消え保存先のフォルダと利用者のファイルが残ること、アプリか MCP サーバーがロックを持っていれば何も消さず `busy`（7）、`--purge` で `config.json` が壊れていれば何も消さず 6（`--purge` が無ければ読まずに消せる）、端末でなければ 3、`n`・空の答えは何も消さず 0、入力が閉じていれば 1、Homebrew（Caskroom の有無）と正規の場所の外は何も消さず 5（案内に `--zap` の有無）、既定ディレクトリが無いときにロックのために作らないこと、手で置いた `~/.local/bin/yunagi` を消さず一覧に出して 1、シンボリックリンクはリンクだけを消し先に触れないこと、消せなかったものがあってもほかは消し続けて一覧に出し 1。OS を呼ぶ部分は偽物で確かめる：macOS の 5 か所の消去と `defaults delete` の呼び出し、Windows の `PATH` から `bin` だけを外す（ほかの項目は書かれたまま）こと、切り離す後片付けの引数（終了を待つ ID・アンインストーラー・インストール先・`--purge` のときだけ既定ディレクトリ）、その場では `yunagi.lock` 以外だけを消してインストール先は後片付けに任せること、起動に失敗したときの一覧と 1。実機の確認は 4.9。
  - 画面の管理の操作（CLI・MCP 仕様書 7.4。コアの単体試験 `agent_admin`・`history`・`agent_client` と、Tauri コマンドの結合試験 `src-tauri/tests/bridge.rs` の `agent_admin_commands`）：登録の削除が、変更履歴にも項目にも指されていない登録だけに通り、固定の `cli`・`unknown`（`fixed_client`）と履歴のある登録（`client_in_use`）は何も消さず、消した識別子が次の接続で `read` だけで登録し直されること。確認済みの印が、渡した記録だけに付き、最初の時刻を残し、一覧では付かないこと（付けたら `changed` が届き、上部のバーの件数が減る）。権限の変更が、見せた権限（`expect`）が違えば書かず `scopes_changed` になり、`unknown` への `read` 以外が断られ、変えたら `changed`（`by: agent`）が届き、変わらなければ届かないこと。取り消しが、入力中の項目で `user_editing`、見せた後に状態が変わっていれば `changed`（`afterPreview`）になり、取り消したら記録が確認済み・取り消し済みになること。
  - MCP に出さないこと（CLI の結合テスト `crates/cli/tests/cli/unix.rs`）：`tools/list` に管理の操作が無く、`tools/call` で `list_agents`・`list_changes`・`set_agent_scopes`・`preview_revert`・`revert_change` を呼ぶと `-32602` になり、権限が変わらないこと。
  - **実機で確かめる（YUN-87 が拾う。いまは未確認）**：Windows のコンソール（cmd・PowerShell・Windows Terminal・Git Bash）で、標準入力と標準出力が端末かの判定（確認を得られるか）が期待どおりか。macOS・Windows のローカル時刻の表示。変更履歴の画面（S-06。YUN-81 で作った。画面の自動試験は `src/agents/Agents.test.ts`・`src/settings/Settings.test.ts`、Tauri コマンドの結合試験は `src-tauri/tests/bridge.rs` の `agent_admin_commands`）の、実機での確認：アプリでの取り消し（`changed` の後の再読み込み、入力中のノートへの取り込み。ノートや項目の本文に入力した直後に変更履歴を開いたとき、フォーカスがパネルへ移ってエディタの守る行が空になり、そのノートの取り消しが `user_editing` で断られないこと）、パネルの見た目（権限の一覧と変更の一覧のスクロール、取り消しの確かめる文・差分の表示、◆ と「取り消し済み」の見え方）、フォーカスの動き（開く・閉じる・設定へ戻る）、設定のエージェント区分（権限の確かめる文、登録を消す、ローカル API の状態。Linux の UNIX ドメインソケットと Windows の名前付きパイプで、状態の表示が変わらないか）。
- アプリ起動中と停止中の両方で、CLI・MCP の操作が成功すること。MCP サーバーの起動中にアプリを起動・終了しても、操作が失敗せずロックが残らないこと。
- 接続の手順（アーキテクチャ設計書 4.4。CLI と MCP の両方で、読み取りと書き込みの両方）：
  - アプリが動いているとき、ローカル API につながり、ロックを待たずに（5 秒かからずに）成功すること。ロックを取らないこと。

Nothing changed.`）と `--json` の `updated`・`text` が仕様どおりで、終了コードがどちらも 0 であること。前後に空白や改行を含む本文が前後の空白を除いて保存され、応答の `text` に除いた後の本文が入ること。`echo` で末尾に改行の付いた本文を `TEXT` の `-`（標準入力）で2回送ると、2回目が `updated: false` になること。画面で末尾に空白を付けて入力した本文と、`add_todo`・`add_blocker` で前後に空白を付けて送った本文が、前後の空白を除いて保存されること。途中に改行を含む本文が `invalid_argument` になり、保存の再試行中でも空白だけの本文が `storage_unavailable` ではなく `invalid_argument` になること。障害の解消メモを入力中に、その障害へ今と同じ本文の `edit_blocker` を送ると、`user_editing` にならずに `updated: false` で成功し、解消メモの入力が壊れないこと。同じ本文でも、保存の再試行中は `storage_unavailable`、持ち越し済みの項目では `conflict`（`reason: carried_over`）、その項目の本文を入力中は `conflict`（`reason: user_editing`）、取りやめた TODO では `invalid_argument` になること（MCP・CLI 仕様書 3章）。
- 持ち越し済みの項目（前の日に残っている元の項目）の ID への `edit_todo`・`edit_blocker`・`complete_todo`・`reopen_todo`・`resolve_blocker` が、何も変えずに `conflict`（`reason: carried_over`。終了コード 5）になり、エラーに持ち越し先の `carried_to_id` と `carried_to_date` が入ること。元の項目と持ち越し先の項目のどちらの状態・本文・解消メモ・完了時刻も変わらず、change_log に記録されないこと。同じ操作を何度送っても同じ結果になること。`carried_to_id` に送り直すと、通常の決まりで成功すること。2日続けて持ち越した項目では、最初の元の項目への操作が次の日の項目を指し、そこへ送り直すと、さらに今日の項目を指す `carried_over` になること。持ち越し先が取りやめた TODO なら、送り直した `edit_todo`・`complete_todo`・`reopen_todo` が `invalid_argument` になること。持ち越し先を削除した後は、元の項目への操作が通常どおり受け付けられること。判定の順が `invalid_argument`・`storage_unavailable` の後、`user_editing`・`note_exists` の前であること（例：別の解消メモがある持ち越し済みの障害への `--note` 付きの `resolve_blocker` が `carried_over` になること）。`get_board`・`open_board`・`search` の各項目の `carried_to_id`・`carried_to_date` が、持ち越し済みの項目では持ち越し先の id と日付、それ以外では `null` であること（MCP・CLI 仕様書 3章・4.3）。
- 解消メモのある解消済みの障害を画面で未解消に戻したとき（Mod+Enter・x・チェック欄のクリック）、解消メモが消えずに残り、未解消の間は表示されず、解消時刻が空になること。もう一度解消すると、残っていた解消メモが表示されて欄が開き、カーソルが末尾にあり、解消時刻が新しい時刻になること。未解消に戻した障害への `--note` 付きの `resolve_blocker` は、残っている解消メモと同じ本文なら解消になり、別の本文なら `conflict`（`reason: note_exists`）で何も変わらないこと。`get_board` の `resolution_note` に残っている解消メモが返ること。未解消に戻した直後に Mod+Z で取り消すと、元の解消時刻に戻り、解消メモの欄が開かないこと。未解消に戻した後にエージェントが `resolve_blocker` で解消していた場合は、Mod+Z でエージェントの解消時刻が上書きされないこと。解消メモの残った障害を `--note` なしの `resolve_blocker` で解消すると、応答の `resolution_note` に残っていた解消メモが入ること。解消メモを入力中に未解消に戻すと、入力が保存されてから欄が閉じ、その後の `--note` 付きの `resolve_blocker` が `user_editing` にならず解消メモの判定に従うこと。解消メモの残った未解消の障害を持ち越すと、次の日の障害の解消メモが空で、元の日の障害に解消メモが残ること。画面で TODO を未完了に戻すと完了時刻が空になり、Mod+Z で取り消すと元の完了時刻に戻ること（操作仕様書 2章、MCP・CLI 仕様書 3章）。
- ノートの入力中（IME の変換中を含む）に `append_note`・`edit_note` を受けても、カーソル・選択範囲・変換中の文字が保たれ、取り込んだ変更が Mod+Z で取り消されないこと。振り返りの入力中の `append_reflection` も同じであること。
- カーソルのある行への `edit_note` が `conflict`（`reason: user_editing`）になること。カーソル行より上にまだ保存していない行を足した状態でも、カーソル行の判定が保存済みの本文の行番号で正しく行われること（隣の行を書き換える `edit_note` は受け付けられ、カーソル行への `edit_note` は `conflict` になること）。カーソル行の保護は、最後の入力から 10 秒たつか、フォーカスが外れるか、アプリが前面から外れると終わり、カーソル行への `edit_note` が受け付けられること。保存済みの行を書き換えてまだ保存していない状態で、カーソルを別の行へ移した後でも、その行への `edit_note`（書き換え・削除・移動）が `conflict`（`reason: user_editing`）になること。
- `--expect` の不一致による `conflict` が `reason: changed` になり、入力中による `conflict`（`reason: user_editing`）と区別できること。両方に当たる `edit_note` は `reason: changed` になること（MCP・CLI 仕様書 3章・4.3）。
- 画面が守る行を知らせた後にエージェントの `append_note` などで版が進んだとき、知らせ直しが届くまでは同じノートへの `edit_note` が `conflict`（`reason: user_editing`）になり、知らせ直しの後は守る行以外への `edit_note` が受け付けられること。
- 読み取り（`get_board`・`open_board`・`get_note`・`search`）の権限：`read` を持たないクライアント（スコープを空にしたもの、`append` などの書き込みのスコープだけのもの）と、登録されていないクライアントは、アプリ経由でも直接モードでも `permission_denied`（`required_scope: read`、終了コード 3）になり、何も読まれないこと。`get_note` では、権限の誤りが `--heading` の誤りや `not_found` より先に返ること。`read` だけを持つクライアントで読めること。画面の読み取り（`get_screen_board`・`get_text_doc`）は権限に関係なく動くこと（MCP・CLI 仕様書 2章）。コアの関数の試験は YUN-64（`domain::board`・`domain::text_doc`）と YUN-90（`domain::search`）、CLI のアプリ経由（`src-tauri/tests/api.rs`）・直接モード（`crates/cli/tests/cli.rs`）の両方と終了コード（3・2）の試験は YUN-90 で行った。MCP の試験（アプリ経由・直接モードの両方で、`read` を持たない識別子と識別子なしが `isError` の `permission_denied` になること）は YUN-92 で行った（下の「MCP サーバーの自動テスト」）。
- `get_note --heading` の照合：`get_board` の `headings` の文字をそのまま渡すと当たること。時刻だけ・件名だけ・部分一致・`## ` つきでは `not_found` になること。`9:05` と `09:05` が別の見出しとして扱われること。全角空白や途中の空白を含む件名が書いたとおりに当たり、`H` の前後の空白は除かれること。件名の無い見出し（`## 10:00`）が当たること。同じ文字の見出しが複数あるとき、すべての区間が本文の順に返ること。区間が見出しの行から次の時刻付き見出しの前までで、時刻の付かない `##` の見出しは区間を区切らないこと。前置きは見出しでは選べないこと。`H` が空・空白だけ・途中に改行を含むと `invalid_argument`（終了コード 2）になること。まだ書いていない日は `not_found` で、day の行を作らないこと。CRLF のノートで、`text` の各行の末尾に CR が残り、LF で分けた行を `edit_note` の `--expect` にそのまま渡せること。返った `start_line` と区間の行の位置から求めた行番号を、そのまま `edit_note --line` に渡すと正しい行に当たること。見出しを指定しない `get_note` が全文と版を返すこと。
- ノート・振り返りで、エージェントの変更と利用者の保存が行き違った場合（版の番号の食い違い）に、利用者の入力とエージェントの変更がどちらもエディタに残ること。同じ位置への行の追加と、同じ行を両方が変えた場合は、両方が残り利用者の行が先になること。取り込みの後、次の保存が弾かれず、エージェントの行が二重にならないこと。
- エージェントが保存済みの行の範囲を書き換え・削除・移動し、その範囲の中に利用者のまだ保存していない新しい行がある場合、利用者の行が範囲のあった位置に残る（移動では範囲と一緒に動かない）こと。
- 利用者が同じノート・同じ項目に続けて入力して保存が続いても、利用者自身の保存どうしが行き違いにならず、最後の入力が残ること（例：項目の本文を `foo` から `foobar` にしたとき、`foo` の保存が後から書き込まれないこと）。
- 項目の保存では利用者が変えた欄だけが書かれること。本文の入力中にエージェントが `complete_todo` で完了にし、その後に利用者の本文の保存が届いた場合、項目が完了のままで、本文は利用者の入力になっていること。同じ欄をエージェントも変えていた場合は、利用者の入力が残り、エージェントの変更が変更履歴に残ること。
- 利用者が画面で TODO を完了にしてから保存が書き込まれるまでの間（保存を遅らせて模擬する）に、同じ TODO への `complete_todo` が届いた場合、届いた時点で付いた未確認の印（上部のバーとサイドバーの件数、項目の行頭の菱形）が保存の後に消え、項目が完了で完了時刻が利用者の操作の時刻になり、その操作の記録が change_log と変更履歴 S-06 から消え、その記録を指定した `agent revert` が `not_found` になること（アーキテクチャ設計書 4.1）。未完了に戻したときの `reopen_todo`、障害を解消したときの `--note` の無い `resolve_blocker` も同じであること。`--note` 付きの `resolve_blocker` では、記録から状態と解消時刻の欄だけが外れ、解消メモはエージェントの変更として未確認の印付きで残ること。エージェントの操作が届いた後、保存の最初の書き込みが失敗し、再試行で成功した場合も同じ結果になること。その後にエージェントが同じ操作をやり直すと `updated: false` で成功し、記録が増えないこと。行き違いの間にエージェントが完了・未完了に戻す・完了と続けた場合は、最初の完了の記録だけが消え、後の2つの記録が残り、未完了に戻した記録の `before` が利用者の完了（完了時刻は利用者の操作の時刻）になり、項目の完了時刻が最後の完了の記録の `after` のままで、最後の完了の記録を `agent revert` で取り消せる（`reason: changed` にならない）こと。行き違いの間にエージェントが完了にしてから未完了に戻した場合は、完了の記録が消え、未完了に戻した記録の `before` が利用者の完了になり、利用者の保存で完了になること。利用者が完了・未完了に戻す・完了と続けて1つの保存にまとまり、その間にエージェントが完了にした場合は、エージェントの記録が消えること。エージェントの記録と利用者の操作が同じミリ秒の場合は、利用者の操作が先とみなされること。完了済みの TODO を画面で未完了に戻して保存されるまでの間に同じ TODO への `reopen_todo` が届いた場合も記録が消え、その後に Mod+Z で取り消すと、エージェントの変更があったとはみなされずに完了に戻り、元の完了時刻になること（操作仕様書 2章）。利用者の操作より前にエージェントが完了にしていた（画面の再読み込みの前に利用者が完了にした）場合は、エージェントの記録が残ること。利用者が完了にしてから未完了に戻して1つの保存にまとまった場合は、項目が未完了になり、エージェントの記録が残って `agent revert` が `reason: changed` になること。
- 取り消しが正しく働き、人の変更と衝突した場合に `conflict`（`reason: changed`）になること。項目では、エージェントが変えた欄だけで判定し、その欄だけを戻すこと（例：エージェントが完了にした後に人が本文を変えた項目は、取り消しで未完了に戻り、本文は人の変更のまま残ること）。
- `yunagi agent setup` が既存設定をバックアップし、確認後にのみ書き込むこと（自動テストは上の項目のとおり。YUN-93）。
  - **実機で確かめる（Linear の YUN-87 が拾う。いまは未確認）**：Linux では、本物の `claude`（2.1.318）・`codex`（0.166.0）を一時フォルダの `HOME` で動かし、登録・登録済みの再実行・違う内容の付け直し・Codex の追記と `codex mcp get` での表示まで確かめた。未確認は次のとおり。①Windows での登録（`claude.exe`・`codex` の実行、`%USERPROFILE%\.claude.json`・`%USERPROFILE%\.codex\config.toml`、`yunagi.exe` を包まずに登録して起動できるか）と macOS での登録。②Codex で、`env_vars` に設定されていない名前を書いたとき、macOS・Windows でもエラーにならず起動するか（Linux は起動する）。③macOS・Windows で、Claude Code が既定で環境変数を引き継ぐか、Codex の基準の環境の中身（`HOME` と `LOCALAPPDATA` を含むか）、Claude Code の `CLAUDE_CODE_MCP_ALLOWLIST_ENV=1` の基準の環境に `LOCALAPPDATA` が含まれるか。④登録した後、Claude Code・Codex を起動して `yunagi mcp` が実際につながること（上の MCP サーバーの実機の項目と一緒に）。

### 4.8 OS 全体のショートカット（Yunagi を前面に呼び出す）

操作仕様書 1章「OS 全体の操作」、アーキテクチャ設計書 3.5。自動テストで確かめているのは、割当 → OS のキーの変換、登録・外す・登録し直す・失敗の分類（登録の部品を偽物に差し替えたもの）、画面側の登録のし直し（割当を変える・保存に失敗して戻る・使えなくなる・初期値に戻す）と、設定の理由の表示まで。OS に実際に登録して窓が前面に出ることは、どの OS でも実機で確かめていない（開発は Linux でしか行えず、その Linux でも窓を通した確認はしていない）。次を実機で確かめる（テスト計画書の手動試験。Linear の YUN-87 が拾う）：

### 4.11 自動更新

ビルド・配布手順書 5章（YUN-83）。自動テストは 4.7。公開鍵・配布元（YUN-100）と配布用 CI の署名と公開（YUN-101）が無いので、実際の更新はまだ一度も通していない。次を実機で確かめる（YUN-87 が拾う。いまは未確認）：

- 3 つの OS（配布する全アーキテクチャ）で、旧版から新しい版への更新が、通知 → 「更新して再起動」→ ダウンロード → 再起動で最後まで通り、再起動後に新しい版で起動し、データが残っていること。Linux は AppImage（動作中のファイルの入れ替え）、macOS は `.app.tar.gz`（アドホック署名の後の入れ替え。入れ替えた後も起動すること）、Windows は NSIS（`installMode: passive`。進み具合だけが出て、操作が要らないこと。入れ替えの中でアプリが終わり、新しい版が自動で起動すること）。
- 更新前のバックアップ：マイグレーションを含む版へ更新したとき、再起動後に `backups/` にマイグレーション前のバックアップができていること（07 5章）。マイグレーションに失敗する版で、バックアップに戻り、エラー画面が旧版の再導入方法を案内すること。
- 署名：署名に版が入る形で署名ファイルが作られ、`requireSignedVersion` を有効にしたまま更新が通ること（入らない Tauri の CLI だと、すべての更新が断られる）。署名を壊した配布物・別の鍵で署名した配布物・`latest.json` の版と署名の版が違う配布物が、断られて入れ替わらないこと（通知に「更新できませんでした」が出て、データベースを閉じていないこと）。
- 無効時に通信しないこと：設定で更新の自動確認を無効にして、起動して数分と 24 時間を過ぎるまで、配布元への通信が 1 回も無いこと（ネットワークの監視で外から確かめる）。有効に戻した直後に通信が始まること。公開鍵と配布元が空のままのビルドで、通信が無く、通知も出ないこと。
- 作業中の扱い：ノートに入力している最中に「更新して再起動」を選んでも、再起動の後に入力が残っていること。保存に失敗している状態では更新が始まらないこと。ダウンロード中にアプリを使い続けられること。
- Linux の `.deb`・`.tar.gz` で入れたアプリが、配布元を設定していても確認せず、通知も出さないこと（AppImage だけが対象）。
- 日本語の更新内容が文字化けせず、長い更新内容が表示の中で送れること。配布元に届かない・遅いときに、アプリの起動と操作が重くならないこと。

### 4.12 利用者ガイド（日英）

利用者ガイド（`docs/user/ja/guide.md`・`docs/user/en/guide.md`。YUN-105）の確かめ方と、ガイドに載せる画面写真の撮り方。ガイドは、画面の文言・キー・コマンドを実際のコードに合わせて書き、設計書の内部の言葉（課題番号・章の番号・内部の型名）は出さない。

**自動テスト**（`scripts/docs/guide.test.ts`。`pnpm check:web` に含まれ、毎コミット走る）：

- 日英の構成がそろっていること：見出しの深さと章の番号の並び、コードの囲みの数・言語・行数、ショートカットの表の行数とキーの欄、文中のキーの並び、公開前に決まる仮の表記（`<公式サイト>` と `<official-site>`、`<tap名>` と `<tap>`）の数。
- コードと食い違わないこと：ショートカットの表が `src/lib/keymap.ts` の初期割当と過不足なく一致する（取り消し・やり直しを除く）。ガイドに書いた `yunagi` のコマンドとオプションが `yunagi --help` の本文（`crates/cli/src/args.rs` の `USAGE`）にある。ガイドが引く設定の項目名・ボタン名・通知（「選んだものを持ち越す」「更新して再起動」「保存できていません」など）が、画面の文言（`src/lib/i18n*.ts`）と同じ。設定の区分の名前は日英とも英字（General・Display・Operation・Data・Agents）で書く。
- 利用者向けの書き方であること：課題番号・設計書のパス・「設計書」「仕様書」の言葉が出ていない。

自動では確かめられないこと（ガイドの文と実際の動きの食い違い）は、公開前に、ガイドを上から順に実機でたどって確かめる（YUN-87 の手動試験と一緒に行う）。インストール・更新・アンインストールは 4.9・4.11、`yunagi show` と Wayland の手順は 4.8 で確かめるので、ここでは通読して食い違いを拾う。日本語の画面と英語の画面の両方で、画面の文言がガイドと同じであること。

**画面写真の撮り方**（公式サイトと販売ページ、ガイドの案内に載せる分。ガイドの本文には写真の目印を置かない。サイトのどこに載せるかは、公式サイトを作るときに決める。ガイドで使う場所は、下の各項目に書いた章のとおり）：

- 共通の条件：実機の macOS（Retina）で、アプリのウィンドウを 1280×800 論理ピクセルにして撮る（PNG、2 倍で 2560×1600。窓の影は付けず、窓の中だけ）。データは架空のサンプルにし（個人名・社名・実在の URL を入れない）、サイドバーを開いた状態で撮る。ライトとダークの両方、日本語の画面と英語の画面の両方を撮る（ガイドにはライトの画面を日本語版・英語版のそれぞれに載せ、ダークの画面はサイトで使う）。時刻は凪メーターの太陽が空の中ほどに見える昼間（始業 9:00・終業 19:00 の設定で 14:00 ごろ）に合わせる。
- 撮る画面：
  1. 整理モード（レイアウト A）。TODO 5 件（うち 1 件は完了、1 件は持ち越し回数 2 の印つき）、障害 2 件（うち 1 件は解消済みで解消メモつき）、振り返りに「良かったこと」「詰まったこと」「明日の一手」を 1 行ずつ。ガイド 3 章「1 日の使い方」の最初に使う。
  2. ノートモード。時刻付き見出し 2 つ（例：「10:00 定例」「14:30 レビュー」）と、TODO・障害へ送った行（行末の「→ TODO」「→ BLOCKER」）。右の Outline と Sent が見えること。3 章の「会議中」「会議の後」に使う。
  3. 持ち越し（CARRY OVER）。持ち越し回数 3 の TODO の行に「分割する」「やめる」が出ている状態。3 章の「朝」に使う。
  4. 検索パレット。「レビュー」と入力して結果が日付つきで並んだ状態。3 章の Mod+K の説明に使う。
  5. ふりかえり（Archive）。週のカード 5 枚と、選んだ日のプレビュー。3 章の「過去の日を見返す」に使う。
  6. 凪メーター（残りが 0 件）。「NAGI」と表示された状態を、整理モードの上部だけ切り出す（高さ 112px の帯）。3 章の凪メーターの説明に使う。
  7. 設定の Operation 区分。「ショートカット割当」の一覧が見えること。2 章と 4 章に使う。
  8. 設定の Agents 区分と、エージェントの変更履歴（サイドバーの Agents）。6 章に使う。
  9. 新しい版の通知（サイドバー下端の「New version」を開いた小さな表示）。1 章「更新」に使う。
- 撮るタイミング：画面の見た目が確定し、実機の確認（YUN-87）が済んでから、公開する版で撮る。撮り直しは、画面の見た目を変える PR のたびには行わず、公開前と、見た目が大きく変わった版のときだけ行う。

## 5. 性能基準

| 項目 | 基準 | 計測方法 |
| --- | --- | --- |
| 常駐状態からの呼び出し | 200ms 以内 | ショートカット押下から描画完了まで |
| コールド起動 | 1.5 秒以内 | プロセス起動から操作可能まで |
| 入力応答 | 16ms 以内 | キー入力から描画まで（p95） |
| 自動保存 | 入力停止から 0.5 秒以内 | 保存完了イベントまで |
| 検索 | 1 秒以内 | データモデル設計書 5章の見積もり量で生成した 5年分（1,800日）の合成データ（日本語を含む）で（p95） |

計測は一般的な業務用ノートPC相当の環境を基準機とし、機種を記録する。

開発中の測定（2026-11-03、YUN-76。Intel Core i7-11850H）：入力応答のうち、長いノート（約 23,000 字・840 行・時刻付き見出し 40）で1文字ごとに画面が行う処理（見出しの飾りと Outline・送信済みの印の更新と、入力中の状態の知らせのための最後に保存した本文との差分）を、jsdom の上で測った（描画の時間は含むが、実際の WebView とは違う）。1秒に10文字の速さで6か所を打ったとき、保存できている間は p95 約 1.5ms、保存に失敗し続けている間（まだ保存していない変更が本文全体に散らばる）は p95 約 1.2ms だった。同じ打ち方で保存に失敗し続けると、見直す前は差分を1文字ごとに2回、表を埋める方法で求めていたため p95 約 17ms で、差分を1回にまとめ、変えた行が少ないときは Myers の方法で求めるようにした（`src/lib/text_merge.ts`）。測り方は `src/note/NoteView.perf.test.ts`（`YUNAGI_PERF=1 pnpm vitest run src/note/NoteView.perf.test.ts`）。実際の WebView での測定は、リリース判定（6章）の前に行う。

開発中の測定（2026-11-03、YUN-75。Intel Core i7-11850H）：検索パレット（画面設計書 6章）で、結果の上限（50 件）まで 10KB ほどのノートの結果を出した状態で1文字ずつ打ったとき、1文字ごとの処理（入力欄の更新、日付とコマンドの照合、一覧の描き直し）は jsdom の上で p95 約 0.5ms だった。検索は打ち止めてから1回だけ送り、結果の切り出しは答えが届いたときだけ行う。答えが届いたときの切り出しと描画は中央値約 10ms・p95 約 25ms で、打ち止めた後に1回だけかかる。1文字ずつ打っても検索を1回だけ送ることと、後から送った検索の答えだけを使うことは、毎回のテスト（`src/lib/palette.test.ts`・`src/palette/Palette.test.ts`）で確かめる。測り方は `src/palette/Palette.perf.test.ts`（`YUNAGI_PERF=1 pnpm vitest run src/palette/Palette.perf.test.ts`）。

## 6. リリース判定

- 重大度「高」（定義は operations/support-runbook.md 3章）の未解決不具合がないこと。
- 性能基準をすべて満たすこと。
- 手動チェックリストを、配布する全 OS・アーキテクチャで完了していること（検証できなかった組み合わせは「試験提供」と明記して配布する）。
- 公開前は macOS・Windows の CI が自動では回らないので、公開するコミットで、開発用 CI と配布用 CI の試運転を手動で実行し、すべて成功していること（2章「macOS・Windows での開発用 CI」の「公開前の確認」。YUN-87）。
