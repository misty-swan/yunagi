# セキュリティ方針

> 本書はセキュリティ方針の全文である。GitHub がセキュリティポリシーとして認識するのは、リポジトリのルート（`.github/`、`docs/` でもよい）にある SECURITY.md だけなので、ルートの `SECURITY.md` に報告の窓口と対象の版を短く書き、全文は本書に置く（YUN-109）。窓口（3章）を変えるときは、ルートの `SECURITY.md` も同じに直す（`scripts/docs/public.test.ts` が報告先のメールが一致していることを確かめる）。

## 1. 基本姿勢

Yunagi は利用者の業務メモを扱うため、データを端末の外に出さないことを基本とする。外部との通信は、自動更新の確認（既定で有効。設定で無効にできる。送る情報は版・OS・アーキテクチャのみで、配布ホストには IP アドレスとアクセス日時が記録される）と、利用者が明示的に有効にした機能（外部ツール連携、クラウド同期）に限る。

## 2. サポート対象の版

セキュリティ修正は、最新のマイナー版（例：1.4.x）のパッチ版として提供する。それより古いマイナー版には提供せず、更新を案内する。

## 3. 脆弱性の報告

- 報告先：security@getyunagi.com（メールの受け口は Cloudflare の Email Routing。ビルド・配布手順書 2章）。公開リポジトリの Private vulnerability reporting も受け付ける。
- 公開の Issue には書き込まないでください。
- 受領の連絡は 3 営業日以内、初期評価の結果は 10 営業日以内に返すことを目標とする。
- 修正版の公開後、報告者の同意を得て謝辞を記載する。

## 4. 保護の仕組み

### 4.1 データの保存

- データは利用者のデータディレクトリにのみ保存する。ディレクトリとデータベースは利用者本人だけが読み書きできる権限で作成する。
- 外部ツールの認証情報は OS のキーチェーンに保存し、データベースや設定ファイルに平文で書かない。

### 4.2 ローカル API と AI エージェント

- ローカル API は、UNIX ドメインソケット（macOS・Linux）または名前付きパイプ（Windows）で提供し、ネットワークのポートを開かない。
- 接続時にトークンで認証する。トークン・ソケット・ロックファイルは、保存先の設定に関係なく端末ローカルの既定ディレクトリ（アーキテクチャ設計書 6章）に置き、クラウドドライブへ同期されないようにする。
- 権限と認証の細部（アーキテクチャ設計書 4.6）：既定ディレクトリを本人だけの権限（0700）にし、ソケットは bind の後に 0600 にする（ソケットの権限だけに頼らない）。Windows のパイプは作った利用者だけに許す権限を明示し、リモートの接続を断り、名前を起動のたびにランダムにして先取りを防ぐ。トークンは OS の乱数 32 バイトを 16 進にした値で、待ち受けを始めるたびに作り直し、0600 で書いて置き換え、定数時間で比べ、ログやエラーの文に出さない。トークンが証明するのは「同じ OS の利用者」で、エージェントの識別子は名乗るだけである（次の項と同じく、防御の境界ではない）。
- `yunagi show` は、ローカル API の `show_app` で窓を前面に出す頼みを送る。データにもスコープにも触れず、トークンの認証は通常の依頼と同じ（アーキテクチャ設計書 3.5・4.6、MCP・CLI 仕様書 3.3）。2 つ目のアプリの起動を動いているアプリに引き渡す仕組み（`tauri-plugin-single-instance`）は、ローカル API とは別の受け口を作る：Linux は D-Bus のセッションバスの名前（`<識別子>.SingleInstance`）、macOS は `/tmp/<識別子>_si.sock` の UNIX ドメインソケット、Windows は名前付きのミューテックス。受けたアプリは引数と作業フォルダを読まず、窓を前面に出すだけなので、同じ OS の利用者のほかのプロセスができるのは窓を出させることまで（データには触れない）。macOS のソケットは、利用者ごとではなく共有の `/tmp` にあるため、ほかの利用者のプロセスも窓を出させられる（窓を出させる以上のことはできない）。同時に 2 人がログインしている macOS では、あとから起動した利用者のアプリが、先の利用者のアプリに引き渡して終わってしまう（プラグインの制限。アーキテクチャ設計書 3.5 の既知の制限）。Windows のミューテックスはログオンのセッションごと、Linux の D-Bus のセッションバスは利用者ごとなので、この問題は無い。
- 依頼文の書き出し（`export_handoff`、アプリの Mod+Shift+A）は読み取りの操作で、`read` スコープが要る。依頼文にはその TODO の本文と、ノートの同じ見出しの区間の行、未解消の障害の本文が入る（CLI・MCP 仕様書 5章）。アプリの Mod+Shift+A は、依頼文を Rust 側だけでクリップボードに書く（`tauri-plugin-clipboard-manager`。アーキテクチャ設計書 4.3）。画面（WebView）には、クリップボードを読み書きする権限を渡さず（`capabilities/default.json` に `clipboard-manager:*` を足さない）、画面の不具合や読み込んだ内容が、クリップボードを読んだり任意の文を書いたりできないようにする。書き込んだ依頼文は、同じ OS の利用者のほかのアプリから読め、クリップボード履歴を持つ OS・アプリ（Windows のクリップボード履歴、クリップボードマネージャなど）に残りうる。これは利用者が依頼文をコピーする操作の性質で、Yunagi は書いた後のクリップボードを消さない（貼り付け先の操作を邪魔しないため）。利用者ガイドで、依頼文にノートの内容が入ることを伝える。
- エージェントの権限は既定で読み取りのみとし、書き込みはスコープごとに利用者が明示的に許可する。振り返りの既存文章の書き換えはどの権限でもできない。
- CLI からの書き込みは `cli` クライアントとして記録し、既定スコープは `read` のみとする。スコープの変更と `agent revert` は、CLI では対話端末（TTY）上の確認を経ないと確定しない（非対話の実行は `permission_denied`、終了コード 3）。アプリでは設定画面と変更履歴の画面から行う。この確認は誤って確定しないためのもので、防御の境界ではない：標準入力を擬似端末につなげば通せ、トークンを読める同じ利用者のプロセスは、ローカル API の管理の操作（`set_agent_scopes`・`revert_change`。MCP には出さない）をソケットに直接送れる。識別子のない MCP 接続は `unknown` として `read` のみを与え、`unknown` に書き込みのスコープは足せない。
- CLI は人とエージェントを確実には区別できず、防御の境界ではない。エージェントがシェルを実行できる環境では、`cli` に与えた権限はエージェントにも使われうる。
- エージェントによる変更はすべて記録し、1件ずつ取り消せる。
- エージェントに読ませたデータが、そのエージェントを通じて各AIサービスに送られることは、利用者と各AIサービスとの契約の範囲となる。この点を連携ガイドに明記する。

### 4.3 配布と更新

- 配布物には SHA-256 ハッシュを公開し、インストールスクリプトは照合に失敗すると中止する。全配布物のハッシュをまとめた `SHA256SUMS` には、配布用鍵（更新署名鍵とは別）で minisign 署名を付ける。
- 自動更新のパッケージは Yunagi 独自の鍵で署名し、アプリは署名を検証してから適用する。
- 更新署名鍵・配布用鍵の管理と漏えい時の手順は、ビルド・配布手順書 6章に従う。
- 本アプリは OS の有料コード署名を使用していない。この方針と、配布物の真正性を確認する方法（`SHA256SUMS.sig` の検証手順）を公式サイトに明記する。
- 公式サイトは Cloudflare Pages に置く（ビルド・配布手順書 2章）。導入スクリプトと `latest.json` を差し替えられると影響が大きいので、Cloudflare のアカウントは 2 要素認証で守り、公開用の API トークンは Pages の編集だけの権限にして、GitHub Actions の secrets にだけ置く。取り下げ時は、同章の方法で `latest.json` を前の版に戻す。

### 4.4 依存関係

- Rust・JavaScript の依存はロックファイルで固定し、CI で既知の脆弱性を検査する（ビルド・配布手順書 3章）。修正版が無い指摘を通す許可リストは、理由と見直す期限を添えて置き、期限を過ぎると開発用 CI も止まる（同 3.1）。許可外ライセンスの検出も同じ配布用 CI で行う。許可するか決まっていないライセンス（`pending`）がある間は、この検出は落ちる。BSL-1.0・CDLA-Permissive-2.0・Unicode-3.0 は、2026-11-06 に許可へ加えた（YUN-96。以下の `clipboard-win`・`webpki-root-certs` の記述のとおり）。
- CI で使う GitHub Actions の action は、タグではなくコミットの SHA で固定し、乗っ取りで書き換えられた action が CI（配布用 CI では署名鍵の近く）で動かないようにする。更新は Dependabot が PR で知らせ、人が確かめてマージする（ビルド・配布手順書 3章「action の固定」）。
- 依存の更新は、公開から一定期間（目安 14 日）を経た版を採用する。action の更新も同じ目安に従う。クリップボードのプラグイン（`tauri-plugin-clipboard-manager` 2.5.0）が連れてくる依存のうち、入れた時点（2026-11-05）で公開から 14 日たっていなかった `wl-clipboard-rs`（0.9.5）と `clipboard-win`（5.4.3）は、`Cargo.lock` で 14 日を経た一つ前の版（0.9.4・5.4.1）に下げた。`clipboard-win` と `error-code` のライセンスは BSL-1.0（Boost。Windows でだけ使う）で、許可するライセンスの一覧（サードパーティライセンス表記の方針 2章）に無かったため、一覧に加えるかをオーナーの判断に回し、寛容なライセンスなので加えると決めた（2026-11-06。YUN-96。決定と理由は third-party-licenses.md 2章 3 が正本）。
  自動更新のプラグイン（`tauri-plugin-updater` 2.14.0。公開 2026-10-14。YUN-83）を入れたときの扱いも同じ形にした（`deny.toml` は置かず、一時的な設定で `cargo deny` を確かめた）。①公開から 14 日たっていなかった `openssl-probe`（0.2.2 → 0.2.1）・`xattr`（1.7.0 → 1.6.1）は、`Cargo.lock` で一つ前の版に下げた。`webpki-root-certs` は、最新の 1.0.11 が 14 日未満で、14 日を経た中で最も新しい 1.0.10（2026-10-19 公開）にした（その前の 1.0.9 には RUSTSEC-2026-0383 があるので、1.0.9 までは下げない）。②`webpki-root-certs` のライセンス CDLA-Permissive-2.0（Mozilla の CA 証明書の一覧の使用許諾。寛容なライセンス）も許可リストに無かったので、YUN-96 の「一覧に加えるか」に 1 件足し、同じ日に加えると決めた。③`zip` 4.6.1 の脆弱性 4 件（プラグインが固定していて上げられない）は、`.cargo/audit.toml` の許可リストに理由と期限（2027-02-05）を添えて載せた（ビルド・配布手順書 3章）。更新の確認と入れ替えは Rust 側だけで行い、画面にプラグインの権限を渡さない（同 5.1）。

## 5. 範囲外

- 利用者の端末自体が侵害されている場合の保護。
- 利用者が保存先に指定したクラウドドライブ（iCloud Drive、Dropbox 等）での保護。なお、保存先をクラウド同期フォルダにする場合は同時に1台だけで開くことが前提で、2台で同時に開くとデータベースが壊れることがある。

## 6. セキュリティ告知

セキュリティ修正と鍵の失効は、公式サイトのお知らせと GitHub Security Advisory（公開リポジトリ）で告知する。
