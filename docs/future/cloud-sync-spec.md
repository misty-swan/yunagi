# クラウド同期仕様書（ドラフト）

> 有料機能 B の検討用ドラフトです。実装前に暗号方式と運用体制を専門家とともに確定させます。

## 1. 目的と前提

- 同じ利用者の複数の端末で、Yunagi のデータを同期する。
- 利用者が Dropbox や Syncthing、git で自力同期できる状況でも選ばれるよう、次の3点を必須とする：エンドツーエンド暗号化、同時編集時の競合解決、設定不要の導入。
- サーバーは暗号化されたデータを保管・中継するだけで、内容を復号できない。

## 2. 暗号化（案）

| 項目 | 方式（候補） |
| --- | --- |
| 鍵の階層 | データ鍵はランダムに生成する。これを、同期パスフレーズから Argon2id で導出した鍵と、復旧キーのそれぞれで包んで（ラップして）保管する。パスフレーズを変更しても、データを暗号化し直す必要はない |
| データの暗号化 | データ鍵で XChaCha20-Poly1305（変更単位ごと） |
| 端末の追加 | 既存端末に表示する QR コード、またはパスフレーズか復旧キーでデータ鍵を受け渡す |
| 鍵の紛失 | パスフレーズと復旧キー（初回設定時に表示し、利用者が保管）の両方を失うと復号できない。この点を明示する |

## 3. 同期モデル（案）

- 各端末は変更を「操作ログ」として記録し、暗号化してサーバーに送る。
- 項目（item）は列ごとの最終書き込み優先（Lamport 時刻と端末 ID で順序付け）で統合する。
- ノートと振り返りの本文は、テキスト向けの CRDT（候補：Automerge、Yjs の Rust 実装）で統合し、同時編集でも文字が失われないようにする。
- 論理日付の境界設定は端末間で共有する。

## 4. 競合の扱い

| 状況 | 動作 |
| --- | --- |
| 同じ TODO を2台で別々に編集 | 後の編集を採用し、採用しなかった内容を同期用の競合履歴に残す（保存先は下記の未決事項） |
| 一方で完了、他方で編集 | 編集内容を残したうえで完了状態を採用する |
| ノートの同じ箇所を同時に編集 | CRDT で両方の入力を保持する |
| 持ち越しを2台で実行 | 同じ元項目からの持ち越しは1件に統合する |

## 5. サーバー

- 保管するもの：利用者 ID、端末 ID、暗号化された操作ログ、ログの順序情報、課金状態。
- 保管しないもの：業務データの平文、暗号鍵、パスフレーズ。
- 保持期間：操作ログは定期的にスナップショットへ圧縮し、古いログを削除する。

## 6. 運用

- 可用性目標、障害時の告知方法、データの書き出し手段を定める（TBD）。
- サービスを終了する場合は、十分な告知期間を設け、ローカルのデータは引き続き使えるようにする。

## 7. 未決事項

- CRDT ライブラリの選定
- サーバーの構成と事業者
- 料金と無料試用期間
- 競合で採用しなかった内容の保存先（新しい表を設けるか、change_log の `actor` を同期操作にも広げるか。データモデル設計書で定める）
- タイムゾーンが異なる端末どうしでの論理日付の扱い（案：その日のボードを最初に作った端末のタイムゾーンで確定し、他の端末はそれに従う）
- ローカル版で保存先をクラウド同期フォルダにしている利用者が公式同期へ移るときの手順
