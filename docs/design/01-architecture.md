# アーキテクチャ設計書

## 1. 方針

Yunagi は、端末内で完結するローカルファーストのデスクトップアプリとして構成する。すべてのデータの読み書きは「コア」と呼ぶ単一の層に集約し、画面・CLI・MCP サーバーはいずれもコアを通じてデータに触れる。これにより、利用者とAIエージェントが同時に操作しても、整合性と変更履歴を一か所で保証できる。

## 2. 全体構成

```
Yunagi アプリ（Tauri）
├─ フロントエンド（WebView）
│   ├─ 整理モード / ノートモード / 持ち越し / 検索 / 設定 / 変更履歴
│   └─ エディタ（ノート・振り返り。Vimモード対応）
│        │ Tauri コマンド（IPC）
└─ コア（Rust。クレート yunagi-core）
    ├─ ドメイン層：日付ボード、TODO、障害、振り返り、ノート、持ち越し
    ├─ 権限・変更履歴：エージェント操作の許可判定と取り消し
    ├─ ストレージ：SQLite（WAL）＋ FTS5 全文検索
    ├─ ローカル API サーバー：UNIX ドメインソケット / 名前付きパイプ
    └─ OS 連携：グローバルショートカット、IME 切替、キーチェーン、更新
          ▲
          │ ローカル API（アプリ停止中はロックを取って DB を直接開く。4章）
          │
コンソール用バイナリ `yunagi`（同じ yunagi-core を使う）
├─ CLI：`yunagi <名詞> <動詞>`（シェル・git フックから）
└─ MCP サーバー：`yunagi mcp`（stdio。Claude Code / Codex から）
```

CLI と MCP サーバーは、GUI とは別のコンソール用バイナリ `yunagi`（Windows は `yunagi.exe`）のサブコマンドとして提供し、アプリに同梱する（配置先はビルド・配布手順書 2章）。GUI とコンソール用バイナリは別のクレートとしてビルドし、どちらも同じコアのクレート `yunagi-core` を使う（`yunagi` に WebView を結び付けないため。同じクレートにすると、`yunagi` も Tauri と WebView のライブラリに依存し、それらの入っていない環境では動かなくなる）。

## 3. 技術選定

| 領域 | 採用 | 理由 |
| --- | --- | --- |
| アプリ基盤 | Tauri 2 | 軽量、3 OS 対応、Rust コアと Web UI の分離 |
| コア言語 | Rust | Tauri と同一言語。CLI・MCP とアプリが同じコアのクレート（`yunagi-core`）を使い、ドメイン層を共有できる |
| フロントエンド | TypeScript（6 系）＋ Svelte 5 | 起動と入力の速さを優先して、軽量な UI フレームワークから選んだ。試作で SolidJS と比べて決めた（3.1）。TypeScript の版は 3.2 |
| エディタ | CodeMirror 6 ＋ Vim 拡張 | Vim のノーマル・挿入・ビジュアルモードと IME の扱いに実績がある |
| データベース | SQLite（WAL モード、`synchronous=NORMAL`）、FTS5 | 単一ファイルで堅牢。全文検索を内蔵。`synchronous=NORMAL` では電源断時に失うのは最後のチェックポイント以降の直近の書き込みに限られ、要件の「直前数秒以上は失わない」を満たす見込み（08 で確認） |
| 秘密情報 | OS キーチェーン（`keyring` クレート等） | 外部ツールの認証情報を平文で持たない |
| 自動更新 | Tauri Updater（独自鍵で署名） | OS の有料署名に依存しない |

### 3.1 フロントエンドの選定理由（2026-11-02 決定）

Svelte と SolidJS で同じ小さな画面を Tauri 2 上に作って比べた（YUN-2。結果は `experiments/yun-2-frontend/RESULTS.md`。試作のコードは比較用で、本番には流用しない）。

- 起動時間・メモリ・入力の反応には、両者で意味のある差がなかった。速さで決まらないため、作りやすさと保守のしやすさで選んだ。
- 整理モードの一覧（その場で編集する項目と、エージェントの変更による再読み込み。4章 6）を、Svelte は基本機能だけで正しく書けた。SolidJS では、差分で更新する仕組み（`reconcile`）と比較処理の自作が要った。書き忘れたときの壊れ方も、SolidJS のほうが重かった（再読み込みのたびに入力中の項目からフォーカスが外れる）。
- Svelte のほうが、画面のコードが短く、依存パッケージも少ない。SolidJS の利点である JS の小ささは、共通の CodeMirror を含めると約 3% の差で、アプリに同梱するため起動時間にも表れなかった。
- IME（日本語入力）は、Linux（fcitx5-mozc）で両版を実機確認し、問題はなかった。macOS・Windows ではテスト計画書の IME 試験で確かめる。

実装の注意：

- その場で編集する項目（contenteditable）は1つの部品にまとめる。本文は `bind:textContent` で結び付け、式で直接書かない（入力のたびに余分な書き換えが起き、カーソルが崩れる）。一覧はキー付きの `{#each}` で描き、項目を増やした・分けた直後のフォーカスは `await tick()` の後に移す。
- これらの動き（分割・削除・移動、再読み込みの後もフォーカスと選択範囲が残ること）は、試作と同じく自動テストで守る。

### 3.2 型チェックの道具と TypeScript の版（2026-11-02 決定）

フロントエンドの型チェック（型の食い違いを自動で見つける検査）は、`svelte-check` の 4 系で行う。TypeScript は 6 系を使い、7 系は使わない。実際に使う版は、pnpm の `pnpm-lock.yaml`（入れた依存の正確な版を記録するファイル）で固定する。型チェックは手元の検査コマンド（`pnpm check`）に含め、開発用 CI（push と PR のたびに走る自動検査。`.github/workflows/ci.yml`）でも走らせる。

- `svelte-check` 4.7.8 が依存の宣言で対応を示している TypeScript は、5 系と 6 系である。7 系だけを入れると、起動時に「6 系と 7 系の両方を入れ、`--tsgo` を付けよ」と表示して止まる。
- 6 系と 7 系を両方入れて `--tsgo` を付けた場合も、`.svelte` と `.ts` の型エラーをどちらも見つけられた。ただし、これは変換したファイルを一度ディスクに書き出す試験的な方式で、2 つの版を同時に管理することになる。7 系の利点である速さは、コードが大きくなるほど効いてくるが、試したのは 2 ファイルだけで比べられていない。
- 確かめた手順と結果は `experiments/yun-14-typescript/RESULTS.md` にある。
- `svelte-check` が 7 系に正式に対応したら、移行を検討する（svelte-check を上げるときに確かめる）。

## 4. 書き込み経路と同時実行

1. アプリ起動中は、コアがデータベースへの唯一の書き込み主体となる。CLI と MCP サーバーはローカル API 経由でコアに依頼する。
2. アプリ停止中は、CLI と MCP サーバーが操作ごとにロックファイル `yunagi.lock`（6章の既定ディレクトリ）の排他ロックを取得してからデータベースを開き、操作が終わったらロックを離す。ロックを持ち続けない。
3. MCP サーバーは常駐するプロセスのため、アプリの起動・停止をまたいで動き続ける。そこで操作ごとに、まずローカル API への接続を試み、接続できなければ 2 の直接モードで処理する。
4. アプリは起動時に `yunagi.lock` を取得する。取れないとき（CLI・MCP の操作中）は最大数秒待ち、それでも取れなければエラーを表示する。
5. いずれの経路でも、ドメイン層の同じ関数を通るため、検証・権限判定・変更履歴の記録は一様に適用される。
6. MVP では、コアは変更をイベントとしてフロントエンドに通知し、画面はデータを再読み込みして最新の状態を表示する（エージェントによる変更も含む）。変わった項目の強調などの演出は第2フェーズ（ロードマップ参照）とする。

ローカル API のソケットは利用者本人のみが読み書きできる権限で作成し、接続時にランダムなトークンで認証する。トークン・ソケット・ロックファイルは、保存先の設定に関係なく6章の既定ディレクトリに置く（保存先をクラウド同期フォルダにしても同期されないようにするため）。

### 4.1 利用者の入力中に届いたエージェントの変更（2026-11-02 決定）

再読み込み（4章 6）で、利用者が入力中の文字・カーソル・変換中の文字を壊さず、利用者の入力を失わないよう、対象ごとに次のように扱う。

**項目の入力中**：フロントエンドは、フォーカスのある項目の欄（本文または解消メモ）と「入力中かどうか」をコアに知らせる。項目の本文または解消メモは、その欄にフォーカスがあり、かつ最後の入力から 10 秒以内か IME の変換中であれば入力中とする。10 秒は、考えながら打つ間の小休止を含めつつ、エージェントを長く待たせないための長さ。フォーカスが外れたとき、またはアプリが前面から外れたときは、まだ保存していない入力（自動保存の待ち。最大 0.5 秒）をすぐに書き込み、その書き込みが終わった時点で入力中を終える。書き込みが終わるまではフォーカスが無くても入力中とみなす。保存前にエージェントの変更を受け付けると、続く保存でエージェントの変更が利用者の入力で上書きされるため。

**保存に失敗している間**：書き込みに失敗して自動で再試行している間（画面設計書 3章「上部のバー」の「保存できていません」）は、入力中とはみなさない。代わりに、コアは画面からの保存の書き込みに失敗してから、次に書き込みが成功するまでの間、エージェントの書き込みをすべて（対象に関係なく）受け付けず `storage_unavailable` を返す（ただし、引数の誤りや取りやめた TODO への書き込みなど、保存先に関係なく必ず失敗する `invalid_argument` は先に返す。MCP・CLI 仕様書 3章の判定の順）。読み取りは受け付ける。保存先への書き込みが失敗している以上、ほかの対象への書き込みも確かではなく、まだ保存できていない入力がある対象の内容も確定しないため。保存が成功すれば通常の扱いに戻る。これにより、保存が失敗し続けても `user_editing` を返し続けることはなく、エージェントは保存先の問題であることを知れる。

**ノート・振り返りの守る行**：エディタにフォーカスがある間、またはまだ保存していない入力がある間、フロントエンドは、エージェントに変えさせない行（守る行）をコアに知らせ、変わるたびに知らせ直す。守る行は次の2つを合わせたもの。

- カーソル行：カーソルのある行（選択範囲が複数行にまたがるときはその全部の行）。項目と同じく、エディタにフォーカスがあり、かつ最後の入力から 10 秒以内か IME の変換中の間だけ含める。フォーカスが外れたとき、またはアプリが前面から外れたときは、すぐに含めるのをやめる（まだ保存していない入力は、次の「未保存の変更がある行」として保存まで守られる）。入力をやめてエディタを開いたままにしても、エージェントを待たせ続けないため。
- 未保存の変更がある行：最後に保存した本文の行のうち、エディタで書き換えたか削除して、まだ保存していない行。差分の上では「削除＋追加」に見える書き換えも、元の行の書き換えとして含める。カーソルを別の行へ移しても、保存されるまでは守る行に残る。

行番号は、コアにある保存済みの本文で数える（エージェントが `get_note` で読み、`edit_note` で指定するのと同じ数え方）。エディタにはまだ保存していない行が含まれうるため、フロントエンドは、最後に保存した本文とエディタの内容の差分から、行番号を保存済みの本文の行番号に置き換えて知らせる。保存前に足した新しい行は、エージェントが指定できないので知らせない（保存済みの行を書き換えた結果の行なら、元の行が「未保存の変更がある行」として守られる）。知らせた行番号には、数えた本文（最後に保存した本文）の版の番号（`rev`）を添える。コアは版ごとの本文を持たないため、行番号をずらして使うことはしない。守る行が1行以上あると知らせている間に、添えられた版とコアの版が違う（その間にエージェントの変更か利用者の保存が書き込まれ、行番号が古くなった）ときは、そのノート・振り返りへの `edit_note` をすべて `conflict`（`reason: user_editing`）にする。フロントエンドは、版が進むたび（自分の保存が成功したとき、エージェントの変更を取り込んだとき）に、新しい版で守る行を知らせ直す。知らせ直しが届けば通常の判定に戻る。版が一致していれば、守る行はコアの本文の行番号そのものなので、守る行が消えている場合は起きない。

| 対象 | 入力中に届いたエージェントの変更 |
| --- | --- |
| 項目の本文（`edit_todo`） | 持ち越し済みの項目（前の日に残る元の項目）は、入力中かどうかにかかわらず `conflict`（`reason: carried_over`）で、取りやめた TODO（`dropped`）は `invalid_argument` で拒む（MCP・CLI 仕様書 3章。次の行も同じ）。その項目の本文を入力中なら受け付けず、`conflict`（`reason: user_editing`。MCP・CLI 仕様書 4.3）を返す。エージェントは後でやり直す。解消メモの入力中は、本文とは別の欄なので受け付ける。入力中でなければ受け付け、フォーカスがあってもその場で画面に反映する（カーソルは同じ文字位置。本文より後ろなら末尾） |
| 項目の状態（`complete_todo` / `reopen_todo` / `resolve_blocker`） | 持ち越し済みの項目と取りやめた TODO でなければ、本文・解消メモとは別の欄なので、本文または解消メモの入力中でも受け付けてすぐ反映する。ただし `--note` 付きの `resolve_blocker` は解消メモの欄にも書くため、その障害の解消メモを入力中なら受け付けず、`conflict`（`reason: user_editing`）を返す（本文に対する `edit_todo` と同じ）。入力中でなければ、解消メモの欄にフォーカスがあっても書き込み、その場で画面に反映する。解消メモの欄は障害が解消済みの間だけ開く（未解消に戻すと、まだ保存していない入力を書き込んで閉じ、入力中を終える。操作仕様書 2章）ため、このとき障害はすでに解消済みで、やり直した `resolve_blocker` は解消済みの障害への扱い（MCP・CLI 仕様書 3章）に従う |
| ノート・振り返り（`append_note` / `append_reflection` / `edit_note`） | 受け付ける。エディタには本文の置き換えではなく差分（変更箇所だけ）として取り込み（下記「取り込み方」）、カーソルと選択範囲を保つ。IME の変換中は、変換が終わるまで取り込みを待つ。取り込んだ変更は Mod+Z の取り消しの対象にしない（04 2章。取り消しは変更履歴 S-06 から）。`edit_note` で、守る行（上記）を書き換え・削除・移動しようとした場合と、守る行の版が古い場合（上記）だけ `conflict`（`reason: user_editing`）にする。`--expect` の不一致（`reason: changed`）にも当たるときは `changed` を返す（MCP・CLI 仕様書 3章） |

**ノート・振り返りへの取り込み方**：エージェントの変更をエディタに取り込むとき（保存の行き違いで最新の内容を取り込むときも同じ）、フロントエンドは、最後に保存した本文をもとにして、「エージェント側の変更（もとの本文→コアの最新）」と「利用者のまだ保存していない変更（もとの本文→エディタ）」を合わせる。

- 重ならない変更は、両方を残す。
- 同じ位置への行の追加は、両方を残す（利用者の行を先にする）。
- 利用者がまだ保存していない新しい行は、すぐ上の保存済みの行の後ろに付いているものとして扱う。その保存済みの行がエージェントの変更（書き換え・削除・移動）の範囲に入って元の位置から無くなった場合は、利用者の行を、その範囲があった位置に残す。範囲を書き換えた場合は新しい行の後ろ、削除・移動した場合は範囲のすぐ上の行（範囲の外で残っている行）の後ろに置く。移動では利用者の行を範囲と一緒に動かさない（移動は「元の位置から削除して別の位置に追加」として扱うため）。
- 同じ行を両方が変えた場合（守る行を知らせる前にエージェントの変更が届いた、行き違いのときに限られる）は、両方の結果を残す。その行の位置に、利用者の結果の行、続けてエージェントの結果の行を置く（同じ位置への追加と同じく利用者の行が先。どちらかが削除なら、その側の行は無い）。どちらの行を残すかは利用者が画面で決める。

エージェントの変更は、コアが受け付けた時点でデータベースに書き込まれて確定し、change_log の `after` もその内容になる。エージェントに返す成功はこの確定を指す。取り込みの後に利用者がその内容を消したり書き換えたりして保存した場合は、エージェントの変更の後の人の変更として扱う（変更履歴 S-06 には取り込んだエージェントの変更がそのまま残り、`agent revert` は人の変更と衝突したものとして `reason: changed` になる。MCP・CLI 仕様書 7章）。

取り込んだ後、フロントエンドは「最後に保存した本文」をコアの最新の本文に、もとにする版の番号をコアの最新の版に進める。以後の「利用者のまだ保存していない変更」は、この新しいもととエディタの差分になる。もとを進めないと、次の保存が古い版のもととして弾かれ、古いもとで取り込みをやり直して、取り込み済みのエージェントの行が二重になるため。続けて、新しい版で守る行を知らせ直し（上記）、まだ保存していない入力があれば保存する。

これにより、利用者の入力はすべてエディタに残り、エージェントの変更も受け付けた時点でノートに書き込まれ、取り込んだ後もエディタに残る（利用者が自分で消すまで）。

**ノート・振り返りの保存の行き違いを防ぐ**：note・reflection は版の番号（`rev`。データモデル設計書）を持つ。フロントエンドの保存には、もとにした版の番号を添える。同じノート・振り返りへの保存は一度に1つだけ送り、成功の応答で返る新しい版の番号を次の保存のもとにする（利用者自身の保存どうしが行き違わないようにするため）。コアの版のほうが新しい（その間にエージェントが変更した）場合、コアは保存を受け付けずに最新の内容を返す。フロントエンドは、上の取り込み方で最新の内容をエディタに取り込み、利用者のまだ保存していない入力を残したまま保存し直す。

**項目の保存**：item は版の番号を持たない。フロントエンドの保存では、利用者が変えた欄（本文・解消メモ・状態・並び順など）だけを送り、コアは送られた欄だけを書く。ほかの欄は書かないため、エージェントが同じ項目の別の欄を変えていても、その変更は残る（例：本文の入力中にエージェントが `complete_todo` で完了にしても、続く本文の保存で未完了に戻らない）。同じ欄をエージェントも変えていた場合（入力中の判定と行き違ったときに限られる）は、利用者の保存で上書きする（状態の欄を両方が同じ値にした場合は、下記「利用者とエージェントが項目を同じ状態にした行き違い」に従う）。項目は利用者の入力を優先するので、ノートのように保存を拒否して最新を返し、保存し直す往復をしても結果は変わらないため。エージェントの変更は受け付けた時点で確定しており（ノートと同じ）、利用者の保存はその後の人の変更として扱う。エージェントの変更は change_log に記録済みで（未確認の印も付いたまま）、変更履歴 S-06 で確かめられ、`agent revert` はその欄について人の変更と衝突したものとして `reason: changed` になる。

同じ項目への保存は、ノートと同じく一度に1つだけ送り、前の保存の応答を待ってから次を送る。待っている間に変えた欄は、次の保存にまとめる（同じ欄を何度も変えたら最後の値だけを送る）。版の番号が無いので、送った順に書き込まれないと、利用者自身の古い保存（例：本文 `foo`）が新しい保存（`foobar`）を追い越して上書きしてしまうため。

**利用者とエージェントが項目を同じ状態にした行き違い（2026-11-03 決定）**：利用者が画面で項目の状態を変えて（完了にする・未完了に戻す・解消する）から、その保存が書き込まれるまでの間（自動保存の待ちや、前の保存の応答待ち）に、エージェントの同じ状態にする操作（`complete_todo`・`reopen_todo`・`resolve_blocker`）が届くことがある。届いた時点のコアは利用者の変更をまだ知らないので、エージェントの操作は状態を変えたものとして受け付け、change_log に記録する。そのままでは、続く利用者の保存は値を変えず、変更がエージェントのものとして残る（未確認の印が付き、`agent revert` で利用者が自分で変えた状態が戻されうる）。そこで、この場合は利用者の変更として扱う。利用者の保存が先に届いていれば、エージェントの操作は「すでに目的の状態」として何も変えず、記録もされない（MCP・CLI 仕様書 3章）ので、その順に届いた場合と同じ結果にそろえる。エージェントの操作を拒否しないのは、届いた時点では利用者の変更を知りえないため。画面が状態の変更を操作のすぐ後に送っても、それがコアに届くまでの間は同じことが起きうるので、届く前に防ぐのではなく、保存を書き込むときに判定する。

- 画面からの保存では、状態の欄に、変える前の値（利用者がその保存で最初に状態を変えたときに画面に出ていた状態）と、利用者が状態を変えた操作の時刻を添える。前の保存の応答を待つ間に何度も状態を変えて1つの保存にまとめた場合（上記）は、最初の操作の時刻と最後の操作の時刻の両方を添える（1回なら同じ時刻）。時刻はコアと同じ端末の時計でミリ秒まで測る。画面で状態を変えたときの完了時刻（`completed_at`。障害では解消時刻）は、操作仕様書 2章のとおり画面が決めて（ふつうは利用者の最後の操作の時刻、未完了・未解消に戻したときは空、Mod+Z で戻す操作を取り消したときは元の時刻）保存に添え、行き違いの有無に関係なく、その値を書く。
- コアは、利用者の保存を書き込むときに、その項目の状態を変えたエージェントの記録のうち、最初の操作の時刻より後に作られた（change_log の `created_at` で比べる。同じ時刻なら利用者の操作が先とみなす）最初の記録が、次の両方に当たれば行き違いと判定する。
  1. 取り消されていない。
  2. 状態の `before` が変える前の値で、`after` が保存の値（利用者が最後に選んだ状態）。
- 行き違いのとき、コアは、その記録から状態と完了時刻の欄を外す。記録にほかの欄が残れば（`--note` 付きの `resolve_blocker` の解消メモなど）、その欄はエージェントの変更のまま残す（未確認の印も残る）。何も残らなければ、記録を消す（実際に何かを変えた操作だけを記録する決まり。データモデル設計書 change_log）。利用者の保存とこの書き換えは、1つのトランザクションで行い、終わったら変更をフロントエンドに知らせる（4章 6）。画面は再読み込みし、上部のバーとサイドバーの件数、項目の行頭の菱形、変更履歴 S-06 から、その記録の分を消す。消した記録を `agent revert` で指定すると `not_found` になる。
- 外すのは最初の記録だけで、それより後のエージェントの記録（行き違いの間に未完了に戻してから、もう一度完了にした場合など）は残す。利用者の保存が先に届いていれば、何も変えずに終わるのは最初の操作だけで、その後の操作は状態を実際に変えるため。その順に届いた場合と同じ記録にするため、次のようにする。
  - 後の記録が無いとき：利用者の保存のとおり、状態と完了時刻を書く。
  - 後の記録があるとき：すぐ後の記録の状態と完了時刻の `before` を、利用者の保存の値（状態と、保存に添えた完了時刻）に書き直す（外した記録の値が残らないように）。現在の状態が保存の値と同じなら、状態と完了時刻は書かず、最後の記録の `after` のままにする（利用者の保存は、その順なら後の記録より前に書かれているため）。現在の状態が保存の値と違えば、上の「項目の保存」のとおり利用者の保存で上書きする。
  - 残った記録は、ふつうのエージェントの記録として扱う（`agent revert` の判定も MCP・CLI 仕様書 7章のとおり）。外した記録は、Mod+Z で状態を戻すかの判定（操作仕様書 2章の「その後にエージェントが状態を変えていた場合は戻さない」）でも、エージェントの変更に数えない。
- エージェントにはすでに成功（`updated: true`）を返しているが、項目はエージェントが目指した状態になっているので、目的は果たされている。同じ操作をやり直せば `updated: false` になる。
- エージェントの操作が届いた後に保存の書き込みが失敗して再試行した場合は、書き込みが成功した時点で判定する（再試行の間に届くエージェントの書き込みは、上の「保存に失敗している間」のとおり `storage_unavailable` になる）。
- 当たらない場合はこれまでどおり扱う。最初の操作の時刻より前に作られた記録（利用者の操作の直前にエージェントが変え、画面の再読み込みが間に合わなかった場合）は、実際にエージェントが先に変えているので、エージェントの変更として残す。まとめた保存では、途中の状態は問わず、変える前の値と最後に選んだ状態で判定する（例：完了・未完了に戻す・完了と続けた間にエージェントが完了にした場合は、行き違いとして記録を外す。利用者の保存が先に届いていれば、エージェントの操作は完了の上で何も変えないため）。利用者が最後に選んだ状態がエージェントの目指した状態と違う場合（例：完了にしてから未完了に戻した）は、利用者の保存で上書きし、エージェントの記録は残す（`agent revert` は `reason: changed` になる）。

change_log の項目の記録には、その操作が変えた欄だけを `before` / `after` に入れる（データモデル設計書 change_log）。`agent revert` は、その欄の現在の値と `after` を比べて人が後から変えたかを判定し、取り消しではその欄だけを `before` に戻す。ほかの欄（利用者がその後に変えた本文など）には触れない。

アプリの停止中は画面での入力がないため、この扱いは起動中にだけ働く。

### 4.2 `yunagi.lock` のロックの取り方（2026-11-03 決定）

- OS のファイルロック（Rust 標準の `File::try_lock`。Linux・macOS は `flock`、Windows は `LockFileEx`）で排他ロックを取る。外部のクレートは使わない（標準で3つの OS に対応するため）。プロセスが異常終了しても OS がロックを離すので、取り残されたロックを手で消す必要はない。
- コアのロックの関数は既定ディレクトリ（6章）を受け取り、ファイル名 `yunagi.lock` はコアが付ける。保存先（`data_dir`）を渡すと、保存先を変えた利用者のアプリと CLI・MCP が別のファイルをロックしてしまうため。
- ロックファイルは消さない（消すと、消す前のファイルを掴んだプロセスと作り直したファイルを掴んだプロセスが、両方ともロックを取れてしまうため）。
- 取れないときは 50 ミリ秒ごとに取り直しを試み、最大 5 秒待つ（4章 4 の「数秒」）。直接モードの CLI・MCP の操作も同じ時間だけ待つ。それでも取れなければエラーにする。
- データベースは、取ったロックを渡さないと開けない（コアの `Database::open`）。開いている間はデータベースの接続がロックを持ち、閉じるとロックも離れる。これで、ロックを持たずにマイグレーションが走らないことを型で守る（データモデル設計書 1.1）。型で守れるのは「ロックを持っている」ことまでで、そのロックが既定ディレクトリのものであることは、呼び出し側が既定ディレクトリを求める関数（YUN-20）の結果を渡すことで守る。

## 5. 日付の扱い

「その日」はカレンダー日付ではなく、設定した切り替わり時刻（既定 4:00）を基準とした論理日付で扱う。論理日付の算出はコアのみが行い、CLI・MCP も同じ規則に従う。タイムゾーンは端末の設定に従い、日付ごとに記録時のタイムゾーンを保存する。切り替わり時刻を変更した場合は、変更後に作成するデータにだけ適用し、既存の日付は付け直さない。

論理日付 `D` は、カレンダー日 `D` の切り替わり時刻の瞬間に始まる。壁時計の時刻どうしではなく瞬間で比べ、夏時間の切り替えでも日付が逆戻りしないようにする。切り替わり時刻が夏時間の開始で飛ばされる日（例：2:00〜2:59 が無い日に 2:30）は、飛ばされた後の最初の時刻（3:00）に始まる。切り替わり時刻が夏時間の終了で2回ある日は、1回目に始まる。

## 6. データの保存場所

| OS | 既定のデータディレクトリ |
| --- | --- |
| macOS | `~/Library/Application Support/Yunagi/` |
| Windows | `%LOCALAPPDATA%\Yunagi\` |
| Linux | `$XDG_DATA_HOME/yunagi/`（未設定時 `~/.local/share/yunagi/`） |

既定ディレクトリは、アプリ本体の配置先とは別にする（アプリ本体の配置先はビルド・配布手順書 2章）。

設定ファイル `config.json`（保存先 `data_dir` を持つ）、ローカル API の認証トークン、ロックファイル `yunagi.lock`、ソケットは、保存先の設定に関係なく常に上記の既定ディレクトリに置く。保存先（`data_dir`）に置くのはデータベースと `backups/` である。

保存先は設定で変更できる。変更時はデータベースを安全に移動し、移動先を `config.json` に記録する。自動バックアップは保存先の `backups/` に直近7日分を作成する。

- `config.json` が無いとき、または `data_dir` の項目が無いときは、既定ディレクトリを保存先とする。壊れている（JSON として読めない、`data_dir` が絶対パスでない）ときは、既定の保存先で開かずにエラーにする（データが消えたように見え、別の場所に新しいデータベースを作ってしまうため）。このアプリが知らない項目は、書き戻すときに消さない。
- 保存先の変更（2026-11-03 決定）は、データベースと `backups/` を新しい保存先に写してから `config.json` を書き換え、最後に元の保存先のものを消す。データベースは SQLite のオンラインバックアップで写し（WAL にだけある書き込みも含む）、整合性を確かめてから置く。`config.json` を書き換える前に失敗したら、写したものを消して元のまま残す。元のものを消せなかったときは失敗にせず、残ったものを利用者に知らせる。
- 新しい保存先に、すでにデータベース（`yunagi.db` とその `-wal`・`-shm`）か、空でない `backups/` があるときは、上書きせずに断る。今の保存先の `backups/` の中も断る（`backups/` を自分の中へ写し続けてしまうため）。`..` を含むパスも断る（まだ無いフォルダを通ると実体を求められず、これらの確認をすり抜けるため）。
- 変更は `yunagi.lock`（4章）を取り、データベースを閉じてから行う。

保存先を iCloud Drive・Dropbox などのクラウド同期フォルダにする場合は、同時に1台だけで開く場合に限って使える（SQLite のデータベースと WAL のファイルが別々に同期されると壊れうるため）。同期フォルダと判定できる場合は、設定時に警告を表示する。複数端末で使う場合は、Markdown 書き出しまたはバックアップの同期を推奨する。

### 6.1 アプリの識別子（2026-11-03 決定）

アプリの識別子（bundle identifier。OS がアプリを見分けるための名前）は `io.github.misty-swan.yunagi` とする。`src-tauri/tauri.conf.json` の `identifier` に書く。

- 識別子は macOS のアプリの見分けや、WebView のデータの置き場所などに使われる。公開後に変えると、既存の利用者の環境で別のアプリとして扱われるため、変えない。
- 公式ドメインは未取得で、取れるかも決まっていない。このため、すでに持っている GitHub のアカウント名をもとにした名前にする。ドメインを取得した後も、識別子は変えない。
- GitHub のアカウント名を変えたり手放したりしても、識別子は変えない。名前空間を他人に取られないよう、アカウント名は変えない運用にする。
- macOS の識別子に使える文字は英数字・ハイフン・ピリオドだけで、下線（`_`）は使えない。このため、アカウント名のハイフンはそのまま使う。Linux の慣習（D-Bus の名前、Flathub）はハイフンを勧めないが、使えないわけではない。Flathub での配布は予定していない（配布物はビルド・配布手順書 2章のとおり）。
- 上のデータディレクトリは識別子ではなく、アプリ名 `Yunagi`（Linux は `yunagi`）で決める。Tauri の保存場所を返す関数（`app_data_dir` など）は識別子でフォルダ名を作るため、データディレクトリを求めるのには使わない。コアの同じ関数を、アプリと CLI の両方が使う。
- Linux では、識別子が画面の窓の名前（Wayland の app_id）になる。install.sh が作るデスクトップエントリのファイル名は、識別子にそろえる（ビルド・配布手順書 4.1）。
- 識別子は、WebView が自分のデータを置くフォルダの名前にも使われる（Windows の `%LOCALAPPDATA%` の下、macOS の `~/Library/WebKit/` の下など）。このフォルダは上のデータディレクトリとは別の場所にできる。
