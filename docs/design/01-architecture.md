# アーキテクチャ設計書

## 1. 方針

Yunagi は、端末内で完結するローカルファーストのデスクトップアプリとして構成する。すべてのデータの読み書きは「コア」と呼ぶ単一の層に集約し、画面・CLI・MCP サーバーはいずれもコアを通じてデータに触れる。これにより、利用者とAIエージェントが同時に操作しても、整合性と変更履歴を一か所で保証できる。

## 2. 全体構成

```
Yunagi アプリ（Tauri）
├─ フロントエンド（WebView）
│   ├─ 整理モード / ノートモード / 持ち越し / 検索 / 設定 / 変更履歴
│   └─ エディタ（ノート・振り返り。Vimモード対応）
│        │ Tauri コマンド（IPC）
├─ ローカル API の待ち受け（UNIX ドメインソケット / 名前付きパイプ。4.6）
│        │ コアの入口（`AppCore::api_write` など）
└─ コア（Rust。クレート yunagi-core）
    ├─ ドメイン層：日付ボード、TODO、障害、振り返り、ノート、持ち越し
    ├─ 権限・変更履歴：エージェント操作の許可判定と取り消し
    ├─ ストレージ：SQLite（WAL）＋ FTS5 全文検索
    └─ OS 連携：グローバルショートカット、IME 切替、キーチェーン、更新
          ▲
          │ ローカル API（アプリ停止中はロックを取って DB を直接開く。4章）
          │
コンソール用バイナリ `yunagi`（同じ yunagi-core を使う）
├─ CLI：`yunagi <名詞> <動詞>`（シェル・git フックから）
└─ MCP サーバー：`yunagi mcp`（stdio。Claude Code / Codex から）
```

CLI と MCP サーバーは、GUI とは別のコンソール用バイナリ `yunagi`（Windows は `yunagi.exe`）のサブコマンドとして提供し、アプリに同梱する（配置先はビルド・配布手順書 2章）。GUI とコンソール用バイナリは別のクレートとしてビルドし、どちらも同じコアのクレート `yunagi-core` を使う（`yunagi` に WebView を結び付けないため。同じクレートにすると、`yunagi` も Tauri と WebView のライブラリに依存し、それらの入っていない環境では動かなくなる）。

ローカル API は、アプリ（待ち受け。`src-tauri/src/api/`）と `yunagi`（接続）の両方が同じ取り決めを使うので、通信路（UNIX ドメインソケット・名前付きパイプ）・トークン・プロトコルの型・クライアントの 1 回分の接続は、共通のクレート `yunagi-api`（`crates/api/`）に置く。コアは接続の方式を知らないままにする（4.4）ので、コアには置かない。待ち受けのループと、依頼をコアの入口へ渡す部分は、`AppCore` を使うのでアプリ側に置く（4.6）。

## 3. 技術選定

| 領域 | 採用 | 理由 |
| --- | --- | --- |
| アプリ基盤 | Tauri 2 | 軽量、3 OS 対応、Rust コアと Web UI の分離 |
| コア言語 | Rust | Tauri と同一言語。CLI・MCP とアプリが同じコアのクレート（`yunagi-core`）を使い、ドメイン層を共有できる |
| フロントエンド | TypeScript（6 系）＋ Svelte 5 | 起動と入力の速さを優先して、軽量な UI フレームワークから選んだ。試作で SolidJS と比べて決めた（3.1）。TypeScript の版は 3.2 |
| エディタ | CodeMirror 6 ＋ Vim 拡張（`@replit/codemirror-vim`。3.3） | Vim のノーマル・挿入・ビジュアルモードと IME の扱いに実績がある |
| データベース | SQLite（WAL モード、`synchronous=NORMAL`）、FTS5 | 単一ファイルで堅牢。全文検索を内蔵。`synchronous=NORMAL` では電源断時に失うのは最後のチェックポイント以降の直近の書き込みに限られ、要件の「直前数秒以上は失わない」を満たす見込み（08 で確認） |
| 秘密情報 | OS キーチェーン（`keyring` クレート等） | 外部ツールの認証情報を平文で持たない |
| 自動更新 | Tauri Updater（独自鍵で署名） | OS の有料署名に依存しない |

### 3.1 フロントエンドの選定理由（2026-11-02 決定）

Svelte と SolidJS で同じ小さな画面を Tauri 2 上に作って比べた（YUN-2。結果は `experiments/yun-2-frontend/RESULTS.md`。試作のコードは比較用で、本番には流用しない）。

- 起動時間・メモリ・入力の反応には、両者で意味のある差がなかった。速さで決まらないため、作りやすさと保守のしやすさで選んだ。
- 整理モードの一覧（その場で編集する項目と、エージェントの変更による再読み込み。4章 6）を、Svelte は基本機能だけで正しく書けた。SolidJS では、差分で更新する仕組み（`reconcile`）と比較処理の自作が要った。書き忘れたときの壊れ方も、SolidJS のほうが重かった（再読み込みのたびに入力中の項目からフォーカスが外れる）。
- Svelte のほうが、画面のコードが短く、依存パッケージも少ない。SolidJS の利点である JS の小ささは、共通の CodeMirror を含めると約 3% の差で、アプリに同梱するため起動時間にも表れなかった。
- IME（日本語入力）は、Linux（fcitx5-mozc）で両版を実機確認し、問題はなかった。macOS・Windows ではテスト計画書の IME 試験で確かめる。

実装の注意：

- その場で編集する項目（contenteditable）は1つの部品にまとめる。本文は `bind:textContent` で結び付け、式で直接書かない（入力のたびに余分な書き換えが起き、カーソルが崩れる）。一覧はキー付きの `{#each}` で描き、項目を増やした・分けた直後のフォーカスは `await tick()` の後に移す。
- これらの動き（分割・削除・移動、再読み込みの後もフォーカスと選択範囲が残ること）は、試作と同じく自動テストで守る。

### 3.2 型チェックの道具と TypeScript の版（2026-11-02 決定、2026-11-03 再確認）

フロントエンドの型チェック（型の食い違いを自動で見つける検査）は、`svelte-check` の 4 系で行う。TypeScript は 6 系を使い、7 系は使わない。実際に使う版は、pnpm の `pnpm-lock.yaml`（入れた依存の正確な版を記録するファイル）で固定する。型チェックは手元の検査コマンド（`pnpm check`）に含め、開発用 CI（push と PR のたびに走る自動検査。`.github/workflows/ci.yml`）でも走らせる。

- `svelte-check` 4.7.8 が依存の宣言で対応を示している TypeScript は、5 系と 6 系である。7 系だけを入れると、起動時に「6 系と 7 系の両方を入れ、`--tsgo` を付けよ」と表示して止まる（起動時の表示は `--tsgo` だけを挙げるが、説明書は次に書く `--tsgo-experimental-api` も挙げている）。
- 6 系と 7 系を両方入れて `--tsgo` を付けた場合も、`.svelte` と `.ts` の型エラーをどちらも見つけられた。ただし、これは変換したファイルを一度ディスクに書き出す試験的な方式で、2 つの版を同時に管理することになる。7 系の利点である速さは、コードが大きくなるほど効いてくるが、試したのは 2 ファイルだけで比べられていない。
- 確かめた手順と結果は `experiments/yun-14-typescript/RESULTS.md` にある。
- 2026-11-03 に、`svelte-check` を最新の 4.7.8 に上げたときにも確かめ、7 系へは移行しないと決めた（YUN-31）。4.7.8 の依存の宣言は 5 系と 6 系のままで、説明書（README）も 7 系には 6 系と 7 系の両方と `--tsgo` か `--tsgo-experimental-api` の指定が要るとしている。`--tsgo-experimental-api`（TypeScript 7 の試験的な API を使う方式）でも 2 件の型エラーをどちらも見つけられたが、`svelte-check` 自身が「試験的な機能で、予告なく壊れうる」と示している。どちらの指定も試験的な扱いで、正式な対応ではない。7 系の入れ方（パッケージの名前）は説明書の中でも食い違っている（中身は `RESULTS.md` 3章）ため、試すときは `RESULTS.md` のコマンドに従う。
- `svelte-check` が 7 系に正式に対応したら、移行を検討する（svelte-check を上げるときに確かめる）。正式な対応とは、依存の宣言に 7 系が入り、7 系を使うのに要る指定や入れ方が説明書で試験的な扱いでなくなることをいう（6 系を一緒に入れる必要が残ってもよい）。そのうえで、`RESULTS.md` の手順の版をその時点の最新に差し替えて、2 件の型エラーを見つけられることを確かめる。

### 3.3 エディタの Vim 拡張（2026-11-04 決定）

ノートと振り返りのエディタ（CodeMirror 6）の Vim のキーは、`@replit/codemirror-vim`（MIT。CodeMirror 6 用の Vim 拡張で、npm で `@codemirror/` の名前のものは無い）で作る。完全な互換は目指さない（操作仕様書 4.1）。

- 版は `package.json` に正確な版で書いて固定する（`6.4.0`。ほかの依存と同じ）。この拡張が要求する `@codemirror/language`・`@codemirror/search` も、同じく固定して直接の依存に加える（拡張は `@codemirror/state` などを1つだけ使う必要があるため、`pnpm why @codemirror/state` で版が1つであることを依存を足すたびに確かめる）。
- 使い方は `src/lib/editor_vim.ts` にまとめる。有効・無効は設定の Vim モード（`prefs.vimMode`）に従い、開いているエディタにすぐ反映する（`TextDocEditor.setVim`。日を移ってエディタの状態を作り直しても従う）。Vim のキーは、部品のキー（ノートの Enter）と標準のキーより先に受ける。
- Vim は、使ったキーを以降に渡さない（アプリ全体のキー処理に届かない）。そのため、Windows・Linux では Ctrl を押した押下（Mod と重なる）を、`<C-r>`（やり直し）と `<C-[>`（Esc）を除いて Vim に渡さない（`leavesToApp`。押下から Vim のキーの名前を作る関数を包んで実現する。Vim の標準の割当を `Vim.unmap` で外す方法は、Vim の内部の記録とずれて照合が壊れるため使わない）。macOS の Mod は ⌘ で Vim が使わないので何もしない。Ctrl+R は Vim がやり直しに使うので、割当に使えないキーにする（`src/lib/keymap.ts` の `problemOf`。Ctrl+[ と同じ扱い）。
- Yunagi 固有の `<Space>t`・`<Space>b`・`<Space>h` は、Vim の対応表が全体で1つなので、読み込み時に一度だけ登録し、動かすエディタは押したエディタに結んだ操作（`setVimHost`）で決める。振り返り欄は結ばず、キーだけを受けて何もしない。Vim の標準の `<Space>`（右へ移動。`l` と同じ）は、押した時点で確定して続きのキーを待たないので、この割当だけを外す。
- モードの表示は、拡張の下端の帯（`status`）を使わず、画面の部品（`src/shell/VimBadge.svelte`）が右下に出す。モードの変化は `onVimMode` で部品に知らせる。`/` `?` の検索欄（拡張が下端に出す）と、ブロックのカーソル・検索の一致の色は、色のトークンに置き換える（`src/styles/base.css`）。
- Vim 拡張は、Vimモードが無効でも起動時に読み込む（`TextDocEditor` が静的に読み込むため）。起動の速さは性能試験（テスト計画書 3章の性能）で測り、Vim 拡張の読み込みが目標を妨げると分かったら、Vimモードを有効にしたときの遅延読み込みに変える。
- IME との両立（操作仕様書 4.4）は、この上に作った（3.4）。ノーマルモード中に IME が先に受けたキーの扱いは `src/lib/editor_vim.ts` の `imeKeydown`・`imeInput`（Vim 拡張は、IME が入れようとした文字を Vim のキーとして扱って変換を終わらせるが、かなになる母音（`a` が「あ」）は Vim のキーにならないので、押した物理キーから作ったキーに置き換えて渡す）。

### 3.4 IME の英数切替の方式（2026-11-04 決定）

Vim モードで挿入モードを抜けたとき IME を英数入力に切り替え、入ったとき抜けた時点の入力状態に戻す（操作仕様書 4.4）。切替は OS の機能なので、デスクトップアプリ（`src-tauri/src/ime.rs`）に置く。コア（`yunagi-core`）には入れない（CLI・MCP は画面を持たず、OS の入力状態に触れないため）。

- **呼び出し**：画面は、挿入モードを抜けた・入ったことを Tauri コマンド `ime_leave_insert`・`ime_enter_insert` で知らせる。切替は専用の 1 本のスレッドが順に行い、コマンドは待たずに返る（Esc の直後に `i` を押しても、英数への切替より先に復元が走らない）。入力状態は OS ごとに形が違うので、仕組みごとの文字列（画面は中身を見ない）として、デスクトップアプリ（Rust）側が「直前に挿入モードを抜けた時点」のものを 1 つだけ持つ（整理モードのリストとエディタで共通。復元したら捨てる）。切替の失敗はログに出すだけで、画面の操作を止めない（ベストエフォート）。`ime_status` は、この環境で切り替えられるか（設定画面の制約の表示。画面設計書 7章）を返す。
- **Linux：外部コマンドを呼ぶ**。fcitx5 は `fcitx5-remote`（状態の取得、`-c` で英数、`-o` で IME を有効）、IBus は `ibus engine`（エンジン名の取得と指定。英数は `xkb:us::eng`）。どちらも、常駐プロセスへ D-Bus で頼むコマンドで、D-Bus を直接話す部品（`zbus` など）を新たに依存に入れずに済む。Linux の配布物は AppImage・`.tar.gz`・`.deb`（ビルド・配布手順書 2章）で、どれもホストのコマンドを呼べると考える（コマンドを呼べない隔離された形式の Flatpak・Snap は配布物に含まれない。将来加えるときは、D-Bus を直接話す方式へ切り替える必要がある）。ただし AppImage は、起動のときに環境変数（`LD_LIBRARY_PATH` など）を足すことがあり、それを引き継いだ子プロセスのホストのコマンドが動かないおそれがある。この環境では確かめられていないので、テスト計画書 4.2 で AppImage 版からの呼び出しを確かめる。fcitx5 が動いていればそれを、そうでなければ IBus を使い、どちらも動いていなければ切替の無い環境として扱う（fcitx5 は IBus と同じ名前の D-Bus 口も出すので、先に fcitx5 を見る）。コマンドが無い・動いていない環境は、実行のたびに探し直す（後から IME を起動した場合に使えるように）。
- **Windows：IMM のオープン状態**。前面にあるのがこのアプリの窓のときだけ、フォーカスのある窓の IME の窓へ `WM_IME_CONTROL`（`IMC_GETOPENSTATUS`・`IMC_SETOPENSTATUS`）を送る（別のアプリの入力状態を変えないため。入力のフォーカスは WebView2 の子の窓にあるので、アプリの窓そのものではなく、フォーカスのある窓から IME の窓を求める）。閉じると英数（直接入力）になる。
- **macOS：入力ソース API**（Carbon の Text Input Sources）。いまの入力ソースの ID を覚え、ASCII 入力のソース（`TISCopyCurrentASCIICapableKeyboardInputSource`）へ切り替え、戻すときは ID から入力ソースを求めて選ぶ。この API はメインスレッドで呼ぶ必要があるので、アプリのメインスレッドに頼んで終わるのを待つ。
- **新しい依存**（Rust）：Windows 向けに `windows`、macOS 向けに `core-foundation` を、`src-tauri` の直接の依存に足した（そのターゲットでだけ。直下の `Cargo.toml` の `[workspace.dependencies]`）。どちらも Tauri がすでに使っていて `Cargo.lock` に載っている版（`windows` 0.62.2・`core-foundation` 0.10.1）なので、新しく取り込むコードは増えない。必要な理由：Windows は IMM の関数と窓の API（`ImmGetDefaultIMEWnd`・`SendMessageW` など）を安全な型で呼ぶため、macOS は入力ソース API が返す文字列・配列・辞書の参照の管理（解放漏れを避ける）のため。入力ソース API そのものの宣言（`extern`）は、Rust の部品が無いので `ime.rs` に書く。macOS の `objc2-app-kit` には入力ソース API が無いので使えない。コマンドを呼ぶ方式（`im-select` などの外部ツール）は、利用者に追加の導入を求めるので採らない。
- **確かめられた範囲**：開発は Linux でしか行えない。Linux の fcitx5 は、切替の手順（`Session`・`linux::detect`・`SystemRunner`）を実機の fcitx5 に対して動かし、英数への切替（状態 2 → 1）と復元（1 → 2）を確かめた（アプリの窓を通したものではなく、WebKitGTK の入力との組み合わせは未確認）。Windows・macOS の部分は、`cargo check --target`（x86_64-pc-windows-gnu・x86_64-apple-darwin）で型の検査だけを通し、実機では動かしていない。IBus は動かしていない。実機の確認項目はテスト計画書 4.2 にある。

### 3.5 OS 全体のショートカットの方式（2026-11-04 決定）

アプリが前面になくても、割当のキー（初期割当は macOS が Mod+Alt+Y、Windows・Linux が Alt+Shift+Y）で Yunagi の窓を前面に出す（操作仕様書 1章「OS 全体の操作」）。OS への登録は OS の機能なので、デスクトップアプリ（`src-tauri/src/global_shortcut.rs`）に置く。コア（`yunagi-core`）には入れない。

- **部品**：Tauri のプラグイン `tauri-plugin-global-shortcut` の 2.4.1（直下の `Cargo.toml` で `=` で固定。3.x は alpha なので使わない）。内部は `global-hotkey` で、Windows は `RegisterHotKey`、macOS は `RegisterEventHotKey`、Linux の X11 は `XGrabKey` を使う。
- **登録は Rust 側だけで行う**。プラグインの画面側のパッケージ（`@tauri-apps/plugin-global-shortcut`）は入れず、`capabilities/default.json` に `global-shortcut:*` も窓の操作の権限も足さない。画面には、割当を渡す Tauri コマンド `set_global_shortcut(binding)` 1つだけを見せる。画面から任意のキーを OS に登録したり、窓を操作したりできないようにするため。窓を前面に出す処理（最小化を解く・表示・フォーカス）も Rust 側に閉じる。押したときだけ働かせる（プラグインは離したときにも処理を呼ぶ）。
- **割当は画面が持つ**（設定の `shortcuts`。keymap.ts の `bringToFront`）。画面は、設定の読み込みが終わった後、いまの割当の値が変わるたびにコマンドを呼ぶ（`src/lib/global_shortcut.svelte.ts`）。呼び出しは順に1つずつ。コマンドは、前の登録を外してから、新しい登録をする。割当が `null`（使えない状態）なら外すだけ。割当の文字列 → OS のキーの変換は、`Mod` を macOS では ⌘（`SUPER`）、それ以外では Ctrl にし、英字は `Key<文字>`、数字は `Digit<数字>`（キーの位置）にする。英字・数字以外は変換しない（画面側の検査と同じ）。
- **失敗しても起動を止めない**。プラグインは `run()` の `setup` の中で実行時に入れ（`AppHandle::plugin`）、入れられなければログに出して続ける（以後の登録は `Unavailable`）。窓を開かない結合テスト（`tests/bridge.rs`・`tests/crash.rs`）と `manage_core` にはプラグインを入れない。登録の結果は、コマンドの返り値 `GlobalShortcutStatus`（`off`・`registered`・`taken`・`failed`・`unavailable` と、Wayland かどうかの印）で返し、設定画面が理由の表示に使う。
- **前の登録を外せなかったとき**は、OS にまだ残っているので、登録を持ったままにして `failed` を返し、新しいキーは登録しない（忘れると、古いキーが効き続け、同じキーの登録が「使用中」になる）。次に呼ばれたとき、もう一度外そうとする。
- **登録の失敗の見分け方**：ほかのアプリが使っているキーは、Windows が `ERROR_HOTKEY_ALREADY_REGISTERED`、X11 が `BadAccess` で返し、プラグインはどちらも「HotKey already registered」の文で返すので、`taken` にする。macOS は `RegisterEventHotKey`（修飾キーの `SUPER` は ⌘ にあたる `cmdKey` に変換される。部品のソースで確かめた）の失敗を一般の失敗として返すので `failed` になる（ほかのアプリが使っているときに失敗を返すかは未確認）。
- **Wayland**：`global-hotkey` は X11 だけに対応する。Wayland では XWayland の窓にフォーカスがあるときだけ効く。X の画面に接続できないと、プラグインは接続の失敗を黙って捨て、登録の呼び出しは成功を返す（部品のソースで確かめた）。そのため成否を知る手段が無く、Wayland のセッションでは、登録できても設定に案内を出す（操作仕様書 1章）。代わりの手段は、デスクトップ環境のキーボード設定からコマンド `yunagi show` を呼ぶ方式（CLI 仕様書 3.3。2026-11-04 決定。YUN-88）。Wayland のポータル（`org.freedesktop.portal.GlobalShortcuts`）を使う方式は、デスクトップ環境ごとの対応がまだそろっていないので採らない。
- **`yunagi show` の受け口**（2026-11-04 決定。YUN-88）：ローカル API の `show_app`（CLI・MCP 仕様書 4.4）。データの操作ではないので、`dispatch.rs` が `Call::parse` より前に名前で分け、データベースの錠もクライアントの登録も使わずに、`AppCore::request_show` で知らせ（`Notice::ShowRequested`）を出す。受けた側（`lib.rs` の `emit`）が、窓を前面に出す部品（`global_shortcut::bring_to_front`。OS 全体のショートカットと同じもの）を呼び、画面にイベント `show-requested`（`{note}`）を知らせる。画面は `note` が真のときだけノートモードにする（操作仕様書 1章）。窓の操作は Rust 側に閉じる（画面に権限は渡さない）という決まりは変わらない。窓の操作は `run_on_main_thread` でメインスレッドに頼み、待たない（接続のスレッドが、アプリの終了で接続の終わりを待つ `close` と、メインスレッドの完了の待ちで行き違わないように）。`note` が真の頼みは、コアが `show_note` として覚え（`AppCore::request_show`）、画面が準備できたとき（起動した直後は、API の待ち受けが画面の準備より先に開き、`show-requested` を取りこぼす）と `show-requested` を受けたときに、Tauri コマンド `take_show_note` で受け取る（受け取ると忘れる。最後の頼みに従い、ノートモードの指定の無い頼みは、受け取られていない古い頼みを取り消す）。2 つ目の起動の引き渡しも同じ（コアを持たせる前に届いたものは、`EARLY_SHOW_NOTE` に覚えて同じコマンドで渡す）（引数に `--note` があれば、`note: true` の頼みになる。`lib.rs` の `handover`）。知らせの受け手に窓の操作を置くので、窓を開かない試験（`tests/api.rs`）は知らせを受け取るだけで確かめられる。
- **単一インスタンス**（2026-11-04 決定。YUN-88）：Tauri のプラグイン `tauri-plugin-single-instance` の 2.5.5（直下の `Cargo.toml` で `=` で固定。3.x は alpha なので使わない。2026-10-28 公開）。2 つ目の起動は、動いているアプリに引数と作業フォルダを引き渡して成功（終了コード 0）で終わり、動いているアプリが窓を前面に出す（`show-requested`、`note: false`）。`Builder` の最初のプラグインとして入れる（データベースを開く前に判定する）。動いているアプリを見つける方法は、Linux は D-Bus のセッションバス（名前 `<識別子>.SingleInstance`）、macOS は UNIX ドメインソケット、Windows は名前付きのミューテックス。Linux でセッションバスが無い・使えないときは、プラグインが警告を出して通常どおり起動する（単一インスタンスにはならず、2 つ目は 4章 4 のとおりロックを待って利用者に知らせる）。この仕組みが要る理由：データベースを見つけられない・開けない間の起動時の画面（4.4）は、アプリが動いていてもロックも待ち受けも持たないので、`yunagi show` はアプリが動いていることを待ち受けでもロックでも知れず、起動してしまう。起動した 2 つ目をここで引き渡して終わらせれば、動いているアプリが窓を前面に出す。macOS の受け口は、プラグインが `/tmp/<識別子（`.`・`-` を `_` にしたもの）>_si.sock` の UNIX ドメインソケットとして作る（利用者ごとの場所ではない）。**既知の制限（2026-11-04 決定）**：同時に 2 人がログインしている macOS では、あとから起動した利用者のアプリが、先の利用者のアプリのソケットに引き渡して終わり、起動できない（プラグインがソケットの持ち主を確かめないため）。個人の端末で使う想定（要件定義書）なので、MVP では直さず、実機で確かめる項目に入れる（テスト計画書 4.8）。直すときは、プラグインを使わずに、利用者ごとの場所のソケットで同じことをする。Windows のミューテックスは名前に `Global\` が付かず、ログオンのセッションごと。Linux の D-Bus のセッションバスは利用者ごと。**Wayland のフォーカスの許可**：Wayland では、裏にいるアプリが自分でフォーカスを取ることをコンポジターが止めることがある。キー設定から起動された `yunagi` は、許可の印（環境変数 `XDG_ACTIVATION_TOKEN`）を受け取っていることがあるが、`show_app` も単一インスタンスの引き渡しも、この印をアプリに渡していない。GNOME などで「窓が前に出ずに通知になる」ときの第一候補の原因なので、実機で確かめる（テスト計画書 4.8）。必要なら `show_app` に引数を足す（`show_app` は知らない引数を `-32602` で断るので、足すのはプロトコルの変更になる）。待ち受けの条件をゆるめて `show` だけ受ける案は採らない（「API が答える間はアプリがロックを持つ」という約束が崩れ、データの操作が `busy` を返せなくなるため）。**新しい依存**：Linux では D-Bus の部品（`zbus` とその依存の `async-io`・`async-process`・`zvariant` など約 30 のクレート）が `Cargo.lock` に増える（D-Bus の部品は Linux のビルドだけが使う。macOS・Windows は別の仕組みで、`Cargo.lock` の追加分のうち、使うのはその一部）。`Cargo.lock` に載った版は、これまでと同じく CI の脆弱性検査（ビルド・配布手順書 3章）の対象。
- **確かめられた範囲**：開発は Linux でしか行えない。割当 → OS のキーの変換、登録・外す・登録し直す・失敗の分類（部品を偽物に差し替えたもの）、画面側の登録のし直し（割当を変える・保存に失敗して戻る・使えなくなる）と理由の表示は、自動テストで確かめた。実際に OS に登録して窓が前面に出るかは、どの OS でも実機で確かめていない（テスト計画書 4.8）。`src-tauri/src/global_shortcut.rs` は OS ごとの分岐を持たない（`Mod` の読み替えだけ `cfg!(target_os = "macos")`）。登録の部品 `global-hotkey` は、Windows 向け（`x86_64-pc-windows-gnu`）の型検査を通した。macOS 向けは、この環境では Objective-C の部品のビルドで止まり（`cc` が `objc2-exception-helper` をビルドできない）、アプリごとも部品だけも型検査を通せていない。アプリごとの Windows 向けの型検査も、C の道具（mingw）が無く通せていない。

## 4. 書き込み経路と同時実行

1. アプリ起動中は、コアがデータベースへの唯一の書き込み主体となる。CLI と MCP サーバーはローカル API 経由でコアに依頼する。
2. アプリ停止中は、CLI と MCP サーバーが操作ごとにロックファイル `yunagi.lock`（6章の既定ディレクトリ）の排他ロックを取得してからデータベースを開き、操作が終わったらロックを離す。ロックを持ち続けない。
3. CLI も MCP サーバーも、操作ごとに、まずローカル API への接続を試み、ローカル API が無いときだけ 2 の直接モードで処理する（手順は 4.4。MCP サーバーは常駐し、アプリの起動・停止をまたいで動き続けるので、操作ごとに選び直す）。ロックが取れなかったからといって、ローカル API を試す順にはしない（アプリが動いている間はアプリがロックを持っているため、ロックを取ろうとしても必ず待たされて失敗する）。
4. アプリは起動時に `yunagi.lock` を取得する。取れないとき（CLI・MCP の直接モードの操作中）は最大数秒待ち、それでも取れなければエラーを表示する。CLI・MCP の側でロックが取れないときの扱いは 4.4。
5. いずれの経路でも、ドメイン層の同じ関数を通るため、検証・権限判定・変更履歴の記録は一様に適用される。
6. MVP では、コアは変更をイベントとしてフロントエンドに通知し、画面はデータを再読み込みして最新の状態を表示する（エージェントによる変更も含む）。変わった項目の強調などの演出は第2フェーズ（ロードマップ参照）とする。

ローカル API のソケットは利用者本人のみが読み書きできる権限で作成し、接続時にランダムなトークンで認証する。トークン・ソケット・ロックファイルは、保存先の設定に関係なく6章の既定ディレクトリに置く（保存先をクラウド同期フォルダにしても同期されないようにするため）。

### 4.1 利用者の入力中に届いたエージェントの変更（2026-11-02 決定）

再読み込み（4章 6）で、利用者が入力中の文字・カーソル・変換中の文字を壊さず、利用者の入力を失わないよう、対象ごとに次のように扱う。

**項目の入力中**：フロントエンドは、フォーカスのある項目の欄（本文または解消メモ）と「入力中かどうか」をコアに知らせる。項目の本文または解消メモは、その欄にフォーカスがあり、かつ最後の入力から 10 秒以内か IME の変換中であれば入力中とする。10 秒は、考えながら打つ間の小休止を含めつつ、エージェントを長く待たせないための長さ。フォーカスが外れたとき、またはアプリが前面から外れたときは、まだ保存していない入力（自動保存の待ち。最大 0.5 秒）をすぐに書き込み、その書き込みが終わった時点で入力中を終える。書き込みが終わるまではフォーカスが無くても入力中とみなす。保存前にエージェントの変更を受け付けると、続く保存でエージェントの変更が利用者の入力で上書きされるため。

**保存に失敗している間**：書き込みに失敗して自動で再試行している間（画面設計書 3章「上部のバー」の「保存できていません」）は、入力中とはみなさない。代わりに、コアは画面からの保存の書き込みに失敗してから、次に書き込みが成功するまでの間、エージェントの書き込みをすべて（対象に関係なく）受け付けず `storage_unavailable` を返す（ただし、引数の誤りや取りやめた TODO への書き込みなど、保存先に関係なく必ず失敗する `invalid_argument` は先に返す。MCP・CLI 仕様書 3.2 の判定の順）。読み取りは受け付ける。保存先への書き込みが失敗している以上、ほかの対象への書き込みも確かではなく、まだ保存できていない入力がある対象の内容も確定しないため。保存が成功すれば通常の扱いに戻る。これにより、保存が失敗し続けても `user_editing` を返し続けることはなく、エージェントは保存先の問題であることを知れる。

**ノート・振り返りの守る行**：エディタにフォーカスがある間、またはまだ保存していない入力がある間、フロントエンドは、エージェントに変えさせない行（守る行）をコアに知らせ、変わるたびに知らせ直す。守る行は次の2つを合わせたもの。

- カーソル行：カーソルのある行（選択範囲が複数行にまたがるときはその全部の行）。項目と同じく、エディタにフォーカスがあり、かつ最後の入力から 10 秒以内か IME の変換中の間だけ含める。フォーカスが外れたとき、またはアプリが前面から外れたときは、すぐに含めるのをやめる（まだ保存していない入力は、次の「未保存の変更がある行」として保存まで守られる）。入力をやめてエディタを開いたままにしても、エージェントを待たせ続けないため。
- 未保存の変更がある行：最後に保存した本文の行のうち、エディタで書き換えたか削除して、まだ保存していない行。差分の上では「削除＋追加」に見える書き換えも、元の行の書き換えとして含める。カーソルを別の行へ移しても、保存されるまでは守る行に残る。

行番号は、コアにある保存済みの本文で数える（エージェントが `get_note` で読み、`edit_note` で指定するのと同じ数え方）。エディタにはまだ保存していない行が含まれうるため、フロントエンドは、最後に保存した本文とエディタの内容の差分から、行番号を保存済みの本文の行番号に置き換えて知らせる。保存前に足した新しい行は、エージェントが指定できないので知らせない（保存済みの行を書き換えた結果の行なら、元の行が「未保存の変更がある行」として守られる）。知らせた行番号には、数えた本文（最後に保存した本文）の版の番号（`rev`）を添える。コアは版ごとの本文を持たないため、行番号をずらして使うことはしない。守る行が1行以上あると知らせている間に、添えられた版とコアの版が違う（その間にエージェントの変更か利用者の保存が書き込まれ、行番号が古くなった）ときは、そのノート・振り返りへの `edit_note` をすべて `conflict`（`reason: user_editing`）にする。フロントエンドは、版が進むたび（自分の保存が成功したとき、エージェントの変更を取り込んだとき）に、新しい版で守る行を知らせ直す。知らせ直しが届けば通常の判定に戻る。版が一致していれば、守る行はコアの本文の行番号そのものなので、守る行が消えている場合は起きない。

| 対象 | 入力中に届いたエージェントの変更 |
| --- | --- |
| 項目の本文（`edit_todo` / `edit_blocker`） | 取りやめた TODO（`dropped`）と、種類の違う項目（`edit_todo` に障害、`edit_blocker` に TODO）は `invalid_argument` で拒み、それ以外の持ち越し済みの項目（前の日に残る元の項目）は、入力中かどうかにかかわらず `conflict`（`reason: carried_over`）で拒む（`invalid_argument` が先。MCP・CLI 仕様書 3章。次の行も同じ）。その項目の本文を入力中なら受け付けず、`conflict`（`reason: user_editing`。MCP・CLI 仕様書 4.3）を返す。エージェントは後でやり直す。解消メモの入力中は、本文とは別の欄なので受け付ける。入力中でなければ受け付け、フォーカスがあってもその場で画面に反映する（カーソルは同じ文字位置。本文より後ろなら末尾）。今と同じ本文（前後の空白を除いて比べる）なら、何も変えずに `updated: false` で成功する（MCP・CLI 仕様書 3章） |
| 項目の状態（`complete_todo` / `reopen_todo` / `resolve_blocker`） | 持ち越し済みの項目と取りやめた TODO、種類の違う項目（`complete_todo` / `reopen_todo` に障害、`resolve_blocker` に TODO）でなければ、本文・解消メモとは別の欄なので、本文または解消メモの入力中でも受け付けてすぐ反映する。ただし `--note` 付きの `resolve_blocker` は解消メモの欄にも書くため、その障害の解消メモを入力中なら受け付けず、`conflict`（`reason: user_editing`）を返す（本文に対する `edit_todo` と同じ）。入力中でなければ、解消メモの欄にフォーカスがあっても書き込み、その場で画面に反映する。解消メモの欄は障害が解消済みの間だけ開く（未解消に戻すと、まだ保存していない入力を書き込んで閉じ、入力中を終える。操作仕様書 2章）ため、このとき障害はすでに解消済みで、やり直した `resolve_blocker` は解消済みの障害への扱い（MCP・CLI 仕様書 3章）に従う |
| ノート・振り返り（`append_note` / `append_reflection` / `edit_note`） | 受け付ける。エディタには本文の置き換えではなく差分（変更箇所だけ）として取り込み（下記「取り込み方」）、カーソルと選択範囲を保つ。IME の変換中は、変換が終わるまで取り込みを待つ。取り込んだ変更は Mod+Z の取り消しの対象にしない（04 2章。取り消しは変更履歴 S-06 から）。`edit_note` で、守る行（上記）を書き換え・削除・移動しようとした場合と、守る行の版が古い場合（上記）だけ `conflict`（`reason: user_editing`）にする。`--expect` の不一致（`reason: changed`）にも当たるときは `changed` を返す（MCP・CLI 仕様書 3章） |

**自動保存（2026-11-03 決定）**：画面は保存の操作なしに、入力を自動で保存する（要件 F-08）。コードは `src/lib/autosave.svelte.ts`。

- 送る時：まだ保存していない最初の入力から 0.25 秒後に送る。入力が続いても待ち直さない（入力のたびに待ち直すと、打ち続けている間は保存されず、強制終了で多くを失うため）。保存の書き込みは 0.25 秒未満で終わる前提で（遅い CI の debug ビルドでも 0.2 秒余りで終わることを確かめている）、入力が止まってから保存し終えるまでと、入力中に強制終了して失う入力を、どちらも 0.5 秒以内にする（テスト計画書 4.1・5章）。フォーカスが外れたときとアプリが前面から外れたときは、待たずにすぐ送る（上の「項目の入力中」）。
- 項目の保存は `save_item` コマンド1つで、変えた欄（本文・解消メモ・状態）をまとめて送る（上の「項目の保存」）。まだ作っていない項目は、本文が入ってから作り（`add_item`）、作り終えてから残りの欄を送る。削除・並べ替え・分割は、その項目の保存を送り終えてから行う（`ItemSaves.run`）。削除・並べ替え・削除の取り消しは、画面の中で1つずつ順に送る（`src/lib/board.svelte.ts`）。並べ替えと、まだ作っていない項目を作るときの位置（「この項目の後」など）は、送る時点の画面の並びで決める（前後の行がまだ作られていないうちに入力した行も、画面の順に入るようにするため）。作る前にやめた行（取り消し・削除・何も書かずに離れた）は、まだ送っていない内容を送らずに捨てる。読み込み直しで、作るのを送っている途中の行と同じ種類・本文のまだ知らない項目が届いたら、その行を作ったものとみなして二重に出さない（作った後の読み込みが、作った応答より先に届くことがあるため）。画面で作った項目が、読み込みに2回続けて出てこなければ、ほかで消されたものとして画面からも消す（作る前に始まった読み込みは、作った後の読み込みより前に1回だけ届きうるため）。
- 再試行：保存先の問題（`storage`）、データベースを開いていない（`not_ready`）、コマンドの処理が途中で止まった（`internal`）で失敗したら、内容を持ったまま、1・2・4・8 秒、以後 10 秒ごとに再試行する。その間は「保存できていません」（画面設計書 3章）を出し、「再試行」の操作では待たずに送る。ほかの失敗（引数の誤り・項目が無い・持ち越し済みなど）は、送り直しても成功しないので再試行せず、送った内容を捨てて画面に知らせる（画面は表示を読み込み直す）。再試行しない失敗の後は「保存できていません」を終える。ただし、項目を作る（`add_item`）ときの `internal` は、書き込みが済んだかが分からず、作り直すと項目が2つになりうるので再試行せずに知らせ、その行の続きの入力でも作り直さない（画面はボードを読み込み直す）。作り終えた項目は、画面が付けた仮の名前でも ID でも同じ待ち行列を使う（一度に1つの決まりを守るため）。ノート・振り返りの保存は、どの失敗も再試行する（捨てるとエディタの本文が保存されないまま保存済みに見えるため）。まだ作っていない項目は、本文が空白だけの間は作らない。保存に失敗している間は、その項目の削除・並べ替え・分割を行わない（まだ保存していない入力の前の本文で行わないため）。表示している日を移るなどで待ち行列を片付けるときは、先に保存し、失敗していれば保存し終えるまで再試行を続ける。そのとき、片付ける時点の本文を手元に写し、以後はエディタに触れない（エディタが別の日を映しうるため）。行き違いが続いて送り直しが上限（10 回）を超えたときも、まだ保存していない入力があるとして、削除・並べ替え・分割を行わない。
- 行の分割の再試行（2026-11-03 決定。`ItemSaves.split`）：行の途中の Enter で、画面はすぐに2行を出し、分割（`split_item`）を待たずに送る。分割は保存に数える（4.3）。保存先の問題などで失敗したら、2行を画面に出したまま、上の再試行と同じ間隔で送り直す。送るのは送る時点の2行の本文で、再試行を待つ間に元の行・新しい行に入力した本文も、その分割にまとめる（元の行の入力を別の保存として先に送ると、分割より前に元の項目の本文が短くなり、その間に強制終了すると後ろの半分を失うため）。分割を送っている途中に元の行へ入力した本文は、分割を送り終えてから元の項目の保存として送る。送る時点で新しい行の本文が空白だけなら分割を送らず、何も書かずに離れたら分割をやめて、元の行の本文を元の項目の保存として送る。元の行を空白だけにした入力は送らない（空白だけの本文は保存しないため。分割には、その前の本文を送る）。送り直しても成功しない失敗で分割を捨てたときは、2行の本文をつないで元の項目の保存として送り、新しい行は画面から消す（`internal` で分割が済んでいたなら項目が重なるが、利用者の入力は失わない）。分割を送り終えるまでは、元の項目の削除・並べ替え・分割を行わず（その分割を先に送り終える）、元の項目の本文はまだ保存していない欄として入力中に数える。再試行の間に読み込み直しても、2行のまま出す。
- 入力中の状態の知らせ（2026-11-03 決定。`src/lib/ui_report.svelte.ts`）：画面は、項目の入力中の欄と、ノート・振り返りの守る行を組み立てて `report_ui_state` で知らせる。`report_ui_state` は毎回全体を置き換えるので、整理モード（項目・振り返り）とノートモード（ノート）の分は、画面全体で1つの `InputTracker` にまとめ、1回の知らせに全部を入れる（別々に送ると、後から送った方が前の方の守る行を消す）。どちらのモードの本文も、もう一方のモードの間は消さずに隠すので、隠れている側の未保存の変更がある行も知らせ続ける（隠れている側のエディタはフォーカスを失うので、カーソル行は入らない）。入力・フォーカス・選択範囲・IME の変換・アプリが前面にあるか・保存の状態が変わるたびに組み立て直し、中身が前に送ったものと違うときだけ送る。最後の入力から 10 秒経って入力中でなくなる時刻にも組み立て直す。送るのに失敗したら（データベースを開いていないなど）、次に組み立て直したときに送り直す。
  - 項目：フォーカスのある欄（本文か解消メモ）を、アプリが前面にあり、最後の入力から 10 秒以内か IME の変換中なら入れる。まだ保存し終えていない欄（`ItemSaves.unsavedFields`。送るのを待っている・送っている欄と、分割を送り終えていない元の項目の本文）は、フォーカスに関係なく入れる。まだ作っていない項目は入れない（エージェントが ID を知らないため）。
  - ノート・振り返り：カーソル行（エディタにフォーカスがあり、アプリが前面にあり、最後の入力から 10 秒以内か IME の変換中のとき）を、最後に保存した本文の行番号に置き換えたもの（`text_merge.ts` の `baseLinesOf`。変えていない行は同じ行、書き換えた行は書き換える前の行、足しただけの行は入れない）と、未保存の変更がある行（`DocSaver.unsavedLines`）を合わせ、その版を添える。表示している日を移って、前の日の保存を片付けている途中（保存し終えるまで再試行している）なら、その日の未保存の変更がある行も入れる。守る行の無いエディタは入れない。
- 保存状態：まだ保存していない入力がある間（送るのを待っている間と、送っている間）を「保存中」とする（画面設計書 3章の小さな点）。
- ノート・振り返りで、保存を送っている間に `changed` でエージェントの変更を読み直したときは、応答を受けてから取り込む（送った内容がもとに入る前に取り込むと、利用者の行が二重になるため）。
- ノート・振り返りの読み直し（2026-11-03 決定）：画面向けのボード（`get_board` コマンド）は、振り返り・ノートの版（`reflectionRev`・`noteRev`。まだ書いていない日は 0）を添える。`changed` でボードを読み直したとき、エディタは、その版が最後に保存した（取り込んだ）版より進んでいるときだけ本文を読み直して取り込む（項目だけが変わったときに、ノート・振り返りの本文を読み直さないため）。その日の本文を読んでいる途中に知らされた版は、読み終えてから比べ直す（読み始めた後のエージェントの変更を取りこぼさないため）。日を移ってすぐ戻ったときなど、同じ日を読み直したら、前に始めた読み込みの結果は捨てる。版が進んだときの読み直しに失敗したら、版が変わらなくても間を空けて（1秒）読み直す（次に版が進むまで、エージェントの変更を取り込めないままにしないため。2026-11-03 決定）。読み直しは一度に1つだけ行い、読み直している間に知らされた版は、読み終えてから比べ直す。

**ノート・振り返りへの取り込み方**：エージェントの変更をエディタに取り込むとき（保存の行き違いで最新の内容を取り込むときも同じ）、フロントエンドは、最後に保存した本文をもとにして、「エージェント側の変更（もとの本文→コアの最新）」と「利用者のまだ保存していない変更（もとの本文→エディタ）」を合わせる。

- 重ならない変更は、両方を残す。
- 同じ位置への行の追加は、両方を残す（利用者の行を先にする）。
- 利用者がまだ保存していない新しい行は、すぐ上の保存済みの行の後ろに付いているものとして扱う。その保存済みの行がエージェントの変更（書き換え・削除・移動）の範囲に入って元の位置から無くなった場合は、利用者の行を、その範囲があった位置に残す。範囲を書き換えた場合は新しい行の後ろ、削除・移動した場合は範囲のすぐ上の行（範囲の外で残っている行）の後ろに置く。移動では利用者の行を範囲と一緒に動かさない（移動は「元の位置から削除して別の位置に追加」として扱うため）。
- 同じ行を両方が変えた場合（守る行を知らせる前にエージェントの変更が届いた、行き違いのときに限られる）は、両方の結果を残す。その行の位置に、利用者の結果の行、続けてエージェントの結果の行を置く（同じ位置への追加と同じく利用者の行が先。どちらかが削除なら、その側の行は無い）。どちらの行を残すかは利用者が画面で決める。両方の変えた範囲が一部だけ重なるときは、重なりをつないだ範囲を1つとして、その範囲の利用者の結果、続けてエージェントの結果を置く。両方が同じ結果にしたなら1つだけ残す（2026-11-03 決定。コードは `src/lib/text_merge.ts`）。
- エージェントの新しい行が、利用者の書き換えた行のすぐ後ろに付いている場合は、利用者の結果の行の後ろに置く（利用者の新しい行の扱いと同じ）。

エージェントの変更は、コアが受け付けた時点でデータベースに書き込まれて確定し、change_log の `after` もその内容になる。エージェントに返す成功はこの確定を指す。取り込みの後に利用者がその内容を消したり書き換えたりして保存した場合は、エージェントの変更の後の人の変更として扱う（変更履歴 S-06 には取り込んだエージェントの変更がそのまま残り、`agent revert` は人の変更と衝突したものとして `reason: changed` になる。MCP・CLI 仕様書 7章）。

取り込んだ後、フロントエンドは「最後に保存した本文」をコアの最新の本文に、もとにする版の番号をコアの最新の版に進める。以後の「利用者のまだ保存していない変更」は、この新しいもととエディタの差分になる。もとを進めないと、次の保存が古い版のもととして弾かれ、古いもとで取り込みをやり直して、取り込み済みのエージェントの行が二重になるため。続けて、新しい版で守る行を知らせ直し（上記）、まだ保存していない入力があれば保存する。

これにより、利用者の入力はすべてエディタに残り、エージェントの変更も受け付けた時点でノートに書き込まれ、取り込んだ後もエディタに残る（利用者が自分で消すまで）。

**ノート・振り返りの保存の行き違いを防ぐ**：note・reflection は版の番号（`rev`。データモデル設計書）を持つ。フロントエンドの保存には、もとにした版の番号を添える。同じノート・振り返りへの保存は一度に1つだけ送り、成功の応答で返る新しい版の番号を次の保存のもとにする（利用者自身の保存どうしが行き違わないようにするため）。コアの版のほうが新しい（その間にエージェントが変更した）場合、コアは保存を受け付けずに最新の内容を返す。フロントエンドは、上の取り込み方で最新の内容をエディタに取り込み、利用者のまだ保存していない入力を残したまま保存し直す。

**項目の保存**：item は版の番号を持たない。フロントエンドの保存では、利用者が変えた欄（本文・解消メモ・状態・並び順など）だけを送り、コアは送られた欄だけを書く。ほかの欄は書かないため、エージェントが同じ項目の別の欄を変えていても、その変更は残る（例：本文の入力中にエージェントが `complete_todo` で完了にしても、続く本文の保存で未完了に戻らない）。同じ欄をエージェントも変えていた場合（入力中の判定と行き違ったときに限られる）は、利用者の保存で上書きする（状態の欄を両方が同じ値にした場合は、下記「利用者とエージェントが項目を同じ状態にした行き違い」に従う）。項目は利用者の入力を優先するので、ノートのように保存を拒否して最新を返し、保存し直す往復をしても結果は変わらないため。エージェントの変更は受け付けた時点で確定しており（ノートと同じ）、利用者の保存はその後の人の変更として扱う。エージェントの変更は change_log に記録済みで（未確認の印も付いたまま）、変更履歴 S-06 で確かめられ、`agent revert` はその欄について人の変更と衝突したものとして `reason: changed` になる。

同じ項目への保存は、ノートと同じく一度に1つだけ送り、前の保存の応答を待ってから次を送る。待っている間に変えた欄は、次の保存にまとめる（同じ欄を何度も変えたら最後の値だけを送る）。版の番号が無いので、送った順に書き込まれないと、利用者自身の古い保存（例：本文 `foo`）が新しい保存（`foobar`）を追い越して上書きしてしまうため。

**利用者とエージェントが項目を同じ状態にした行き違い（2026-11-03 決定）**：利用者が画面で項目の状態を変えて（完了にする・未完了に戻す・解消する）から、その保存が書き込まれるまでの間（自動保存の待ちや、前の保存の応答待ち）に、エージェントの同じ状態にする操作（`complete_todo`・`reopen_todo`・`resolve_blocker`）が届くことがある。届いた時点のコアは利用者の変更をまだ知らないので、エージェントの操作は状態を変えたものとして受け付け、change_log に記録する。そのままでは、続く利用者の保存は値を変えず、変更がエージェントのものとして残る（未確認の印が付き、`agent revert` で利用者が自分で変えた状態が戻されうる）。そこで、この場合は利用者の変更として扱う。利用者の保存が先に届いていれば、エージェントの操作は「すでに目的の状態」として何も変えず、記録もされない（MCP・CLI 仕様書 3章）ので、その順に届いた場合と同じ結果にそろえる。エージェントの操作を拒否しないのは、届いた時点では利用者の変更を知りえないため。画面が状態の変更を操作のすぐ後に送っても、それがコアに届くまでの間は同じことが起きうるので、届く前に防ぐのではなく、保存を書き込むときに判定する。

- 画面からの保存では、状態の欄に、変える前の値（利用者がその保存で最初に状態を変えたときに画面に出ていた状態）と、利用者が状態を変えた操作の時刻を添える。前の保存の応答を待つ間に何度も状態を変えて1つの保存にまとめた場合（上記）は、変える前の値と時刻は最初の操作のものを添える（2026-11-03 決定。最後の操作の時刻は、下の判定に使わず、完了時刻として画面が別に添えるので、添えない）。時刻はコアと同じ端末の時計でミリ秒まで測る。画面で状態を変えたときの完了時刻（`completed_at`。障害では解消時刻）は、操作仕様書 2章のとおり画面が決めて（ふつうは利用者の最後の操作の時刻、未完了・未解消に戻したときは空、Mod+Z で戻す操作を取り消したときは元の時刻）保存に添え、行き違いの有無に関係なく、その値を書く。
- コアは、利用者の保存を書き込むときに、その項目の状態を変えた記録のうち、最初の操作の時刻より後に作られた（change_log の `created_at` で比べる。同じ時刻なら利用者の操作が先とみなす）最初の記録が、次のすべてに当たれば行き違いと判定する。
  1. 取り消されていない。
  2. 状態の `before` が変える前の値で、`after` が保存の値（利用者が最後に選んだ状態）。
  3. エージェントの状態の操作（`todo.complete`・`todo.reopen`・`blocker.resolve`）の記録である（2026-11-03 決定）。取り消しの記録（`agent.revert`。人が実行したものも含め、状態を変えた記録に数える）が最初なら当たらない。取り消しの前後は利用者の操作との順が入り組むので、ふつうの上書きにする。
  4. 取り消しの記録の `revert_of_id` から指されていない（2026-11-03 決定）。指されている記録は外部キーのため消せない。ふつうは取り消すと `reverted_at` も入るので 1 で外れるが、壊れたデータで外部キーの誤りになり、保存が失敗し続けないよう、指されていれば当たらないものとして扱う。
- 行き違いのとき、コアは、その記録から状態と完了時刻の欄を外す。記録にほかの欄が残れば（`--note` 付きの `resolve_blocker` の解消メモなど）、その欄はエージェントの変更のまま残す（未確認の印も残る）。何も残らなければ、記録を消す（実際に何かを変えた操作だけを記録する決まり。データモデル設計書 change_log）。利用者の保存とこの書き換えは、1つのトランザクションで行い、終わったら変更をフロントエンドに知らせる（4章 6）。画面は再読み込みし、上部のバーとサイドバーの件数、項目の行頭の菱形、変更履歴 S-06 から、その記録の分を消す。消した記録を `agent revert` で指定すると `not_found` になる。
- 外すのは最初の記録だけで、それより後のエージェントの記録（行き違いの間に未完了に戻してから、もう一度完了にした場合など）は残す。利用者の保存が先に届いていれば、何も変えずに終わるのは最初の操作だけで、その後の操作は状態を実際に変えるため。その順に届いた場合と同じ記録にするため、次のようにする。
  - 後の記録が無いとき：利用者の保存のとおり、状態と完了時刻を書く。
  - 後の記録があるとき：すぐ後の記録の状態と完了時刻の `before` を、利用者の保存の値（状態と、保存に添えた完了時刻）に書き直す（外した記録の値が残らないように。完了時刻は、その記録が完了時刻の欄を持つときだけ書き直す）。現在の状態が保存の値と同じなら、状態と完了時刻は書かず、最後の記録の `after` のままにする（利用者の保存は、その順なら後の記録より前に書かれているため）。現在の状態が保存の値と違えば、上の「項目の保存」のとおり利用者の保存で上書きする。
  - 残った記録は、ふつうのエージェントの記録として扱う（`agent revert` の判定も MCP・CLI 仕様書 7章のとおり）。外した記録は、Mod+Z で状態を戻すかの判定（操作仕様書 2章の「その後にエージェントが状態を変えていた場合は戻さない」）でも、エージェントの変更に数えない。
- エージェントにはすでに成功（`updated: true`）を返しているが、項目はエージェントが目指した状態になっているので、目的は果たされている。同じ操作をやり直せば `updated: false` になる。
- エージェントの操作が届いた後に保存の書き込みが失敗して再試行した場合は、書き込みが成功した時点で判定する（再試行の間に届くエージェントの書き込みは、上の「保存に失敗している間」のとおり `storage_unavailable` になる）。
- 当たらない場合はこれまでどおり扱う。最初の操作の時刻より前に作られた記録（利用者の操作の直前にエージェントが変え、画面の再読み込みが間に合わなかった場合）は、実際にエージェントが先に変えているので、エージェントの変更として残す。まとめた保存では、途中の状態は問わず、変える前の値と最後に選んだ状態で判定する（例：完了・未完了に戻す・完了と続けた間にエージェントが完了にした場合は、行き違いとして記録を外す。利用者の保存が先に届いていれば、エージェントの操作は完了の上で何も変えないため）。利用者が最後に選んだ状態がエージェントの目指した状態と違う場合（例：完了にしてから未完了に戻した）は、利用者の保存で上書きし、エージェントの記録は残す（`agent revert` は `reason: changed` になる）。

change_log の項目の記録には、その操作が変えた欄だけを `before` / `after` に入れる（データモデル設計書 change_log）。`agent revert` は、その欄の現在の値と `after` を比べて人が後から変えたかを判定し、取り消しではその欄だけを `before` に戻す。ほかの欄（利用者がその後に変えた本文など）には触れない。

アプリの停止中は画面での入力がないため、この扱いは起動中にだけ働く。

### 4.2 `yunagi.lock` のロックの取り方（2026-11-03 決定）

- OS のファイルロック（Rust 標準の `File::try_lock`。Linux・macOS は `flock`、Windows は `LockFileEx`）で排他ロックを取る。外部のクレートは使わない（標準で3つの OS に対応するため）。プロセスが異常終了しても OS がロックを離すので、取り残されたロックを手で消す必要はない。
- コアのロックの関数は既定ディレクトリ（6章）を受け取り、ファイル名 `yunagi.lock` はコアが付ける。保存先（`data_dir`）を渡すと、保存先を変えた利用者のアプリと CLI・MCP が別のファイルをロックしてしまうため。ただし、環境変数が違って既定ディレクトリそのものがずれると、保存先を渡さなくても別のファイルをロックする。その検出と扱いは 4.5。
- ロックの関数はフォルダを作らない（呼び出し側が用意する）。既定ディレクトリを作るのはアプリだけで、CLI・MCP は作らない（6章。無いときの扱いは 4.5）。
- ロックファイルは消さない。例外は `yunagi uninstall --purge` が最後に既定ディレクトリごと消すときだけ（ビルド・配布手順書 4.4。消している最中に別のプロセスが起動しない使い方に頼る）。消さない理由（消すと、消す前のファイルを掴んだプロセスと作り直したファイルを掴んだプロセスが、両方ともロックを取れてしまうため）。
- 取れないときは 50 ミリ秒ごとに取り直しを試み、最大 5 秒待つ（4章 4 の「数秒」）。直接モードの CLI・MCP の操作も同じ時間だけ待つ。それでも取れなければエラーにする（CLI・MCP では `busy`。待つ間にローカル API も試し直す。4.4）。
- データベースは、取ったロックを渡さないと開けない（コアの `Database::open`）。開いている間はデータベースの接続がロックを持ち、閉じるとロックも離れる。これで、ロックを持たずにマイグレーションが走らないことを型で守る（データモデル設計書 1.1）。
- ロックが既定ディレクトリのものであることも型で守る（2026-11-03 決定）。既定ディレクトリはコアの専用の型（`DefaultDir`）で受け渡し、本番のコードではこの型を、既定ディレクトリを求めるコアの関数（`default_dir`）でしか作れない。ロックの関数と `config.json` の読み書きはこの型だけを受け取るので、保存先などのフォルダを渡せない。テストで一時フォルダを既定ディレクトリとして使う作り方は、コアのテストのビルドにだけ含める（cargo の機能の切り替え（feature）にすると、本番のコードからも有効にできてしまうため）。
- 保存先の変更（6章）は、取ったロックを渡さないと呼べず、`config.json` はそのロックの既定ディレクトリのものを使う。開いているデータベースはロックを持っているので、ロックが手元にあれば、そのプロセスがコアを通して開いたデータベースは閉じている（閉じるのに失敗したときは、ロックだけでなくデータベースごと返す）。コアを通さずに開いた接続までは型で防げないため、データベースはコアの外で開かない。アプリは、ロックを離さずにデータベースを閉じてから保存先を変え、同じロックで開き直す（閉じてから取り直すと、その間に CLI・MCP が開きうるため）。
- データベースの場所（保存先）は、ロックを取った後で `config.json` から求める（コアの `DbLock::database_path`）。`Database::open` もパスを受け取らず、渡されたロックの既定ディレクトリの `config.json` から求める（2026-11-03 決定。直接モードの `Database::with_locked` もこれを使う）。取る前に求めたり、呼び出し側がパスを渡せたりすると、ロックを待っている間にアプリが保存先を移したときや、移した後に古いパスを使ったとき、古い保存先を開いてしまうため。データベースが無いときの扱いは 6.3。

### 4.3 画面とコアのつなぎ方（2026-11-03 決定）

画面（WebView）とコアは、Tauri コマンドとイベントでつなぐ（2章）。コードは `src-tauri/src/`（入口は `AppCore`）と、画面の `src/lib/core.ts`。

- **コマンド**：画面の操作（ボードの取得、項目の追加・保存（本文・完了と解消・解消メモを変えた欄だけまとめて。4.1「自動保存」）・削除と取り消し・並べ替え・分割、ノート・振り返りの読み書き、ノートの行送りと送信済みの印（データモデル設計書 3章 note_send。行送りは本文の保存を兼ね、版が古ければ何も書かずに最新を返す）、入力中の状態の知らせ、Markdown 書き出し（6.4）、検索パレットの全文検索（`search`。データモデル設計書 4.1、画面設計書 6章）、ふりかえりの週・記録のある日・選んだ日のプレビュー（`get_archive`。コアの `domain::archive` を同じ時点で読む。画面設計書 9章））を、コアのドメイン層の関数をそのまま呼ぶコマンドにする。どれも非同期のコマンドにして、データベースの読み書きは止めてよいスレッドで行う（Tauri は同期のコマンドを画面のスレッドで動かすため）。データベースの接続は1つで、読み書きは1つずつ順に行う。
- **設定と、動いている間の保存先の操作**（2026-11-04 決定。設定画面 S-05。画面設計書 7章）：
  - 設定は、コアのドメイン層 `domain::settings` が型（`Settings`・`SettingsPatch`）にまとめる。`get_settings` は既定値を当てた後の設定を、`save_settings` は変える欄だけを受け取って保存し、保存後の設定を返す。誤った値（凪メーターの始業が終業より前でない・フォントサイズが 13〜19 でない・見直しの回数が 1 未満・`HH:MM` でない時刻）は、何も書かずに `invalid_argument`（データモデル設計書 3章 setting）。書き込みは画面の操作（`ScreenWrite::Operation`）として扱い（保存の失敗中を始め・終えない）、`changed` は出さない（設定は項目・ノートなどのデータではなく、画面が自分で当てる。出すと、入力中の画面がボードと件数を読み直す）。日付の切り替わり時刻を変えたときは、すぐに今日を求め直す（`check_today`。30 秒の確かめを待たない）。
  - 保存先の変更（`change_data_dir`）・既存のフォルダの選び直し（`use_data_dir`）・バックアップからの復元（`restore_backup`）は、データベースを開いたまま画面が動いている間に行う。状態は「開いた」のまま変えず、`startup` も知らせない（画面が外枠を消して入力中の内容を失わないように）。データベースを使う間は `AppCore` のロックを持ち続け、ほかのコマンドは終わるまで待つ（失敗しない）。定期バックアップとは重ねない（作っている途中のものを待ってから始め、最中は新しく始めない。6.2）。保存先の変更と選び直しは、`yunagi.lock` を離さずにデータベースを閉じ（4.2）、コアの `change_data_dir`・`use_existing_data_dir` を行ってから、同じロックで開き直す（開き直せなかったときだけ、開けなかった状態を `startup` で知らせる）。復元は開いているデータベースのまま `restore_backup` を行う。使えない保存先・バックアップは、何も変えずに `rejected`（理由は起動時の操作の理由に、保存先の変更の理由 `same_directory`・`inside_backups`・`target_has_data` を足したもの）を返す。選び直しと復元は中身が別のデータになるので、画面は実行する前にまだ保存していない入力を送り、成功したら読み込み直す。
  - ほかに、いまの保存先を返す `get_data_dir` と、保存先の候補がクラウド同期フォルダと判定できるかを返す `check_data_dir`（判定のみ。何も変えない）。
  - フォルダを選ぶ OS のダイアログは、Tauri のダイアログのプラグイン（`tauri-plugin-dialog`。権限は `dialog:allow-open` だけ）を画面から使う（コアは通さない）。選んだフォルダは、上のコマンドに絶対パスで渡す。
- **依頼文の書き出し**（2026-11-05 決定。YUN-70。Mod+Shift+A。操作仕様書 2章、CLI・MCP 仕様書 5章）：コマンド `copy_handoff`（`id`）が、コアの `domain::handoff::build`（権限は確かめない画面の入り口。読み取りだけで、change_log にも `changed` にも触れない）で選んだ TODO の依頼文を作り、クリップボードに書く。クリップボードへの書き込みは Rust 側だけで行う（Tauri のプラグイン `tauri-plugin-clipboard-manager` の Rust の API。`src-tauri/src/clipboard.rs`）。画面（WebView）には、プラグインの JavaScript の API も権限（`capabilities/default.json` の `clipboard-manager:*`）も渡さない。依頼文を作るコマンドを待ってから画面で `navigator.clipboard` に書くと、キー操作の後という扱いが待つ間に切れ、WebKit 系（macOS の WKWebView、Linux の WebKitGTK）で断られうるため。画面が任意の文を書いたり、クリップボードを読んだりできないようにするためでもある。プラグインを入れられなくても（`global_shortcut` と同じ）アプリは起動し、書き込みだけが `clipboard_failed` になる。項目が無ければ `not_found`、障害の ID なら `invalid_argument`（`wrong_kind`）。
- **エージェントの管理**（2026-11-05 決定。YUN-81。設定のエージェント区分と変更履歴 S-06。画面設計書 7・8章、CLI・MCP 仕様書 7.4）：`list_agents`・`set_agent_scopes`・`remove_agent`・`api_status`・`list_changes`・`preview_revert`・`revert_change`・`mark_changes_seen`。画面はローカル API（トークンとソケットで同じ利用者の別プロセスを受ける口。4.6）を通さず、同じコアの `domain::agent_admin`・`domain::history` を直接呼ぶ。書き込みは `AppCore::admin_write`：画面の状態（入力中・保存の失敗中。`ScreenState`）を取り消しに渡し、変えたら `changed`（`by: agent`）を出す。画面の保存の失敗中は、画面の保存ではないので始め・終えない。
- **自動更新**（2026-11-05 決定。YUN-83。ビルド・配布手順書 5章、画面設計書 3章）：`get_update_state`（現在の状態）・`install_update`（「更新して再起動」）と、イベント `update-state`（状態が変わったとき。`none`・`available`・`downloading`・`failed`・`restarting`）。確認と入れ替えは Rust 側だけ（`src-tauri/src/updater.rs`。Tauri のプラグイン `tauri-plugin-updater` の Rust の API）で、画面にプラグインの JavaScript の API と権限（`updater:*`）は渡さない（クリップボードと同じ。画面から配布元や公開鍵を指定できないようにするため）。通信は `Backend` の後ろに置き、試験は偽物を使う（更新の自動確認が無効・設定が空・データベースを開く前は通信しないことを確かめる）。有効かは確認のたびにデータベースから読み直し、`save_settings` が `update_check` を変えたら確認のスレッドを起こす。入れ替えの前にデータベースを閉じ（`AppCore::close`）、入れ替えが済んだら（失敗しても）再起動する。プラグインを入れられなくても（`global_shortcut` と同じ）アプリは起動する。
- **受け渡す型**：コアの型をそのまま渡さず、アプリのクレートに画面向けの型を置く（名前は camelCase、ID と論理日付は文字列、時刻は UNIX 時刻のミリ秒）。コアの型は CLI・MCP とも共有するので、画面の都合を持ち込まないため。TypeScript の定義は ts-rs で Rust の型から作り、`src/lib/bindings.ts` に置く。置いたものが Rust の型と食い違うと `pnpm check` が失敗する（作り直し方は README）。失敗は `kind` で見分ける形で返し、画面に出す文は画面が `kind` から決める（README「エラーの表示」）。
- **イベント**：コアは、データを実際に変えた書き込みの後に `changed`（変えたものが画面かエージェントか）を出す。画面は表示中のデータを読み込み直す（4章 6）。画面自身の保存の後にも出す（行き違いの判定（4.1）で記録が変わることがあるため）。何も変えなかった書き込み（同じ本文の保存など）では出さない。ほかに、データベースを開く処理の状態が変わったとき `startup`、今日の論理日付が変わったとき `today-changed`、定期バックアップを作れなかったとき `backup-failed` を出す。エージェント・CLI の書き込み（ローカル API。4.6）も、画面と同じ `changed` を出す。入口は `AppCore::agent_write` と同じ作りの `AppCore::api_write`（ローカル API 用。データベースを使うのを待つのが最大 5 秒で、超えたら `busy` にする点だけが違う。4.4）。
- **入力中の状態**：画面は、入力中の項目の欄と、ノート・振り返りの守る行（4.1）を、変わるたびに全体を知らせ直す（`report_ui_state`）。コマンドはそれぞれ別のスレッドで処理され、続けて送ると届く順が入れ替わりうるので、知らせには画面の読み込みごとの印と、送るたびに増える番号を添え、コアは同じ読み込みの古い知らせを捨てる。コアはこれを `UiState` としてエージェントの書き込みの判定に渡す（守る行の判定はコアの `domain::text_doc::edit_note`。守る行への書き換え・削除・移動と、知らせた版が古いときに `user_editing`。ほかの行を動かして守る行の番号がずれるだけの操作は受け付ける。守る行の本文を変えない書き換えも、項目の本文と同じく入力中を先に確かめて `user_editing`）。「保存に失敗している間」（4.1）は画面から知らせず、コアが画面の保存の結果から決める：保存の書き込みが失敗したら（保存先の問題。引数の誤りなど保存先に関係なく失敗したものは数えない）始まり、次に保存が成功したら終わる。ここでの保存は、利用者が入力・選んだ内容の書き込み（項目の追加・本文・状態・解消メモ・分割、ノート・振り返り）で、画面が失敗したら内容を持ったまま再試行するもの（画面設計書 3章）。ノートの行送りは本文の保存を兼ねるので、保存として数える（行送りそのものは送り直さないが、本文はふだんの自動保存が内容を持ったまま再試行する。2026-11-03 決定）。削除・削除の取り消し・並べ替えと、持ち越しの確定・後回し・再表示の記録（画面設計書 5章。失敗は画面に出して利用者が選び直す）は、成功しても失敗しても数えない（再試行を待つ入力ではなく、成功で保存の失敗中を終えると、まだ保存できていない入力があるのにエージェントの書き込みを受け付けてしまうため）。
- **起動**：アプリは起動するとすぐ窓を出し、データベースは別のスレッドで開く（`yunagi.lock` を最大 5 秒待つため。4.2）。画面は `startup` を聞き始めてから状態を問い合わせる（その間に開き終わっても取りこぼさないため）。状態は「開いている途中」「開いた」「戻した」（起動時にバックアップから戻して開いた。退避した前のデータベースの場所を持ち、画面が `acknowledge_restore` で確かめたと知らせるまで続く。画面を読み込み直しても場所を示せるよう、コアが持つ。開いているので、コマンドは使える）「見つからない」（6.3 の情報を持つ）「開けなかった」（理由の種類とログ用の文）。開くまでの間、データベースを使うコマンドは `not_ready` を返す。画面の見せ方は画面設計書 10.1。
  - 開けなかった理由（2026-11-03 決定）：既定ディレクトリを使えない（`default_dir`）、ロックが 5 秒で取れない（`lock_busy`）・開けない（`lock`）、`config.json` が壊れている（`config`）、新しく作る場所にデータベースがある（`already_exists`）、マイグレーションに失敗して適用前に戻した（`migration_failed`）・戻すことにも失敗した（`migration_restore_failed`）、新しい版で作られた（`unsupported_schema`）、壊れている（`corrupted`：マイグレーション前のバックアップの整合性が通らないときと、SQLite が「壊れている」「データベースでない」と答えたとき。6.2）、そのほか（`storage`）。あわせて、開こうとした `yunagi.db`、マイグレーション前のバックアップ（マイグレーションの失敗のとき）、`config.json`（`config` のとき）のパスを返す。
  - 起動時の操作（2026-11-03 決定）：見つからない・開けなかったときにもう一度開く（`retry_open`）、見つからないときに新しく作る（`create_database`）・データベースのある既存のフォルダを保存先に選び直す（`choose_data_dir`。6章「保存先の選び直し」）、見つからない・壊れていて開けないときにバックアップで置き換えて開く（`restore_at_startup`。6.2「開けないデータベースからの回復」。成功すると「戻した」になる）、戻した結果を確かめた（`acknowledge_restore`。「開いた」にする）、バックアップの一覧（`list_backups`。開いた後と、保存先が分かっている間に使える）。どれも状態が合わなければ `invalid_state` を返し、行っている間は開いている途中にして、ほかの起動時の操作を断る。選んだフォルダ・バックアップを使えないときは、何も変えずに `rejected`（理由：パスの形の誤り・フォルダが無い・`yunagi.db` が無い・読めない・壊れている・Yunagi のデータベースでない・新しい版のもの）を返し、状態は元のまま（開き直して求め直す）。ロックが取れないなど、選び直す・戻す前に止まったときは `not_ready`（状態は `startup` で届く）。戻す途中で失敗し、退避した前のデータベースを元の場所に戻すこともできなかったときは、退避した場所を持つ `put_back_failed` を返す（画面がその場所を示せるように）。結果の状態は `startup` で届く。
- **日付の切り替わり**：アプリは 30 秒ごとに今日の論理日付を求め直し（設定の切り替わり時刻も読み直す）、変わっていれば `today-changed` を出して、その日の定期バックアップを作る（6.2）。切り替わりを知るのは最大 30 秒遅れる。端末のタイムゾーンを求められないときは UTC で扱う。

### 4.4 CLI・MCP の接続の手順と、ロックが取れないとき（2026-11-04 決定）

CLI と MCP サーバーが、ローカル API と直接モード（4章 2）のどちらで処理するかを決める手順。アプリが動いている間はアプリがロックを持つので、直接モードの CLI・MCP はロックを取れない。そのため、ローカル API が先で、ロックを取るのは API が無いときだけにする（4章 3）。コードは `crates/cli` の共通の部品（接続。`src/connect.rs` の `Connector`。操作ごとに `Connector::call` を呼ぶ）に置き、CLI と `yunagi mcp`（同じバイナリ）が同じものを使う（YUN-90 で作った。`crates/cli` は `lib.rs` と `main.rs` に分け、試験が同じプロセスの中で動かせるようにしている）。直接モードで操作を処理する部分（引数を読み、コアの入口を呼び、05 の JSON とエラーにする）は、アプリの待ち受けと同じものを使うよう `yunagi-api` の `ops` に置いた（4.6）ので、どちらの経路でも応答は食い違わない。コアは接続の方式を知らないままにする（ロックの関数 `DbLock::acquire` を `wait` を 0 にして呼ぶだけで足りる）。

**アプリの側の決まり（ローカル API の待ち受け）**

- 待ち受けるのは、アプリがロックを持っていて、データベースを開き終えている間だけにする（`Slot::Open`）。ロックを取ってから開き終えるまで（マイグレーション中）は待ち受けず、ロックを離すとき（開けなかった・見つからないなどでロックを離す状態）は、離す前に止める。これで、API が答えている間は必ずアプリがロックを持つ（API とほかの直接モードが同時にデータベースを書かない）。見つからない・開けなかった状態（6.3、4.3「起動」）ではアプリはロックを持たないので、CLI・MCP は直接モードで処理し、直接モードの決まり（6.3 の `storage_unavailable`）に従う。
- 保存先の変更・選び直し・復元で、データベースを開き直している間（ロックは持ったまま。4.3）は待ち受けを止めず、依頼を `AppCore` の中で待たせる。ただし待たせるのは最大 5 秒（`DEFAULT_LOCK_WAIT`）までで、それでも始められなければ、何も反映せずにアプリが `busy`（CLI・MCP 仕様書 4.3）を返す。復元などが長引いても、接続したクライアントが応答なしで待ち続けず、エージェントの側の時間切れによる送り直しで書き込みが二重にならないため。
- 待ち受けを止める（ロックを離す前、アプリの終了）ときは、新しい接続を受け付けなくしてから（ソケットのファイルをすぐ消す。新しいクライアントは「待ち受けが無い」と分かり、手順 2 へ進む）、依頼をまだ受け取っていない接続はすぐ閉じ、処理中の依頼を最後まで行って応答を返し、その後に接続を閉じる。応答の前に閉じると、書き込みが済んでいるのにクライアントが `result_unknown` を受け取るため。止め始めた後に届いた依頼は、始めずに `busy` で断る（何も反映していない）。異常終了のときだけは応答が返らず、クライアントは `result_unknown` になる。順は 4.6。
- 異常終了で残ったソケットのファイルは、ロックを持つアプリだけが消して作り直す。ほかのプロセスは消さない。認証のトークンは、待ち受けを始めるたびに作り直し、ソケットより先に書く。ソケット・パイプの名前、トークンのファイル名と形式、プロトコル、止める順、状態の口は 4.6（2026-11-04 決定。YUN-89）。
- 保存先の変更・選び直し・復元で、データベースを開き直せずに開けなかった状態へ移るとき（ロックが離れるとき）は、離れた直後に待ち受けを止める（`AppCore::with_database_closed`）。開き直す関数の中でロックが離れるので、離す前には止められない。その間に届いた依頼は、データベースが開いていないので、何も反映せず `busy` で終わる（API が答える間は、アプリがロックを持つという約束は、依頼がデータベースに触れないことで守る）。

**クライアントの手順（操作ごと。接続を使い回さない）**

次を、最大 5 秒（`DEFAULT_LOCK_WAIT`）、50 ミリ秒ごとに繰り返す。

1. ローカル API に接続して認証する。結果で次に進む。
   - つながった：以後の操作をこの接続で行い、直接モードには戻らない。ロックは取らず、待たない。権限などの判定の結果（`permission_denied` など）は、そのまま返す。
   - 待ち受けが無い：ソケット（パイプ）のファイルが無い、`ECONNREFUSED`（異常終了で残ったソケット）、Windows でパイプが無い。2 に進む。macOS では待ち行列が満杯のときも `ECONNREFUSED` が返るが、そのときはアプリがロックを持っているので 2 で取れず、1 に戻って試し直すため、結果は同じ。ただし `doctor` は macOS ではこの区別がつかず、`listener_busy` でなく `starting_or_unresponsive` になりうる。
   - 1 回の接続と認証には、期限の残りと 1 秒の短いほうまでしか待たない。接続を受けても認証に答えない（固まっている）ときは、まだ何も送っていないので、一時的につながらないものとして次の繰り返しで試し直し、期限で `busy` にする。
   - 待ち受けはあるが一時的につながらない：Windows でパイプが全部ふさがっている（`ERROR_PIPE_BUSY`）、UNIX ソケットの待ち行列が満杯（`EAGAIN`）、割り込まれた（`EINTR`）、接続が時間切れ（`ETIMEDOUT`）。直接モードには切り替えず（アプリはいるため）、次の繰り返しで試し直す。期限までつながらなければ `busy`。
   - 待ち受けはあるが使えない：認証の失敗、プロトコルの版の不一致、権限が無い（`EACCES`）。直接モードには切り替えず、`api_error`（CLI・MCP 仕様書 4.3）を返す。アプリはそこにいて、ロックを持っているため、切り替えても必ず待たされて `busy` になるだけで、原因（トークン・版・権限）が隠れるため。
2. `yunagi.lock` を `wait` 0 で取ってみる（1回だけ試す）。取れたら直接モード（4章 2）で処理する。取れなければ、期限（5 秒）までなら 50 ミリ秒待って 1 に戻り、期限を過ぎていたら `busy`（CLI・MCP 仕様書 4.3）を返す。

- 待つ間に 1 を試し直すのは、アプリの起動中（ロックを取ってからデータベースを開き終えるまで）に操作が届いたとき、開き終わり次第そちらへ切り替えるため。ロックだけを 5 秒待ち、最後に1回だけ API を試す形にすると、アプリが開き終わっても 5 秒たつまで切り替わらず、また、API を試した直後にアプリが起動すると、API もロックも取れずに失敗する。
- `busy` は、操作を何も反映していない（ロックを取れず API にもつながらなかった、またはアプリが始められないと断った）ことを意味する。CLI・MCP のどちらでも、同じ操作（`add_todo`・`append_note` などの追加を含む）をそのままやり直してよい。続くときは、アプリを再起動するよう利用者に頼む。原因は、アプリが起動してデータベースを開くのに 5 秒を超えた（マイグレーションなど）、ほかの直接モードの操作が長引いている、アプリの待ち受けが動いていない、のどれか。クライアントからは見分けられない。
- 逆に、直接モードの CLI・MCP がロックを持っている間にアプリを起動すると、アプリは最大 5 秒待ち、取れなければ利用者の画面にその旨を出す（4章 4、画面設計書 10.1）。直接モードの操作は短いので、ふつうはこの待ちで済む。
- **ソケットのパスが長すぎるとき**（UNIX 系）：既定ディレクトリの下のソケットのパスが `sun_path` に収まらない（4.6）ときは、アプリは待ち受けを始めない。クライアントは、手順 1 でそれを「待ち受けが無い」として手順 2 に進み、ロックが取れれば直接モードで処理する。ロックが取れない（アプリが動いている）ときは、5 秒待たずに、すぐ `api_error`（`reason: socket_path_too_long`。CLI・MCP 仕様書 4.3）を返す（待っても直らず、`busy` の「再起動して」の案内では直らないため）。判定は共通のクレートの 1 つの関数（`yunagi_api::transport::check_socket_path`）で、アプリとクライアントが同じものを使う。別の場所に置き直すことはしない（既定ディレクトリに置く決まりに反し、クライアントが同じパスを求められなくなるため）。
- **応答の待ち**：依頼を送った後の応答には、クライアントの側で上限を設けない（上の 5 秒の期限は、接続と認証までの話）。上限で切って送り直すと、反映済みの書き込みが二重になるため。待ちの上限はアプリ側が持ち（開き直し中は、アプリが依頼を受け取ってから 5 秒。4.4 の「アプリの側の決まり」）、ふつうの操作は短い。エージェントの道具の側が時間切れにして送り直すことは防げないが、`busy` のとき以外に送り直さないよう、エラーの文で伝える。
- **API に送った後の失敗**：依頼を送った後、応答を受け取る前に接続が切れた（アプリが終了した・異常終了した）ときは、書き込みは反映されたかが分からない。直接モードへ送り直さず、`api_error`（`reason: result_unknown`）を返す。`add_todo`・`append_note` などは、送り直すと二重になるため。読み取りは何も変えないので、1 の手順から1回だけやり直してよい。依頼を送る前の接続の失敗は、送っていないので、1 の結果の扱いに従う。
- 接続の手順は、ローカル API が要る操作だけの `yunagi show`（直接モードが無い。アプリを前面に出す操作なので。アプリが動いていないときは起動する。CLI 仕様書 3.3。2026-11-04 決定。YUN-88）には使わない。`yunagi show` は、手順 1 の接続の試し方（`HelloError` の扱い）だけを同じにして、ロックは取らない。待ち受けが無ければアプリを起動し、起動した後は待ち受けが開くまで最大 30 秒（データベースを開くのにかかる時間を見込む。手順の 5 秒とは別）試し直す。`yunagi doctor` は、同じ接続の試し方で状態だけを調べる。ロックを待たず、一時的につながらないときだけ 1 秒まで試し直す（CLI・MCP 仕様書 3.1）。ロックは取ってすぐ離す。
- 既定ディレクトリは、アプリと CLI・MCP が同じものを使う前提（6章）。環境変数で違う場所を指していると、API もロックも別のものになり、同時に別々のデータベースを開く。この検出と扱いは 4.5 で決めた。直接モードに入る前（手順 2 のロックを取れたとき、または既定ディレクトリが無くて取れなかったとき）に、操作ごとに1回だけ、4.5 の別の候補を調べる。
- **直接モードの細部**（2026-11-04 決定。YUN-90）：直接モードで開くのは、自分の保存先にデータベースがあるときだけにする。ロックが取れても、保存先に `yunagi.db` が無ければ、新しく作らずに `storage_unavailable`（`message` に探した場所と、アプリを開くよう案内。6.3。コアの `Database::open` が「初めて使うとき」に作る動きは、アプリのためのもので、CLI・MCP は使わない）。呼び出し元のクライアントは CLI が `cli`、MCP が `--client` の識別子（無ければ `unknown`）で、アプリ経由と同じく `domain::agent::client_for` で求め、最後に接続した時刻も同じ決まりで更新する（失敗しても続ける）。画面が無いので、守る行などの入力中の判定は働かない（`Agent::without_ui`）。引数の誤り（ID・日付の形、知らない引数）は、接続する前に返す（05 3.2）。

### 4.5 既定ディレクトリのずれ（2026-11-04 決定）

既定ディレクトリ（6章）は環境変数（Linux は `XDG_DATA_HOME` と `HOME`、macOS は `HOME`、Windows は `LOCALAPPDATA`）から求める。アプリと、エージェントが起動する CLI・MCP で環境変数が違うと、既定ディレクトリが別の場所になる。ローカル API（ソケット・トークン）・`yunagi.lock`・`config.json` は、どれも既定ディレクトリにあるので、すべてが別々になる。CLI・MCP はアプリに届かず、ロックも別のファイルになり、直接モードで別のデータベースを開く。

困るのは次の2つ。どちらも、そのままでは利用者もエージェントも気づけない。

- ずれた先に別のデータベースがある：エージェントが、利用者の画面にあるものと別のデータに書く。
- ずれた先の `config.json` が、アプリと同じ保存先（`data_dir`）を指している：アプリと CLI・MCP が別のロックを取るので、排他が効かず、同じデータベースに同時に書く（マイグレーションや保存先の変更の最中も含む）。

CLI・MCP は、データベースを新しく作らない（6.3）ので、ずれた先にデータが無いときは、今でも `storage_unavailable` で止まる。

**検出の方法**：クライアントは、アプリの環境変数を知る手段が無い。アプリの既定ディレクトリを `config.json` などに書き残すこともしない（6章。絶対パスを書くと、既定ディレクトリごと移したときに古い場所を指すため）。そこで、環境変数に頼らず OS に尋ねた標準の場所を「別の候補」として調べ、そこにアプリがいるかを見る。

- **別の候補**：環境変数を見ずに、OS が答える場所から求めた既定ディレクトリ。macOS・Linux はパスワードデータベースのホーム（`getpwuid`。`$HOME` ではない）から、macOS は `<ホーム>/Library/Application Support/Yunagi`、Linux は `<ホーム>/.local/share/yunagi`。Windows は既知のフォルダの API で求める LocalAppData（`FOLDERID_LocalAppData`）の下の `Yunagi`。自分の既定ディレクトリと実体（シンボリックリンクを辿ったもの）が同じなら、ずれていないので、候補にしない。候補は最大1つ。
  - 見つけられるのは、アプリが標準の場所で動き、クライアントの環境変数がそれを変えている向き（`XDG_DATA_HOME`・`HOME`・`LOCALAPPDATA` を上書きしている）。逆向き（アプリのほうが環境変数で標準の場所から外れている）は、クライアントからはアプリの場所を知る手段が無いので、候補にできない。その場合は、自分の既定ディレクトリが無い（アプリは起動時に作る。6章）か、データが無いので、下の `storage_unavailable` の案内で気づけるようにする。ただし、その場所に以前の古いデータベースが残っていると、気づけずにそれを開く。この向きは、検出できないものとして残す（アプリを起動する環境とエージェントを起動する環境で、同じ環境変数を使う決まりで防ぐ。下記）。アプリの既定ディレクトリを標準の場所に目印のファイルとして書き残して検出する案は採らない：目印は既定ディレクトリごと移した後も古いまま残り、どのクライアントも古さに気づけず、利用者の標準の場所に Yunagi がファイルを増やすため。`agent setup` が登録する Codex の `env_vars`（05 6章）は、値ではなく環境変数の名前だけを書くので、絶対パスは残らない。値を書く例外（引き継がないと確かめたエージェントで、名前の転送ができないときだけ。いまは該当なし）も、書き残す先がエージェントの設定で、再実行で更新でき、確認の表示に出るので事情が違う。
  - アプリが動いていても、データベースを開いていない間（見つからない・開けなかった状態。4.4）は、ロックを持たず待ち受けもしないので、この方法では「使っているプロセスがいる」と分からない。その間にずれた先の直接モードが動くと、別のデータベースに書きうる。検出できないものとして残し、`doctor` が別の候補の `has_data` を示すことで手がかりにする。
  - パスワードデータベースのホームは、コンテナやサンドボックスで `HOME` を別の場所にしている環境では、本来の利用者の標準の場所を指す。その候補でアプリが動いていれば、ずれの検出として意図どおりに働く。止まるのは、自分の側に使えるデータベースが無い、または同じ保存先を指しているときだけ（下の 2）。前者は、ずれを検出しなくても `storage_unavailable` で止まる場面なので、止まること自体は変わらず、原因を環境変数のずれとして示せるぶん、案内が正確になる。自分の側に別のデータベースがあれば止まらない（下の 3）。止めない設定は設けない。
- **調べ方**（読むだけ。候補の場所にはフォルダもファイルも作らない）：コアに、候補専用の調べる関数を新しく作る（`DbLock::acquire` は `create(true)` でファイルを作るので使わない）。候補の `yunagi.lock` を、作らずに既存のものだけ読み書きの形で開き、`wait` 0 で取ってみる（Windows の `LockFileEx` は読みか書きで開いたファイルにしか使えないため）。取れなければ「その場所を使っているプロセスがいる」とする（アプリか、直接モードの操作か。区別しない）。取れたらすぐ離す。ファイルが無ければ「無い」。開けない・調べられない（権限が無いなど）ときは、エラーにも「いる」にもせず「調べられない」とし、ずれの判定には使わず、`doctor` にだけ出す（調べられないために、使えている直接モードを止めないため）。ソケットには接続しない（接続の仕様は YUN-89 だが、ロックを見れば足り、候補のトークンを読まずに済む）。あわせて、候補の `config.json` の `data_dir`（無ければ候補そのもの）と `yunagi.db` の有無を、読み取りだけで調べる。共通の部品としてコア（`storage::dir_mismatch`）に置き、CLI・MCP・`doctor`・`agent setup` が同じものを使う（YUN-90 で作った）。部品は次の 4 つ：`alternative`（別の候補を求める。OS にホームを尋ねる部分は引数で差し替えられ、試験は本物のホームを調べずに一時フォルダで確かめる。配布するビルドで効く隠しの環境変数は設けない。「止めない設定は設けない」と同じ）、`Candidate::probe`（調べる）、`own_storage`（自分の保存先に使えるデータベースがあるか）、`judge`（下の判定）。どの環境変数から求めたかの名前は `default_dir_vars`。候補は `DefaultDir` にしない（`default_dir` でしか作れない型のため。候補の `config.json` は専用の読み取りで読む）。自分の既定ディレクトリでは、従来どおり `DbLock::acquire` で `yunagi.lock` を取る（フォルダがあれば、ファイルはできてよい）。
  - ロックファイルは本人だけが読み書きできる権限（0600）で作るので、同じ利用者なら開ける。別の利用者のものなど開けない場合は「調べられない」になり、ずれは検出されない（直接モードでは、その利用者の自分の既定ディレクトリで動く）。
  - 調べるために候補のロックを一瞬取っても、アプリの側は影響を受けない。アプリがロックを取るときは 50 ミリ秒ごとに最大 5 秒取り直す（4.2）ので、調べと重なっても取れる。

**判定と扱い**（4.4 の手順 2。直接モードに入る前に、操作ごとに1回）：

調べるのは、自分の既定ディレクトリで `yunagi.lock` を取れたとき、または既定ディレクトリが無くて取れなかったときだけ。`busy`（アプリか別の直接モードがいる）は自分の既定ディレクトリにプロセスがいるのでずれと関係なく、権限など、フォルダが無い以外の失敗は、調べずに従来の `lock` の失敗として返す（4.3）。調べてからデータベースを開くまでの間にアプリが起動してもよい（調べは最善の努力で、その場合は 4.4 の手順 2 の決めに従う）。判定は次の順（上が先）：

1. 候補が無い、候補を調べられない（`unknown`）、または候補を使っているプロセスがいない：ずれとは扱わず、従来どおり（直接モードで処理する。データが無ければ `storage_unavailable`）。候補にデータがあるだけで、使っているプロセスがいないときは、何も言わない（アプリを閉じている間は、ふつうの状態であるため）。`doctor` にだけ出す（05 3.1）。
2. 候補を使っているプロセスがいて、次のどちらかに当たる：エラー `api_error`（`reason: default_dir_mismatch`、終了コード 8。05 4.3）を返す。ロックは離し、データベースを開かず、何も書かない。直接モードへは切り替えない（切り替えると、利用者の画面と別のデータを読み書きするため）。
   - 自分の保存先に、使えるデータベースが無い。ここでの自分の保存先は、自分の既定ディレクトリの `config.json` から求めた `data_dir`（無ければ既定ディレクトリそのもの）で、`yunagi.db` が無い、または既定ディレクトリが無くて求められない場合。
   - 自分の保存先が、候補の保存先と同じ（実体が同じ）。
3. 候補を使っているプロセスがいて、自分の保存先（上と同じ意味）に別のデータベースがある（2 のどちらにも当たらない）：開発用と普段用を分けるなど、利用者が意図して環境を分けている形なので、止めない。直接モードで続け、警告を1行出す（CLI は標準エラー、MCP サーバーは標準エラーのログに、プロセスごとに1回）。
4. 自分の既定ディレクトリが無く、2 にも当たらない（候補が `unknown` のときを含む。2 が先なので、同じ原因で 2 の `api_error` と 4 の `storage_unavailable` が割れるのは、調べられるかどうかによる）：`storage_unavailable`（6.3 と同じ扱い）。`message` に、探した既定ディレクトリと、それを求めた環境変数の名前を書き、アプリを別の環境変数で起動していないか確かめるよう案内する。CLI・MCP は既定ディレクトリを作らない（作るのはアプリだけ。6章）。ロックの関数が「フォルダは呼び出し側が用意する」（4.2）ので、フォルダが無いときのロックの失敗は、この扱いにそろえる。

- `default_dir_mismatch` を `busy` にしないのは、環境をそろえるまで何度送り直しても直らないため（`busy` だけが再試行の対象。05 4.1）。何も反映していないので、やり直しても二重にはならないが、直るまでは送り直さず、利用者に伝える。ただし、候補を使っているのがアプリでなく別の直接モードの操作（短い）だけのこともあるので（調べでは区別しない）、`message` に「アプリが動いていないときは、同じ操作をやり直してよい」と添える。
- 警告（3）は、CLI では呼び出しごとに標準エラーへ1行出る。環境を分けて使う利用者には繰り返し出るが、標準出力と `--json` の出力は変えず、データを壊さないため、これを許す。
- エージェントが起動する CLI・MCP の環境変数は、エージェントの設定（05 6章）で決まる。`agent setup` が登録するコマンドには、既定ディレクトリの環境変数の値を含めない（05 6章）。Claude Code は既定でシェルの環境を引き継ぐ（Linux の実機で確かめた。2026-11-04、YUN-93）ので何も足さず、Codex は既定では `XDG_DATA_HOME` を引き継がない（実機で確かめた）ので、値ではなく環境変数の名前を転送する指定（`env_vars`）だけを書く（05 6章）。例外として、Claude Code を `CLAUDE_CODE_MCP_ALLOWLIST_ENV=1` または `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` で起動すると、`HOME` は渡るが `XDG_DATA_HOME` は渡らない（Linux の実機。05 6章）。アプリが `XDG_DATA_HOME` で標準外の場所を使っていると、これは上の「検出できない向き」になる。`agent setup` は、Linux で `XDG_DATA_HOME` が設定されているとき、変更内容の表示に注意を添える。
- 環境変数をそろえる手段として、既定ディレクトリを直接指定する専用の環境変数は設けない。設けると、アプリと CLI・MCP のどちらにも設定が要り、ずれる場所が増えるため。利用者は、アプリを起動する環境とエージェントを起動する環境で、同じ `XDG_DATA_HOME` を使うようにする（ふつうは、どちらも設定していない標準の場所のまま使う）。
- アプリ自身は、ずれを調べない（クライアントがいつ・どの環境で来るか分からないため）。

### 4.6 ローカル API の方式（2026-11-04 決定）

アプリが待ち受ける入口の作り方。CLI・MCP が接続する手順は 4.4、操作の名前と入出力は CLI・MCP 仕様書 4.4。コードは、共通の取り決めが `crates/api`（`yunagi-api`。通信路・トークン・プロトコル・接続に加えて、操作の引数を読んでコアの入口を呼び、応答とエラーを 05 の JSON にする `ops`。アプリの待ち受けと直接モードの CLI・MCP が同じものを使う）、待ち受けと依頼の受け渡しが `src-tauri/src/api/`（`mod.rs` が待ち受け、`dispatch.rs` が `ops` を `AppCore::api_read`・`api_write` で包む）。ネットワークのポートは開かない（SECURITY.md 4.2）。

**ファイル**（どれも 6章の既定ディレクトリの直下。保存先の設定に関係しない）

| ファイル | 中身 |
| --- | --- |
| `api.sock` | UNIX ドメインソケット（macOS・Linux） |
| `api.token` | 認証のトークン。1 行目がトークン。Windows は 2 行目に名前付きパイプの名前 |

- Windows のパイプの名前は `\\.\pipe\yunagi-<ランダムな 32 桁の 16 進>`。待ち受けを始めるたびに変わり、`api.token` の 2 行目に書く。ほかのプロセスが同じ名前を前もって作って、クライアントが送るトークンを待ち構えられないようにするため。
- `api.token.tmp` は書くときの一時ファイル（4 の書き方）。異常終了で残っても、次に書くときに消す。

**トークン**

- 形：OS の乱数 32 バイトを小文字の 16 進にした 64 文字。待ち受けを始めるたびに作り直す（アプリの起動のたびだけでなく、見つからない・開けなかった状態から開き直して待ち受けを始め直すときも）。
- 書き方：同じフォルダの一時ファイルを、新しく（`create_new`）本人だけが読み書きできる権限（0600）で作って書き、名前を変えて置く。後から権限を変えないので、読める隙間が無い。ソケットを作る前に書く。Windows では権限を明示せず、`%LOCALAPPDATA%` の下の権限（ふつうは本人と管理者・SYSTEM だけ）を引き継ぐ（実機で確かめる。テスト計画書 4.5）。
- 比較：長さは秘密ではないので、違えば先に断る。同じ長さなら全バイトの差をまとめて見る定数時間の比較で、一致までの早さから中身を推し量らせない。外部のクレートは足さない。16 進として読めない値も `auth_failed`。
- トークンをログ・エラーの文・`doctor` の出力に出さない。止めるときに消す（異常終了で残ったファイルは、次の待ち受けの開始で書き換わる）。
- トークンが証明するのは「同じ OS の利用者が読めるファイルを読めた」ことで、どのエージェントかではない（クライアントの識別子は名乗るだけ。下記）。SECURITY.md 4.2 の「防御の境界ではない」と同じ立場。

**UNIX ドメインソケットの権限**（macOS・Linux）

- 守りの境目は、既定ディレクトリが本人だけの権限（0700）であること。アプリは既定ディレクトリを 0700 で作り（6章）、待ち受けを始めるとき、本人以外が入れるなら 0700 に狭める（SECURITY.md 4.1。保存先が既定ディレクトリのままなら、データベースもこの中にある）。狭められなければ待ち受けない。
- ソケットのファイルは、bind の後に 0600 にする（二重の守り）。ソケットの権限だけには頼らない（bind から権限を変えるまでの隙間があり、接続のときにソケットの権限を確かめない OS もあるため）。
- `umask` は変えない（プロセス全体に効き、アプリは複数のスレッドで動くため）。Linux の抽象名前空間のソケットは、ファイルの権限が無く誰でも接続できるので使わない。
- ソケットのパスが `sun_path` に収まらないときは、待ち受けず、理由を状態とログに残す。上限は NUL を除いて 107 バイト（Linux）・103 バイト（macOS）。判定は `yunagi_api::transport::check_socket_path` の 1 か所で、アプリとクライアントが同じものを使う。クライアントの扱いは 4.4「ソケットのパスが長すぎるとき」。

**始める順**（ロックを持ち、データベースを開き終えた直後。`AppCore` が `Slot::Open` にするところ）

1. ソケットのパスの長さを確かめる。2. 既定ディレクトリを 0700 にする。3. トークンを書く。4. 古いソケットを処理する：`symlink_metadata` で見て、ソケットかシンボリックリンクなら消す（ロックを持つのは自分だけなので、相手が生きているかを試さない。シンボリックリンクは指す先に触れず、リンクだけを消す）。ソケットでもシンボリックリンクでもないもの（フォルダ・普通のファイル）なら、消さずに待ち受けない。5. bind する。6. 0600 にする。どこかで失敗したら、書いたトークンも消して待ち受けず、アプリは動き続ける。理由は `AppCore::api_state` と標準エラーに残す。CLI・MCP からは「待ち受けが無い」ように見え、直接モードを試して、取れなければ `busy`（4.4）になる。

**止める順**（アプリの終了、開けなかった状態に移るとき）

1. 新しい接続を受け付けなくし、ソケットのファイルをすぐ消す（新しいクライアントは「待ち受けが無い」と分かる）。止まって待っている accept は、自分に接続して起こす。
2. 依頼をまだ受け取っていない接続は、すぐ閉じる。`hello` の待ちの接続は黙って閉じる。`hello` の後の依頼の待ちの接続（と、依頼の待ちが時間切れになった接続）には、読む側だけを閉じて、何も反映していないことを伝える `busy`（`id` は `null`）を 1 行書いてから閉じる。何も書かずに閉じると、後から依頼を送ったクライアントには「送った後で接続が切れた」ように見えて、反映されたか分からない `result_unknown`（送り直されない）になってしまうため。クライアントは、依頼を組み立て終えてから接続する（標準入力の読み込みなどを、接続の後にしない。YUN-90）。
3. すでに受け取って処理を始めた依頼は、最後まで行って応答を返し、接続を閉じる。止め始めた後に届いた依頼は始めず、`busy` で断る。
4. すべての接続が閉じたら（上限 15 秒。超えたらログに残して続ける）、トークンのファイルを消す。ソケットとトークンのファイルは、自分が作ったもの（ソケットは i-node、トークンは中身が同じ）のときだけ消す。止まるのが遅れて、次のアプリがロックを取り、作り直した後なら、そのファイルを消さない。接続のスレッドが panic しても、登録を消して止める側に知らせる。
5. ここで初めて `yunagi.lock` を離す（`AppCore::close`）。

**Windows の名前付きパイプ**（**実機では未確認**。Linux の開発機では `cargo check --target x86_64-pc-windows-gnu` の型検査までしかできない。確かめる項目はテスト計画書 4.5）

- 権限を明示する。パイプの既定の権限は Everyone と匿名に読み取りを許すので、作った利用者（持ち主）だけにすべてを許す権限の記述（SDDL `D:P(A;;GA;;;OW)`）を付けて作る。リモートからの接続は断る（`PIPE_REJECT_REMOTE_CLIENTS`）。
- 名前の先取りを防ぐ。名前は上のとおり起動のたびにランダムにし、最初の実体は `FILE_FLAG_FIRST_PIPE_INSTANCE` で作る。同じ名前がすでにあれば失敗するので、待ち受けずにログに書く。
- 接続を渡した直後に、次の実体を作る。その間につなぐクライアントは `ERROR_PIPE_BUSY`（4.4 の「一時的につながらない」）になり、試し直す。
- クライアントの確かめ（YUN-90 で作った。実機では未確認）：パイプを開いた後、`hello`（トークンを含む）を送る前に、パイプの持ち主の SID が自分の SID（プロセスのトークンのユーザー）と同じことを確かめる（`GetSecurityInfo` と `EqualSid`）。サーバーはパイプに持ち主を明示しないので、持ち主は作ったプロセスのトークンで決まる（ふつうはユーザー、管理者権限なら既定の持ち主の Administrators）。そのため、クライアントのトークンのユーザーの SID か、トークンの既定の持ち主の SID のどちらかと同じならよい。違えば、何も送らず、`api_error`（`denied`）。持ち主を確かめる操作そのものが失敗したときも、何も送らず、`api_error`（`unexpected`。権限が無いのではないので `denied` にしない）。管理者権限で起動したアプリに、通常の権限のクライアントは `denied` になる（テスト計画書 4.5 の実機の項目⑧。案内は `denied` の `message`）。
- 同期のパイプには読み・書きの時間切れが無いので、見張りのスレッドが期限に `CancelIoEx` で中断する（読みの期限は絶対の時刻で、1 行の読みの間は置き直さない。依頼を読み終えたら外し、書きの間に残った見張りが書きを中断しないようにする）。応答を書いた後は、相手が読み終えるまで待って（`FlushFileBuffers`）から閉じる（待たないと書いたものが捨てられる）。この待ちは別のスレッド（複製したハンドル）で行い、こちらは書きの上限（5 秒）までしか待たない（相手が読まずに黙っていても接続の枠を塞がない）。

**プロトコル**（JSON-RPC 2.0 を、1 行 1 メッセージの JSON で送る）

- 接続ごとに次の 2 往復だけを行って閉じる（接続を使い回さない。4.4）。(1) クライアントが `hello` を送り、サーバーが答える。(2) クライアントが依頼を 1 つ送り、サーバーが応答を 1 つ返す。まとめての依頼（batch）と、応答の要らない通知（`id` の無い依頼）は受け付けない。
- `hello` の形は版をまたいで変えない（版の食い違いを必ず `hello` で見分けるため）。`params` は `protocol`（クライアントのプロトコルの版）・`token`・`client`（クライアントの識別子。無ければ `unknown`）。確かめる順は、形 → 版 → トークン → 識別子の形。版が違えばトークンを見る前に `api_error`（`reason: version_mismatch`、エラーの中身にアプリの版 `server_protocol`）。トークンが合わなければ `api_error`（`reason: auth_failed`）。通れば `{"protocol": 1, "app_version": "..."}` を返す。通らなかった接続は、失敗を返して閉じる。プロトコルの版は 1 から始め、互換のない変更をするときに上げる。
- 依頼の 1 行の上限は `hello` が 4 KiB、依頼が 4 MiB（ノートの本文が入る大きさ）。超えたら読まずに `INVALID_REQUEST` で閉じる。待つ時間の上限は（1 行の合計の時間。1 バイトずつ送って延ばし続けても超えれば閉じる）、`hello` を受け取るまで 3 秒、`hello` の後に依頼の 1 行を受け取るまで 5 秒、応答を書くのに 5 秒（`ApiOptions`。試験で短くできる）。クライアントは、接続から `hello` の応答までを 1 秒までしか待たない（4.4）。このうち、通信路への接続そのもの（UNIX 系の `connect`）には、標準の関数では時間切れを付けられない。待ち行列が満杯のとき止まって待ちうるので、接続にも 1 秒の上限をかける（`socket2` の非ブロッキングの接続。待ち行列が満杯なら Linux はすぐ `EAGAIN` で失敗し、4.4 の「一時的につながらない」として試し直される。YUN-90 で作った）。`yunagi-api` の `client::connect` は、接続そのものと `hello` の応答までの合計に、上限（期限の残りと 1 秒の短いほう）をかける（`hello` の待ちは、接続に使った時間を引いた残り）。Windows のパイプを開く操作は待たずに返る（全部ふさがっていれば `ERROR_PIPE_BUSY` ですぐ失敗する）ので、接続の上限は使わない。依頼を送った後の応答を待つ時間には上限を設けない（4.4「応答の待ち」）。
- エラー：プロトコルの誤りは JSON-RPC の標準のコード（`-32700` JSON でない、`-32600` 依頼の形が誤り、`-32601` 知らない操作、`-32602` 引数が誤り）。アプリのエラー（CLI・MCP 仕様書 4.3 のコード）は、コード `-32000` の `error.data.error` に、4.3 のオブジェクト（`code`・`reason`・`message` など）をそのまま入れる。MCP サーバーがそのまま返せるようにするため。
- 操作の名前と引数は MCP のツール名・引数にそろえる（CLI・MCP 仕様書 4.4）。`date` は受け取ったまま（`today` など）渡し、アプリが自分の設定とタイムゾーンで論理日付を求める。いま出す操作は、コアの入口が作ってあるものだけ（`get_board`・`open_board`・`get_note`・`search`・`add_todo`・`add_blocker`・`edit_todo`・`edit_blocker`・`complete_todo`・`reopen_todo`・`resolve_blocker`・`append_note`・`append_reflection`・`edit_note`）。`search` も同じ形で足した（コアの入口は `domain::search::search`。YUN-90）。`export_handoff` も同じ形で足した（コアの入口は `domain::handoff::export`。CLI・MCP 仕様書 5章。2026-11-05 決定。YUN-70）。このほかに、窓を前面に出す `show_app`（`yunagi show`。CLI・MCP 仕様書 3.3・4.4。2026-11-04 決定。YUN-88）がある。データの操作ではないので `yunagi_api::ops` ではなく別の部品（`yunagi_api::show`）に置き、`dispatch.rs` が先に名前で分ける（直接モードにも MCP にも無い）。

**コアへの渡し方**

- 読み取りは `AppCore::api_read`、書き込みは `AppCore::api_write`（`agent_write` の API 用。変えたら画面と同じ `changed`（`by: agent`）を出す。何も変えない成功では出さない）を通る。管理の操作（権限の変更・履歴・取り消し。MCP・CLI 仕様書 4.4。MCP には出さない）は、一覧と取り消しの計画も含めて `api_write` を通す（取り消しが画面の入力中・保存の失敗中を見るため。変えないものは `changed` を出さない）。呼び出し元のスコープは確かめない（2026-11-04 決定。YUN-94）。権限・入力中・持ち越しの判定はコアの関数が行う（どの経路でも同じ。4章 5）。
- データベースを使うのを待つのは最大 5 秒（`ApiOptions::db_wait`。`DEFAULT_LOCK_WAIT`）。期限は依頼ごとに 1 回だけ求め、呼び出し元のクライアントを求める処理と操作の本体を、同じ錠を持つ間に行う（錠を 2 回取って待ちが 5 秒を超えないように。`busy` の依頼は、クライアントの登録も反映しない）。書き込む時刻も錠を取った後に求める。待ちは 5 ミリ秒から 50 ミリ秒まで倍々に延ばす取り直し（標準の錠には期限付きの取得が無いため）。保存先の変更・復元の最中はデータベースの錠が長く持たれるので、API の経路だけ、期限付きで取り直す（5 ミリ秒ごと）。超えたら、何も反映せずに `busy`（4.4）。止める側が、処理中の依頼の終わりを待つとき、その依頼が錠を無期限に待っていて止まらない、という行き違いを防ぐ意味もある。データベースを開いていない（`Slot::Open` でない）ときも `busy`。
- 依頼の最初に、呼び出し元のクライアントを求める：識別子が無ければ `unknown`、あれば名前で探し（固定の `cli`・`unknown` を含む）、無ければ `read` だけの権限で登録する（CLI・MCP 仕様書 2章。権限を足すのは利用者）。同時に最後に接続した時刻（`last_seen_at`）を更新するが、前の時刻から 60 秒たっていなければ書かない（読み取りのたびに書き込みを増やさない）。書けなくても依頼を失敗させない（標準エラーに残して続ける。ディスクがいっぱいなどで画面の保存が失敗している間も、読み取りは受け付けるため。`domain::agent::touch_client`）。新しい識別子の登録（`insert`）が失敗したときだけ、`storage_unavailable`。識別子は英小文字・数字で始まる英小文字・数字・`-`・`_`・`.` の 64 文字まで（設定画面と change_log に出るため）。コアの `domain::agent::client_for`（直接モードも同じものを使う）。登録の数には上限（固定の 2 つを含めて 64）を付ける（トークンを持つ相手が名前を変えて登録を増やし続け、設定画面の一覧を使えなくするのを防ぐ）。初めての識別子を登録したときは、読み取りの依頼でも画面に `changed`（`by: agent`）を知らせる（エージェントの一覧が変わるため）。
- 識別子は名乗るだけで、本人であることは確かめない。トークンを読めるプロセスは、どのエージェントの識別子も名乗って、その権限を使える。トークンが証明するのは「同じ OS の利用者」であって、どのエージェントかではない（SECURITY.md 4.2 の「CLI は防御の境界ではない」と同じ立場。スコープの変更と `agent revert` が設定画面か対話端末でしか確定できないのは、この前提のため。CLI・MCP 仕様書 2章）。

**状態の口**

- `AppCore::api_state()`：`Stopped`（待ち受けていない）・`Listening { connections }`（処理中の接続の数）・`Unavailable { reason, detail }`（始められなかった。理由は `SocketPathTooLong`・`PathOccupied`・`PipeNameTaken`・`Other`）。設定画面のエージェント区分の表示がこれを使う。Tauri コマンド `api_status` が、状態の種類（動作中か・始められなかった理由の種類 `cause`・処理中の接続数）だけを画面に渡す（原因の文 `detail` はログ用なので渡さない）。イベントにはせず、画面は設定のエージェント区分を開くたびに問い合わせる（2026-11-05 決定。YUN-81。画面の管理の操作のコマンド一覧は CLI・MCP 仕様書 7.4）。
- 接続は 1 依頼で閉じるので、「接続中のクライアント」の一覧は出さない（常にほとんど空で、トークンを持つ相手に、ほかのクライアントを知らせる理由も無い）。クライアントごとの最後の接続は agent_client の `last_seen_at` を読む。ソケットの操作としては、状態を返す口を設けない。

**確かめ方**：UNIX ドメインソケットの結合試験は `src-tauri/tests/api.rs`（テスト計画書 4.5）、通信路・トークン・行の読み方の単体試験は `crates/api`。Windows の名前付きパイプと macOS のソケットは、型検査（`cargo check --target x86_64-pc-windows-gnu`・`x86_64-apple-darwin`）までで、実機では未確認（テスト計画書 4.5 の実機の項目）。

### 4.7 MCP サーバーの方式（2026-11-04 決定。YUN-92）

`yunagi mcp`（stdio）の作り方。ツールの名前・引数・返り値は CLI・MCP 仕様書 3章・4.2・4.3、MCP としての入出力（握手・結果の包み方・上限）は同 4.5。コードは `crates/cli/src/mcp.rs`（入出力とプロトコル）と `mcp_tools.rs`（ツールの定義）。

- **薄い層にする**：ツールの呼び出しを `Connector::call`（4.4）に渡し、返り値かエラーをそのままツールの結果に載せるだけにする。権限・入力中・持ち越し・変更履歴の判定はコア、ローカル API と直接モードの選び方（`busy`・`api_error`・既定ディレクトリのずれ）は `Connector` が行い、この層では判定し直さない。CLI と MCP は同じ操作の名前と引数（`ops::Call::parse`）を使うので、どちらから呼んでも応答は食い違わない。
- **公式の Rust SDK（`rmcp`）は使わず、自前の JSON-RPC にする**。確かめた日は 2026-11-04（crates.io の最新の安定版は `rmcp` 3.8.0）。理由は 3 つ。(1) `Connector::call` は同期で、待つときは `thread::sleep` で止まる。`rmcp` は非同期（tokio）が前提なので、tokio の実行環境と、同期の呼び出しを別のスレッドへ逃がす橋渡しが要り、これまで tokio を使っていない `yunagi`（CLI）に tokio を持ち込むことになる。(2) 引数の名前と読み方は `ops::Call::parse` が決めている。SDK のマクロでツールの引数の型と JSON スキーマを作ると、同じ決まりが 2 か所に書かれる。(3) 必要なのは `initialize`・`server/discover`・`ping`・`tools/list`・`tools/call` と通知を受けることだけで、小さい。新しい依存を足さないので、版の固定（Cargo.lock の確認）の対象も増えない。サーバーからクライアントへ働きかける機能（進捗・変更の購読 `subscribe_changes` など。05 8章）を足すときは、SDK に替えるかをそのとき決め直す。
- **仕様の版**：MCP の仕様（<https://modelcontextprotocol.io/specification>。2026-11-04 に確かめた）の最新は `2026-07-28` で、`initialize` の握手が無く、リクエストごとに `_meta` で版を送り、`server/discover` を必ず実装する。それ以前（`2025-11-25` まで）は `initialize` から始まる。エージェントがどちらで来るかは実機でしか分からないので、**両方に答える**（接続の状態を持たず、握手の前の `tools/call` も受ける）。細部は 05 4.5。実機のエージェント（Claude Code・Codex）からの接続は未確認で、テスト計画書 4.5 の実機の項目（YUN-87）で、どの版で来るかも含めて確かめる。
- **接続の道具は起動時に 1 つ作る**：環境を分けている形の警告（4.5 の 3）を「プロセスごとに 1 回」にするため。警告と内部の失敗の診断は標準エラーに出す。標準出力には MCP のメッセージ以外を書かない。
- **1 件ずつ順に処理する**：依頼は届いた順に、1 件終わってから次を読む。接続の手順で最大 5 秒待つ間は、`ping` にも答えない（この間エージェントの側の時間切れで待ちきれなくなっても、`busy` は何も反映していない）。同時に複数の依頼を処理する必要は今は無い。
- **終わり方**：標準入力が閉じられたら終了コード 0 で終わる（MCP の stdio の終わらせ方）。起動時の引数の誤り（`--client` の形）は、標準エラーに書いて終了コード 2 で終わる。

**確かめ方**：結合試験は `crates/cli/tests/cli.rs`（`yunagi_cli::run` に標準入力の行を渡す。直接モード・偽のアプリ）と `src-tauri/tests/api.rs`（アプリ経由）、プロトコルとツールの定義の単体試験は `crates/cli/src/mcp.rs`・`mcp_tools.rs`（テスト計画書 4.5）。

## 5. 日付の扱い

「その日」はカレンダー日付ではなく、設定した切り替わり時刻（既定 4:00）を基準とした論理日付で扱う。論理日付の算出はコアのみが行い、CLI・MCP も同じ規則に従う。タイムゾーンは端末の設定に従い、日付ごとに記録時のタイムゾーンを保存する（IANA の名前が取れない環境で記録する形は、データモデル設計書 3章 day）。切り替わり時刻を変更した場合は、変更後に作成するデータにだけ適用し、既存の日付は付け直さない。

論理日付 `D` は、カレンダー日 `D` の切り替わり時刻の瞬間に始まる。壁時計の時刻どうしではなく瞬間で比べ、夏時間の切り替えでも日付が逆戻りしないようにする。切り替わり時刻が夏時間の開始で飛ばされる日（例：2:00〜2:59 が無い日に 2:30）は、飛ばされた後の最初の時刻（3:00）に始まる。切り替わり時刻が夏時間の終了で2回ある日は、1回目に始まる。

## 6. データの保存場所

| OS | 既定のデータディレクトリ |
| --- | --- |
| macOS | `~/Library/Application Support/Yunagi/` |
| Windows | `%LOCALAPPDATA%\Yunagi\` |
| Linux | `$XDG_DATA_HOME/yunagi/`（未設定・空・相対パスのとき `$HOME/.local/share/yunagi/`） |

求める環境変数は、macOS は `HOME`、Windows は `LOCALAPPDATA`、Linux は `XDG_DATA_HOME` と `HOME`（コアの `default_dir`）。値が空のものは未設定として扱い、絶対パスでないものは無視する（XDG Base Directory の決まり）。使う変数が無い（Linux は `XDG_DATA_HOME` も `HOME` も使えない）ときは、既定の場所で代わりにせず、エラーにする（`default_dir`。4.3 の開けなかった理由）。アプリと、エージェントが起動する CLI・MCP で環境変数が違うと、既定ディレクトリが別の場所になる。その検出と扱いは 4.5。

既定ディレクトリは、アプリ本体の配置先とは別にする（アプリ本体の配置先はビルド・配布手順書 2章）。

設定ファイル `config.json`（保存先 `data_dir` を持つ）、ローカル API の認証トークン、ロックファイル `yunagi.lock`、ソケットは、保存先の設定に関係なく常に上記の既定ディレクトリに置く。保存先（`data_dir`）に置くのはデータベースと `backups/` である。アプリは起動時に、既定ディレクトリが無ければ作る（初めて起動したとき。ロックファイルを置くため。UNIX 系では本人だけが入れる権限（0700）で作る。ローカル API のソケットとトークンを置くフォルダで、守りの境目になるため。すでにあるフォルダは、ローカル API の待ち受けを始めるときにゆるければ 0700 に狭める。4.6。保存先のフォルダを作らない決まり（6.3）は、データの置き場所についてのもので、既定ディレクトリには当たらない。2026-11-03 決定）。

保存先は設定で変更できる。変更時はデータベースを安全に移動し、移動先を `config.json` に記録する。自動バックアップは保存先の `backups/` に直近7日分を作成する（6.2）。

- `config.json` が無いとき、または `data_dir` の項目が無いときは、既定ディレクトリを保存先とする。壊れている（JSON として読めない、`data_dir` が絶対パスでない）ときは、既定の保存先で開かずにエラーにする（データが消えたように見え、別の場所に新しいデータベースを作ってしまうため）。このアプリが知らない項目は、書き戻すときに消さない。保存先を既定ディレクトリ（シンボリックリンクを辿った実体どうしで比べる）に戻すときは、`data_dir` の項目を書かずに消す（2026-11-03 決定。既定ディレクトリの絶対パスを書くと、既定ディレクトリごと移したとき（新しい端末への引っ越しなど）に古いパスを指してしまうため。6.3 の「初めて使うとき」の記録をしない理由と同じ）。
- 保存先の変更（2026-11-03 決定）は、データベースと `backups/` を新しい保存先に写してから `config.json` を書き換え、最後に元の保存先のものを消す。データベースは SQLite のオンラインバックアップで写し（WAL にだけある書き込みも含む）、整合性を確かめてから置く。`config.json` を書き換える前に失敗したら、写したものを消して元のまま残す。元のものを消せなかったときは失敗にせず、残ったものを利用者に知らせる。
- 新しい保存先に、すでにデータベースの跡（中身のある `yunagi.db`・`-wal`・`-journal`、`yunagi.db` のシンボリックリンク、調べられないもの。6.3 の「跡」と同じ判定で、コアの1か所にまとめる）か、空でない `backups/` があるときは、上書きせずに断る（2026-11-03 決定。0 バイトのファイルと `-shm` は SQLite が使わない・作り直すので、跡とみなさない）。今の保存先の `backups/` の中も断る（`backups/` を自分の中へ写し続けてしまうため）。`..` を含むパスも断る（まだ無いフォルダを通ると実体を求められず、これらの確認をすり抜けるため）。
- 今の保存先に中身のあるデータベースが無いとき（0 バイトの `yunagi.db`、宛先の無いシンボリックリンクを含む）は、何も変えずに断る（2026-11-03 決定）。移すものが無いのに記録だけを変えると、元の保存先に残った `-wal`（同期の途中で本体がまだ届いていないものなど）を、最後に元のものを消すところで消してしまうため。データベースが見つからないとき（6.3）は、下の「選び直し」か新しく作る（`Database::create`）を使う。
- 保存先の選び直し（2026-11-03 決定）：データベースのある既存のフォルダを、データを移さずに保存先として記録する（コアの `use_existing_data_dir`。6.3 の案内の「保存先を選び直す」）。記録する前に、そのフォルダの `yunagi.db` を開いて中身を確かめ、次のどれかなら何も変えずに断る：フォルダが無い、中身のある `yunagi.db` が無い、SQLite のデータベースとして読めない、整合性の確認（`integrity_check`）が通らない、スキーマの番号が 0（空のデータベースや別のアプリのもの。開くと空の Yunagi のデータベースを作ってしまう）、番号がアプリの知る範囲にない（新しい版で作られたもの）。今の保存先のファイルには触れない。パスの決まり（絶対パス、`..`・`.` を含まない、UTF-8）と既定ディレクトリを選んだときの扱いは、保存先の変更と同じ。確かめるときは、まず読み取り専用で開く（断るときにも、選んだデータベースに書かない。別の端末の新しい版が書いている途中で、`-wal` が同期されているものを書き換えないように）。読み取り専用で開くと SQLite が WAL モードのデータベースの横に空の `-wal`・`-shm` を作ることがあるので、もともと無く、閉じた後も `-wal` が空なら消す（同期フォルダに残さない）。書き込みの途中で止まったデータベース（中身のある `-journal` が残ったもの）は、読み取り専用では SQLite が巻き戻せずに読めず、`Database::open` なら開ける正しいデータベースを断ってしまうので、そのときだけファイルを作らない形の読み書きで開き直す（SQLite が開くときに必ず行う `-journal` の巻き戻しは起きるが、表とスキーマの番号には書かない）。スキーマの番号の範囲は、開く・復元するときと同じ確認を使う。
- 変更・選び直しは `yunagi.lock`（4章）を取り、データベースを閉じてから行う。アプリが動いている間に画面（設定のデータ区分）から行うときは、ロックを離さずにデータベースを閉じ、同じロックで開き直す（4.2・4.3）。

保存先を iCloud Drive・Dropbox などのクラウド同期フォルダにする場合は、同時に1台だけで開く場合に限って使える（SQLite のデータベースと WAL のファイルが別々に同期されると壊れうるため）。同期フォルダと判定できる場合は、設定時に警告を表示する。複数端末で使う場合は、Markdown 書き出しまたはバックアップの同期を推奨する。

### 6.1 アプリの識別子（2026-11-03 決定）

アプリの識別子（bundle identifier。OS がアプリを見分けるための名前）は `io.github.misty-swan.yunagi` とする。`src-tauri/tauri.conf.json` の `identifier` に書く。

- 識別子は macOS のアプリの見分けや、WebView のデータの置き場所などに使われる。公開後に変えると、既存の利用者の環境で別のアプリとして扱われるため、変えない。
- 識別子を決めた時点では公式ドメインが未取得だった。このため、すでに持っている GitHub のアカウント名をもとにした名前にした。公式ドメイン（`getyunagi.com`）を取得した（2026-11-06）後も、識別子は変えない。
- GitHub のアカウント名を変えたり手放したりしても、識別子は変えない。名前空間を他人に取られないよう、アカウント名は変えない運用にする。
- macOS の識別子に使える文字は英数字・ハイフン・ピリオドだけで、下線（`_`）は使えない。このため、アカウント名のハイフンはそのまま使う。Linux の慣習（D-Bus の名前、Flathub）はハイフンを勧めないが、使えないわけではない。Flathub での配布は予定していない（配布物はビルド・配布手順書 2章のとおり）。
- 上のデータディレクトリは識別子ではなく、アプリ名 `Yunagi`（Linux は `yunagi`）で決める。Tauri の保存場所を返す関数（`app_data_dir` など）は識別子でフォルダ名を作るため、データディレクトリを求めるのには使わない。コアの同じ関数を、アプリと CLI の両方が使う。
- Linux では、識別子が画面の窓の名前（Wayland の app_id）になる。install.sh が作るデスクトップエントリのファイル名は、識別子にそろえる（ビルド・配布手順書 4.1）。
- 識別子は、WebView が自分のデータを置くフォルダの名前にも使われる（Linux・Windows は `data_local_dir` の下、macOS は `~/Library/WebKit/` などの下）。このフォルダは上のデータディレクトリとは別の場所にある。OS ごとの場所と、`yunagi uninstall --purge` で消す決まりは 6.5。

### 6.2 自動バックアップと復元（2026-11-03 決定）

保存先の `backups/` には、次の3種類のバックアップを置く。どれも SQLite のオンラインバックアップで写した、`-wal` を伴わない1つのファイルで、設定画面の一覧（画面設計書 7章 S-05 のデータ区分）にまとめて並べ、どれからでも復元できる。

| 種類 | ファイル名 | 作るとき | 残す数 |
| --- | --- | --- | --- |
| 定期 | `daily-<論理日付>-<UNIX 時刻（秒）>.db` | 1日（論理日付）1回 | 日付の新しいものから7つ |
| マイグレーション前 | `pre-migration-v<前>-to-v<後>-<UNIX 時刻（秒）>.db` | マイグレーションの適用前（データモデル設計書 1.1） | 新しいものから3つ |
| 復元前 | `pre-restore-<UNIX 時刻（秒）>.db` | 復元の直前 | 新しいものから3つ |

- 定期バックアップは、コアの「その論理日付の分がまだ無ければ作る」関数（`Database::ensure_daily_backup`）で作る。アプリは、起動してデータベースを開いた直後と、起動中に論理日付が切り替わったとき（4.3）に作る。写して整合性を確かめるのに時間がかかりうる（93 MB のデータベースで 0.5 秒ほど。遅いディスクや同期フォルダではさらにかかる）ので、画面を止めないよう別のスレッドで作る。写すのは開いている接続ではなく、ファイルを別に開いた接続からなので（コアの `Database::daily_backup`）、作っている間も画面の読み書きは待たない。作るのは一度に1つだけ。作れなかったときは、標準エラーに書き、その日に初めて失敗したときだけ画面に `backup-failed` を知らせる（失敗にはせず、次に日付を確かめたとき（30 秒後。4.3）に作り直す。ディスクの空きが戻るなど、一時的な失敗でその日の分が抜けないように。画面での見せ方は画面設計書 3章「上部のバー」の短時間の知らせ）。アプリの終了時は、作っている途中のものを待ってからデータベースを閉じ、ロックを離す（写している途中で CLI・MCP がデータベースを書き換えないように）。保存先の変更と復元はファイルを差し替えるので、定期バックアップと同時に走らせない（2026-11-03 決定）。直接モードの CLI・MCP は呼ばない（操作ごとに写す時間がかかるのを避ける。アプリを開けばその日の分が作られる）。
- 「直近7日分」は、暦の上で7日以内のものではなく、日付の新しい7つとする。アプリを開かない日が続いても、バックアップが全部消えないようにするため。今日より後の日付のもの（時計が進んでいたときに作ったもの）は、いちばん古いものとして扱う（いつまでも枠を占めないように）。
- マイグレーション前のバックアップは、一覧は定期バックアップとそろえるが、世代は別に数える。マイグレーションの後に作る定期バックアップは新しいスキーマになり旧版では開けないので、旧版を再導入したときに戻す先が7日で押し出されないようにするため。マイグレーションのたびに1つ増えるだけなので、3つで足りる。
- 古いものは、定期バックアップを作る関数（作れなかったときも）と復元のたびに消す。復元のときは今日の日付が分からないので、定期には触れない。名前の形に合わないファイル（利用者が置いたものなど）には触れない。作ったばかりのもの（復元前に退避したものなど）は、時計が戻っていて名前の時刻が古く見えても消さない。消せなかったものや、片付けで `backups/` を読めなかったときは失敗にせず、次の機会にまた消す。
- バックアップの置き場所は、データベースを開いたときに渡したパスの横の `backups/` とする（`yunagi.db` がシンボリックリンクでも、マイグレーション前のものと同じフォルダになる）。
- 写している間にほかの接続が書き込んでも、SQLite が写し直すので、ある時点で整合した内容になる。写したものは整合性を確かめ（`integrity_check`）、一時ファイル（`*.db.tmp`）に書いてから名前を変える。中断で残った一時ファイルと、SQLite がその横に作るファイル（`-journal` など）は次に作るときに消す（消せないものは残して続け、一時ファイルには、横のファイルまで含めて空いている名前を選ぶ。写す処理は、すでにあるファイルには書かずに断る）。写すのに失敗したとき（整合性の確認が通らないときを含む）は、作りかけの一時ファイルとその横のファイルを消す。この写し方は3種類のバックアップと保存先の変更（6章）で共通にし、コアの1か所にまとめる（2026-11-03 決定）。
- マイグレーション前のバックアップも、写したものの整合性を確かめる。通らなければ（ふつうは元のデータベースが壊れている）、壊れたバックアップでは失敗したときに戻せないので、マイグレーションを始めずにエラーにする（データベースは適用前のまま。2026-11-03 決定）。整合性が少しでも崩れていると（索引と表の食い違いなど、実害の小さいものでも）新しい版では開けなくなるが、壊れた内容にマイグレーションを重ねるよりよいとする。旧版はそのまま開ける。新しい版では、起動時の画面から、下の「開けないデータベースからの回復」で定期バックアップなどに戻せる（画面の案内は画面設計書 10.1）。
- 開けないデータベースからの回復（2026-11-03 決定）：壊れていて開けないとき（4.3 の `corrupted`）と、見つからないとき（6.3）は、コアの `Database::open_from_backup` で、選んだバックアップで置き換えてから開く（下の復元は開いたデータベースにしか行えないため）。
  - 保存先はロックの `config.json` から求める（`Database::open` と同じ）。保存先のフォルダが無いときと、`yunagi.db` がシンボリックリンクのとき（リンクだけを動かすと、リンク先と横のファイルが離れる）は断る。
  - 選んだバックアップは、下の復元と同じ確認（読めて整合性があり、番号が 1 以上でアプリの知る範囲にある）を通してから、確かめたのと同じ接続で一時ファイル（`backups/restore-<UNIX 時刻（秒）>.db.tmp`）に写す。ここまでは何も変えない。中断で残った一時ファイルは、次の回復と定期バックアップのときに消す（保存先の直下に置くと、片付ける機会が無いため）。
  - 今の `yunagi.db` と横のファイル（あるものだけ）は消さずに、`backups/damaged-<UNIX 時刻（秒）>.db`（横のファイルは同じ名前に `-wal` などを付けたもの。SQLite が組にして読めるように）へ名前を変えて退避し、写したものを `yunagi.db` に置いてから、ふつうに開く（古いスキーマならマイグレーションを適用する。そのとき作られるマイグレーション前のバックアップは、選んだバックアップと同じ内容なので消す）。`damaged-` の名前はバックアップの名前の形に合わないので、一覧に並ばず、古いものとして消されることもない（壊れたものの中身を後で調べたり、問い合わせで受け取ったりできるように）。退避した場所は画面に示す。
  - 途中で失敗したら、置いたものを消し、退避したものを元の場所に戻してからエラーを返す。戻すのにも失敗したら、それまでに戻したものをもう一度退避した名前へ動かし（本体と `-wal` が別々の場所に分かれたまま、次の回復で別の名前に退避されないように）、退避した場所をエラーに書く。ロックは最後まで持つ。
  - 戻したもののマイグレーションに失敗したときも、マイグレーションが作った写し（選んだバックアップと同じ内容）は消し、エラーにそのことを書く（エラーが示す写しを探して見つからない、とならないように）。
- 復元（`Database::restore_backup`）は `yunagi.lock`（4章）を持って開いたデータベースにだけ行う。選んだバックアップが SQLite として読めて整合性があり、スキーマの番号が 1 以上（番号 0 は空のファイルや別のアプリのデータベースで、写し込むとデータが空になるため断る）でアプリの知る範囲にあることを確かめてから、今のデータを復元前のバックアップとして退避し、開いている接続のまま内容を写し込む。スキーマが古ければ続けてマイグレーションを適用する（そのときマイグレーションが作るバックアップは、選んだバックアップと同じ内容なので消す。旧版の再導入に備えた本来のマイグレーション前のものを押し出さないように）。確かめたのと同じ読み取り専用の接続から写し込み、確かめた後にファイルが消えたり差し替わったりしても、確かめていない内容を写さない。途中で失敗したら、退避したものに戻してからエラーにする。接続にトランザクションが開いたままのときは、書きかけの内容を捨てないよう、復元せずに断る。復元を取り消したいときは、退避したものから復元する。

### 6.3 データベースが見つからないとき（2026-11-03 決定）

保存先に `yunagi.db` が無いとき、コア（`Database::open`）は、初めて使うときだけ新しく作り、それ以外は何も作らずにエラーにする。保存先をクラウド同期フォルダにしていて別の端末から同期がまだ届いていないときや、外付けのドライブを繋いでいないとき、利用者が手でファイルを動かしたときに、黙って空のデータベースを作ると、利用者には「データが消えた」ように見え、後から届いたデータと食い違うため。

- 初めて使うときは、次のすべてに当てはまるときとする。
  - 保存先が既定ディレクトリのまま（`config.json` が無い、`data_dir` の項目が無い、または既定ディレクトリを指す）。指しているかは、シンボリックリンクを辿った実体どうしで比べる（表記の違いで初めてでないとみなさないように）。保存先の変更は設定画面でデータベースを開いた後に行うので、保存先を変えていれば、データベースを作ったことがある。
  - そこにデータベースの跡が無い：中身のある `yunagi.db` の `-wal`・`-journal`（0 バイトのものは SQLite が使わないので除く。調べられないものは跡とみなす。この判定は保存先の変更の移動先の確認（6章）と同じで、コアの1か所にまとめる）、宛先の無い `yunagi.db` のシンボリックリンク、`backups/` のバックアップ（6.2 の名前の形に合うもの）のどれも無い。バックアップがあれば、データベースが消えたのであって初めてではない（作らずに、復元を案内する）。ただし、番号 0 からのマイグレーション前のバックアップ（新しく作ったデータベースを初めて開くときに作られ、成功すると消える。データモデル設計書 1.1）は数えない（初めて使うときに中断すると残るため）。`backups/` を読めないときは、あるものとみなす。
  - 初めて作ったことを `config.json` などに記録はしない。`config.json` に既定ディレクトリの絶対パスを書くと、既定ディレクトリごと移したとき（新しい端末への引っ越しなど）に古いパスを指してしまうため。
- 中身の無い（0 バイトの）`yunagi.db` は、無いものとして扱う。同期の途中で中身がまだ届いていないファイルでありうるため（SQLite は 0 バイトのファイルを空のデータベースとして開く）。初めて使うときの条件に当てはまれば、作る途中で止まったものとして作り直す。
- 見つからないときのエラー（コアの `OpenError::NotFound`）は、探した `yunagi.db` のパス、保存先、保存先を記録した `config.json`（保存先を変えているときだけ）、保存先のフォルダそのものがあるかを持つ。画面・CLI はこれを使って、どこを探したかを示し、次を案内する（画面は画面設計書 10.1、起動時の操作は 4.3）。
  - 同期が終わるのを待つ・ドライブを繋ぐ（フォルダが無いとき）。それからやり直す。
  - 保存先を選び直す（データベースのある別のフォルダを指し直す。保存先の変更（6章）は移動先にデータベースがあると断るので、中身を確かめて記録だけを書き換えるコアの `use_existing_data_dir` を使う。6章「保存先の選び直し」）。
  - バックアップから戻す（`backups/` にあるとき）。選んだバックアップで置き換えて開く（6.2「開けないデータベースからの回復」。取り残された `-wal` などがあれば、それも退避してから置く）。
  - 新しく作る。
- 保存先のフォルダが無い（フォルダでないものを指す場合を含む）ときは、開くときも作るときも見つからないときのエラー（フォルダが無い）にする。
- 今あるデータベースを開くときは、SQLite に作らせない形（`SQLITE_OPEN_CREATE` を付けない）で開く。確かめてから開くまでの間にファイルが消えても（同期で置き換わるなど）、空のデータベースを作らず、見つからないときのエラーにする。
- 新しく作るのは、利用者が選んだときだけ、コアの専用の関数（`Database::create`）で行う。場所の決め方とロックは `Database::open` と同じ。すでにデータベース（中身のある `yunagi.db`、中身のある `-wal`・`-journal`、`yunagi.db` のシンボリックリンク）があれば、上書きせずに断る（取り残された `-wal` は SQLite が新しいデータベースに写し込み、シンボリックリンクはリンク先に作られるため）。保存先のフォルダは作らない（繋いでいないドライブの代わりに、別の場所へ作らないように）。
- 直接モードの CLI・MCP（`Database::with_locked`）も同じ扱いで、見つからなければエラーを返す。エラーコードは `storage_unavailable`（終了コード 6。MCP・CLI 仕様書 4.3）とし、`message` に探した場所を書く（`not_found` は操作の対象が無いことに使うので使わない）。CLI・MCP からは新しく作らない（アプリを開いて選ぶ）。
- `config.json` が壊れているときは、6章のとおり既定の保存先で開かずにエラーにする（新しく作るときも同じ）。

### 6.4 Markdown 書き出し（2026-11-03 決定）

1日または期間のボード（TODO・障害・振り返り・ノート）を、日付ごとの Markdown のファイルに書き出す（要件定義書 F-11・4章）。利用者が Markdown として読む・ほかの端末と同期するためのもので、読み戻し（取り込み）はしない。コアの `domain::export`（読む `read_between`、文字列にする `Boards::render`・`Boards::into_days`（続けて行う `markdown_between`・`day_markdown`）、ファイルに書く `write_files`）、画面からは Tauri コマンド `export_markdown`（入口は設定画面のデータ。画面設計書 7章）。

- 対象：期間（両端を含む。前後が逆でも同じ期間とする）の日のうち、削除されていない項目があるか、ノートか振り返りが空白以外の文字を含む日。それ以外の日はファイルを作らない。期間のすべての日を、同じ時点の内容で読む。
- ファイル：呼び出し側が選んだフォルダ（絶対パス。無ければ作らずに失敗とする）に、1日1つの `YYYY-MM-DD.md`（論理日付）を書く。同じ名前のファイルは置き換え、ほかのファイルには触れない（書き出すものが無くなった日の古いファイルも消さない。利用者のフォルダのファイルを消さないため）。置き換えたファイルの権限（Unix の権限の数字）は保つ。同じ名前がシンボリックリンクなら、リンク先を置き換えてリンクは残す（利用者が別のノートのフォルダへリンクしている場合に、リンクを黙ってファイルに変えないため）。リンク先が無いリンク、同じ名前のフォルダ、2つの日が同じファイルを指すとき（同じリンク先へのリンクなど。片方の日を黙って上書きしないため）、Windows で置き換える先が読み取り専用のとき（名前の変更で置き換えられないため）は、失敗とする。ハードリンクは保たない（置き換えると別のファイルになり、ほかの名前は古い中身のまま）。保つには置き換える先にそのまま書き込むしかなく、書きかけのファイルを同期のツールが読むのを避けられないためで、同期フォルダではハードリンクがそもそも保たれないことが多い。文字コードは UTF-8（BOM なし）、改行は LF。
- 書き方：まずすべての日を、置き換える先と同じフォルダの一時ファイル（`.yunagi-export-<ULID>.tmp`。Unix では置き換える先と同じ権限で作り、ほかの利用者が読める間を作らない）に書いてディスクに反映し、それから日付の順に名前を変えて置き換える（同期のツールやエディタが書きかけのファイルを読まないように）。一時ファイルを書けないときと、上の失敗に当たるときは、書いた一時ファイルを消し、何も置き換えずに失敗とする（画面へは `export_failed`（置き換え終えたファイルの数 `replaced` と、ログ用の `detail`）で返す。データベースの読み取りの失敗は `storage` のまま。2026-11-04 決定。画面設計書 7章）（失敗の大半はここで起きるので、ふつうは「全部か、何も変えないか」になる）。名前の変更に失敗したら、残りの一時ファイルを消して止め、失敗したファイルと、それまでに置き換え終えた数を返す（前の日は置き換え済みのまま）。Windows では、同期のツールなどが置き換える先を開いていると少しの間だけ名前を変えられないので、その失敗（アクセスの拒否・共有の違反・ロックの違反）に限って5回まで待ってやり直す。名前を変えた後（途中で失敗したときも、置き換え終えた分について）、Unix ではフォルダも反映する。一時ファイルを置く各フォルダ（リンク先のフォルダを含む）で、書き始める前に、一時ファイルの形のもののうち、名前の ULID の時刻が1時間以上前のもの（中断で残ったもの）を消す（同じフォルダへ書いている途中のほかの書き出しのものを消さないよう、新しいものは残す）。
- データベースを使うのは読む間だけとし、文字列にしてファイルに書くのは接続を手放してから、1日ずつ行う（画面の自動保存などを、ファイルの書き込みの間待たせないため。文字列にした期間全体を一度に持たないため）。期間の長さに上限は設けない（5年分（1,800日。データモデル設計書 5章の見積もりの量）でも、読む間は約 0.15 秒、文字列にするのは約 0.02 秒だった（2026-11-03、YUN-78。Intel Core i7-11850H。測り方は `crates/core/src/domain/export.rs` の `five_years_of_data_are_read_quickly`）。
- 形：見出しと注記は、画面の言語の設定にかかわらず英語に固定する（依頼文の書き出し（MCP・CLI 仕様書 5章）と合わせ、同期した先で言語を変えてもファイルが変わらないように）。書き出した時刻は入れない（内容が変わらなければ、書き出し直してもファイルが変わらず、同期が起きないように）。中身の無い節は出さない。

```markdown
# 2026-11-03

## TODO

- [ ] API のレート制限を調査 (carried over from 2026-11-02)
- [x] PR をレビュー
- ~~古い作業~~ (dropped)
- [ ] 設計の見直し (carried over to 2026-11-04)

## Blockers

- [x] ステージング環境の権限待ち
  - Resolution: 権限をもらった

## Reflection

（振り返りの本文）

## Notes

## 10:00 定例
（ノートの本文）
```

- 項目：TODO・障害の順に、それぞれ並び順で1行ずつ。未完了・未解消は `- [ ] 本文`、完了・解消は `- [x] 本文`、取りやめた TODO はチェック欄を付けずに `- ~~本文~~` とし、注記に理由（`dropped`・`split`・`returned to external tool`）を書く。削除した項目は出さない。本文は書き換えない（Markdown の記号もそのまま。壊れたデータで改行があれば空白にする）。
- 持ち越し：持ち越してきた項目は `carried over from <元の項目の日付>`（元の項目が削除されていても、その日付）、持ち越し済みの項目は `carried over to <持ち越し先の日付>`（データモデル設計書 3章 item の `carried_to_id` の項目の日付）を注記に書く。注記は本文の後の ` (...)` にまとめ、複数あれば `; ` でつなぐ（持ち越し元・取りやめた理由・持ち越し先の順）。
- 解消メモ：解消した障害に解消メモ（前後の空白を除いて空でないもの）があれば、次の行に字下げして `  - Resolution: 解消メモ` と書く。未解消に戻した障害に残っている解消メモは出さない（画面にも出ないため。画面設計書 3章）。
- 振り返り・ノート：振り返り・ノートの順に、本文をそのまま書く。先頭の空白だけの行と、末尾の空白・改行を除き、改行（CRLF・CR）を LF にそろえることだけを行う。ノートの時刻付き見出し `## 10:00 定例` などの見出しの段も変えないので、`## Notes` と同じ段に並ぶ（見出しの段を下げると、利用者が書いた本文と、ノートの会議区切りの形（データモデル設計書 3章 note）がファイルの上で変わり、`## 10:00` で探したり、ほかの端末で同じ本文として読んだりできなくなるため）。

### 6.5 WebView のデータの置き場所と、`uninstall --purge` で消すもの（2026-11-05 決定。YUN-44）

WebView（画面を描く部品）は、キャッシュや保存領域（Cookie・`localStorage` など）を、データディレクトリ（6章）とは別の場所に作る。`yunagi uninstall --purge`（ビルド・配布手順書 4.4）が「データも削除する」約束を守るには、これも消す必要がある。業務データは 4.3 のとおりコアが持ち、画面の側は `localStorage` などを使っていない（2026-11-05 に `src/` を調べた）ので、WebView の場所に残るのは、WebView が自分で作るキャッシュや Cookie の類である。業務データではないが、アプリを使った跡なので、`--purge` では消す。画面の側が `localStorage` などを使うようにしたときも、この場所ごと消すので、決まりは変わらない（その保存を足すときに、残してよいか 6.5 を見直す）。

**置き場所**（`<id>` は識別子 `io.github.misty-swan.yunagi`。6.1）：

| OS | 場所 | 確かめた範囲 |
| --- | --- | --- |
| Linux | `$XDG_DATA_HOME/<id>/`（未設定・空・相対パスのとき `~/.local/share/<id>/`）。キャッシュ（`WebKitCache/`・`CacheStorage/`）も同じフォルダの中 | ソースと実機。Tauri は Linux・Windows で、WebView のデータの場所が未指定なら `app_local_data_dir`（`dirs::data_local_dir()/<id>`）を渡す（`tauri` 2.12.5 の `src/manager/webview.rs`、`src/path/desktop.rs`）。wry の WebKitGTK 版は、それを `base_data_directory` と `base_cache_directory` の両方に使う（`wry` 0.57.1 の `src/webkitgtk/web_context.rs`）。開発機（Linux）で動かしたアプリが、`~/.local/share/<id>/` に `WebKitCache/`・`CacheStorage/`・`storage/`・`mediakeys/`・`hsts-storage.sqlite` を作り、`~/.cache/` には何も作っていないことを見た |
| Windows | `%LOCALAPPDATA%\<id>\`（その下の `EBWebView\` に WebView2 が実際のデータを置く） | ソースまで。Linux と同じ Tauri の処理で場所が決まり、wry が WebView2 の「ユーザーデータフォルダ」にそのまま渡す（`wry` の `src/webview2/mod.rs` の `create_environment`）。`EBWebView` という名前は WebView2 の決まりで、ソースでは確かめていない。Windows の実機では未確認（08 4.9） |
| macOS | 下の「消すもの」の 5 か所のうち、実際にあるもの | ソースまで。Tauri は macOS では場所を渡さず（上の処理は Linux・Windows だけ）、wry は `WKWebsiteDataStore.defaultDataStore` を使う（`wry` の `src/wkwebview/mod.rs`）。実際の場所は WebKit と OS が決めるため、Mac の実機で確かめるまで未確認（08 4.9） |

macOS で想定する場所（サンドボックスに入れない通常のアプリのとき。どれも識別子の名前）：`~/Library/WebKit/<id>/`（保存領域）、`~/Library/Caches/<id>/`（キャッシュ）、`~/Library/HTTPStorages/<id>/`（Cookie など）、`~/Library/Preferences/<id>.plist`（アプリの設定）、`~/Library/Saved Application State/<id>.savedState/`（窓の状態の記憶）。Application Support の下には識別子のフォルダを作らない（データは `~/Library/Application Support/Yunagi/`。6章）。

**`--purge` の決まり**：

- 消すのは、データ（既定ディレクトリの全体と、設定で保存先を変えているときはその保存先の `yunagi.db`・`yunagi.db-wal`・`yunagi.db-shm`・`yunagi.db-journal`・`backups/`。保存先のフォルダ自体は、利用者のほかのファイルがあるかもしれないので消さない）と、上の表の WebView の場所である。macOS は 5 か所を 1 つずつ見て、あるものだけを消す（無いものは飛ばし、エラーにしない。どれが実際にできるかは Mac の実機で確かめるまで分からないため）。
- macOS の `~/Library/Preferences/<id>.plist` は、OS の設定の仕組み（`cfprefsd`）が値を覚えていて書き戻すことがあるので、ファイルを消す前に `defaults delete <id>` を呼ぶ。それでも消した後に現れたときは、消し残りとして一覧に出す。
- Linux の WebView の場所と既定ディレクトリは、同じ「`XDG_DATA_HOME` を求める関数」から導く（実装は WebView の場所を、既定ディレクトリの求め方（`default_dir`）の元の `data_local_dir` 相当の値の下の `<id>` として求め、別々に環境変数を読まない）。試験で、`XDG_DATA_HOME` の未設定・空・相対・絶対の 4 通りについて、両者が同じ親の下になることを確かめる。
- 消す順番と、`config.json` が読めないときに何も消さずに止まることは、ビルド・配布手順書 4.4。
- 消す場所は上に書いた完全なパスだけである（識別子の一部で探したり、`~/Library/WebKit/` のような親のフォルダを消したりしない）。シンボリックリンクは、リンクだけを消して先には触れない。
- 場所は環境変数から求める（Linux は `XDG_DATA_HOME`・`HOME`、Windows は `LOCALAPPDATA`、macOS は `HOME`。6章の既定ディレクトリと同じ決まり。試験は一時フォルダの値に差し替えて行える）。求められないときは、その場所を飛ばさずエラーにする。Tauri の `dirs`（7.0.0）の求め方との違い：Linux は同じ（`XDG_DATA_HOME` が絶対パスならそれ、空・相対パスなら `~/.local/share`。`dirs/src/lin.rs`・`dirs-sys` の `is_absolute_path`）。Windows の `dirs` は環境変数でなく Known Folder（`FOLDERID_LocalAppData`）から求めるので、`LOCALAPPDATA` を書き換えて動かしたときだけ、Tauri が実際に書いた場所とずれる（ふだんは一致する。環境変数を使うのは試験で差し替えるためで、利用者に `LOCALAPPDATA` を変える使い方は想定しない）。
- アプリが動いている間は、`yunagi.lock`（4章）が取れないので、何も消さずに止まり、アプリ（と、エージェントが起動した MCP サーバー。直接モードで一時的にロックを持つ）を終了するよう知らせる（WebView がファイルを使っている間に消すと、一部だけ消えて残るため）。ロックの取り方と、消す順番（Windows で動いている `yunagi.exe` と、ロックファイルのある既定ディレクトリを消すための順）は、ビルド・配布手順書 4.4。
- 消せなかったものがあっても、ほかは消し続け、最後に消したものと消せなかったものを一覧にして、終了コードを 0 以外にする。
- Homebrew の Cask（v1.0 では出さない。ビルド・配布手順書 4.3）を将来出すときは、保存先を変えたまま Cask の `zap` で消すと、Cask が `config.json` を読めないので、変えた先は消えない。そのときに利用者ガイドの「アンインストール」に書く。

実装は `crates/cli/src/uninstall/`（YUN-99。コマンドの決まりは CLI・MCP 仕様書 3.1）。識別子はコアの定数 `APP_IDENTIFIER`（`tauri.conf.json` の `identifier` と同じことを試験で固定する）、既定ディレクトリと Linux・Windows の WebView の場所の親は、コアの `local_data_root_for` 1 つから導く（4 通りの試験はコアの `data_dir.rs`）。

## 9. 未決事項

- Windows の名前付きパイプの権限・先取りの防ぎ・読みの中断・閉じ方は型検査までで、実機では確かめていない（4.6。テスト計画書 4.5。YUN-87）。実機で挙動が違えば 4.6 を直す

- アプリが SIGTERM（デスクトップのログアウト・シャットダウンなど）を受けたときの終了の仕方（4.4・4.6）。Linux の実機（2026-11-07。テスト計画書 4.15 の B-6）で、SIGTERM で止めると通常の終了の片付け（待ち受けを止めてソケットとトークンのファイルを消す）が走らず、`api.sock`・`api.token` が残った。設計上は異常終了と同じ扱いで害は無い（残ったソケットは次の起動でアプリが消して作り直し、トークンは待ち受けの開始で書き換わり、待ち受けが無いので残ったトークンは使えない）が、SIGTERM でも片付けるかは決めていない。決めるときは、Tauri の終了の経路（`RunEvent::Exit`）にシグナルを結び付けるかを見る。macOS の SIGTERM と、Windows のログオフ・シャットダウン時の終了も同じ（実機で挙動を見る。YUN-87）
- Linux のデスクトップ連携：.deb・AppImage に Tauri が入れるデスクトップエントリの名前と、X11 で窓とエントリを結び付ける `StartupWMClass` の値（6.1）
- クラウド同期で、タイムゾーンが異なる端末同士の論理日付の扱い（例：その日のボードを最初に作った端末のタイムゾーンで確定する）
