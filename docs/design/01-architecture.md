# アーキテクチャ設計書

## 1. 方針

Yunagi は、端末内で完結するローカルファーストのデスクトップアプリとして構成する。すべてのデータの読み書きは「コア」と呼ぶ単一の層に集約し、画面・CLI・MCP サーバーはいずれもコアを通じてデータに触れる。これにより、利用者とAIエージェントが同時に操作しても、整合性と変更履歴を一か所で保証できる。

## 2. 全体構成

```
Yunagi アプリ（Tauri）
├─ フロントエンド（WebView）
│   ├─ 整理モード / ノートモード / 持ち越し / 検索 / 設定 / 変更履歴
│   └─ エディタ（ノート・振り返り。Vimモード対応）
│        │ Tauri コマンド（IPC）
└─ コア（Rust）
    ├─ ドメイン層：日付ボード、TODO、障害、振り返り、ノート、持ち越し
    ├─ 権限・変更履歴：エージェント操作の許可判定と取り消し
    ├─ ストレージ：SQLite（WAL）＋ FTS5 全文検索
    ├─ ローカル API サーバー：UNIX ドメインソケット / 名前付きパイプ
    └─ OS 連携：グローバルショートカット、IME 切替、キーチェーン、更新
          ▲
          │ ローカル API（アプリ停止中はロックを取って DB を直接開く。4章）
          │
コンソール用バイナリ `yunagi`
├─ CLI：`yunagi <名詞> <動詞>`（シェル・git フックから）
└─ MCP サーバー：`yunagi mcp`（stdio。Claude Code / Codex から）
```

CLI と MCP サーバーは、GUI とは別のコンソール用バイナリ `yunagi`（Windows は `yunagi.exe`）のサブコマンドとして提供し、アプリに同梱する（配置先はビルド・配布手順書 2章）。GUI とコンソール用バイナリは同じクレートからビルドする。

## 3. 技術選定

| 領域 | 採用 | 理由 |
| --- | --- | --- |
| アプリ基盤 | Tauri 2 | 軽量、3 OS 対応、Rust コアと Web UI の分離 |
| コア言語 | Rust | Tauri と同一言語。CLI・MCP をアプリと同じクレートからビルドし、ドメイン層を共有できる |
| フロントエンド | TypeScript ＋ Svelte 5 | 起動と入力の速さを優先して、軽量な UI フレームワークから選んだ。試作で SolidJS と比べて決めた（3.1） |
| エディタ | CodeMirror 6 ＋ Vim 拡張 | Vim のノーマル・挿入・ビジュアルモードと IME の扱いに実績がある |
| データベース | SQLite（WAL モード、`synchronous=NORMAL`）、FTS5 | 単一ファイルで堅牢。全文検索を内蔵。`synchronous=NORMAL` では電源断時に失うのは最後のチェックポイント以降の直近の書き込みに限られ、要件の「直前数秒以上は失わない」を満たす見込み（08 で確認） |
| 秘密情報 | OS キーチェーン（`keyring` クレート等） | 外部ツールの認証情報を平文で持たない |
| 自動更新 | Tauri Updater（独自鍵で署名） | OS の有料署名に依存しない |

### 3.1 フロントエンドの選定理由（2026-11-02 決定）

Svelte と SolidJS で同じ小さな画面を Tauri 2 上に作って比べた（YUN-2。結果は `experiments/yun-2-frontend/RESULTS.md`。試作のコードは比較用で、本番には流用しない）。

- 起動時間・メモリ・入力の反応には、両者で意味のある差がなかった。速さで決まらないため、作りやすさと保守のしやすさで選んだ。
- 整理モードの一覧（その場で編集する項目と、エージェントの変更による再読み込み。4章 6）を、Svelte は基本機能だけで正しく書けた。SolidJS では、差分で更新する仕組み（`reconcile`）と比較処理の自作が要った。書き忘れたときの壊れ方も、SolidJS のほうが重かった（再読み込みのたびに入力中の項目からフォーカスが外れる）。
- Svelte のほうが、画面のコードが短く、依存パッケージも少ない。SolidJS の利点である JS の小ささは、共通の CodeMirror を含めると約 3% の差で、アプリに同梱するため起動時間にも表れなかった。
- IME（日本語入力）は、Linux（fcitx5-mozc）で両版を実機確認し、問題はなかった。macOS・Windows ではテスト計画書の IME 試験で確かめる。

実装の注意：

- その場で編集する項目（contenteditable）は1つの部品にまとめる。本文は `bind:textContent` で結び付け、式で直接書かない（入力のたびに余分な書き換えが起き、カーソルが崩れる）。一覧はキー付きの `{#each}` で描き、項目を増やした・分けた直後のフォーカスは `await tick()` の後に移す。
- これらの動き（分割・削除・移動、再読み込みの後もフォーカスと選択範囲が残ること）は、試作と同じく自動テストで守る。

## 4. 書き込み経路と同時実行

1. アプリ起動中は、コアがデータベースへの唯一の書き込み主体となる。CLI と MCP サーバーはローカル API 経由でコアに依頼する。
2. アプリ停止中は、CLI と MCP サーバーが操作ごとにロックファイル `yunagi.lock`（6章の既定ディレクトリ）の排他ロックを取得してからデータベースを開き、操作が終わったらロックを離す。ロックを持ち続けない。
3. MCP サーバーは常駐するプロセスのため、アプリの起動・停止をまたいで動き続ける。そこで操作ごとに、まずローカル API への接続を試み、接続できなければ 2 の直接モードで処理する。
4. アプリは起動時に `yunagi.lock` を取得する。取れないとき（CLI・MCP の操作中）は最大数秒待ち、それでも取れなければエラーを表示する。
5. いずれの経路でも、ドメイン層の同じ関数を通るため、検証・権限判定・変更履歴の記録は一様に適用される。
6. MVP では、コアは変更をイベントとしてフロントエンドに通知し、画面はデータを再読み込みして最新の状態を表示する（エージェントによる変更も含む）。変わった項目の強調などの演出は第2フェーズ（ロードマップ参照）とする。

ローカル API のソケットは利用者本人のみが読み書きできる権限で作成し、接続時にランダムなトークンで認証する。トークン・ソケット・ロックファイルは、保存先の設定に関係なく6章の既定ディレクトリに置く（保存先をクラウド同期フォルダにしても同期されないようにするため）。

### 4.1 利用者の入力中に届いたエージェントの変更（2026-11-02 決定）

再読み込み（4章 6）で、利用者が入力中の文字・カーソル・変換中の文字を壊さず、利用者の入力を失わないよう、対象ごとに次のように扱う。

**項目の入力中**：フロントエンドは、フォーカスのある項目の欄（本文または解消メモ）と「入力中かどうか」をコアに知らせる。項目の本文または解消メモは、その欄にフォーカスがあり、かつ最後の入力から 10 秒以内か IME の変換中であれば入力中とする。10 秒は、考えながら打つ間の小休止を含めつつ、エージェントを長く待たせないための長さ。フォーカスが外れたとき、またはアプリが前面から外れたときは、まだ保存していない入力（自動保存の待ち。最大 0.5 秒）をすぐに書き込み、その書き込みが終わった時点で入力中を終える。書き込みが終わるまではフォーカスが無くても入力中とみなす。保存前にエージェントの変更を受け付けると、続く保存でエージェントの変更が利用者の入力で上書きされるため。

**保存に失敗している間**：書き込みに失敗して自動で再試行している間（画面設計書 3章「上部のバー」の「保存できていません」）は、入力中とはみなさない。代わりに、まだ保存できていない入力がある項目・ノート・振り返りへのエージェントの書き込みには `storage_unavailable` を返す。再試行の保存が書き込まれるまで、その対象の内容が確定しないため。保存が成功すれば通常の扱いに戻る。これにより、保存が失敗し続けても `user_editing` を返し続けることはなく、エージェントは保存先の問題であることを知れる。

**ノート・振り返りの守る行**：エディタにフォーカスがある間、またはまだ保存していない入力がある間、フロントエンドは、エージェントに変えさせない行（守る行）をコアに知らせ、変わるたびに知らせ直す。守る行は次の2つを合わせたもの。

- カーソル行：カーソルのある行（選択範囲が複数行にまたがるときはその全部の行）。フォーカスがある間だけ含める。
- 未保存の変更がある行：最後に保存した本文の行のうち、エディタで書き換えたか削除して、まだ保存していない行。差分の上では「削除＋追加」に見える書き換えも、元の行の書き換えとして含める。カーソルを別の行へ移しても、保存されるまでは守る行に残る。

行番号は、コアにある保存済みの本文で数える（エージェントが `get_note` で読み、`edit_note` で指定するのと同じ数え方）。エディタにはまだ保存していない行が含まれうるため、フロントエンドは、最後に保存した本文とエディタの内容の差分から、行番号を保存済みの本文の行番号に置き換えて知らせる。保存前に足した新しい行は、エージェントが指定できないので知らせない（保存済みの行を書き換えた結果の行なら、元の行が「未保存の変更がある行」として守られる）。知らせた行番号には、数えた本文の版の番号（`rev`）を添える。コアの版のほうが新しいときは、その間にコアが書き込んだ変更に合わせて行番号をずらしてから使う。

| 対象 | 入力中に届いたエージェントの変更 |
| --- | --- |
| 項目の本文（`edit_todo`） | その項目の本文を入力中なら受け付けず、`conflict`（`reason: user_editing`。MCP・CLI 仕様書 4.3）を返す。エージェントは後でやり直す。解消メモの入力中は、本文とは別の欄なので受け付ける。入力中でなければ受け付け、フォーカスがあってもその場で画面に反映する（カーソルは同じ文字位置。本文より後ろなら末尾） |
| 項目の状態（`complete_todo` / `reopen_todo` / `resolve_blocker`） | 本文・解消メモとは別の欄なので、本文または解消メモの入力中でも受け付けてすぐ反映する。なお、解消メモは障害を解消した後に入力する（操作仕様書 2章）ため、解消メモの入力中に届く `resolve_blocker` は解消済みの障害への操作になる。その扱い（`--note` による解消メモの書き込みを含む）は未決とする（9章） |
| ノート・振り返り（`append_note` / `append_reflection` / `edit_note`） | 受け付ける。エディタには本文の置き換えではなく差分（変更箇所だけ）として取り込み（下記「取り込み方」）、カーソルと選択範囲を保つ。IME の変換中は、変換が終わるまで取り込みを待つ。取り込んだ変更は Mod+Z の取り消しの対象にしない（04 2章。取り消しは変更履歴 S-06 から）。`edit_note` で、守る行（上記）を書き換え・削除・移動しようとした場合だけ `conflict`（`reason: user_editing`）にする |

**ノート・振り返りへの取り込み方**：エージェントの変更をエディタに取り込むとき（保存の行き違いで最新の内容を取り込むときも同じ）、フロントエンドは、最後に保存した本文をもとにして、「エージェント側の変更（もとの本文→コアの最新）」と「利用者のまだ保存していない変更（もとの本文→エディタ）」を合わせる。

- 重ならない変更は、両方を残す。
- 同じ位置への行の追加は、両方を残す（利用者の行を先にする）。
- 同じ行を両方が変えた場合（守る行を知らせる前にエージェントの変更が届いた、行き違いのときに限られる）は、利用者の入力を残す。エージェントの変更は change_log に記録済みで（未確認の印も付いたまま）、変更履歴 S-06 で確かめられる。

これにより、利用者の入力はすべてエディタに残り、エージェントの変更はノートか変更履歴のどちらかに必ず残る。

**ノート・振り返りの保存の行き違いを防ぐ**：note・reflection は版の番号（`rev`。データモデル設計書）を持つ。フロントエンドの保存には、もとにした版の番号を添える。同じノート・振り返りへの保存は一度に1つだけ送り、成功の応答で返る新しい版の番号を次の保存のもとにする（利用者自身の保存どうしが行き違わないようにするため）。コアの版のほうが新しい（その間にエージェントが変更した）場合、コアは保存を受け付けずに最新の内容を返す。フロントエンドは、上の取り込み方で最新の内容をエディタに取り込み、利用者のまだ保存していない入力を残したまま保存し直す。

**項目の保存**：item は版の番号を持たない。フロントエンドの保存では、利用者が変えた欄（本文・解消メモ・状態・並び順など）だけを送り、コアは送られた欄だけを書く。ほかの欄は書かないため、エージェントが同じ項目の別の欄を変えていても、その変更は残る（例：本文の入力中にエージェントが `complete_todo` で完了にしても、続く本文の保存で未完了に戻らない）。同じ欄をエージェントも変えていた場合（入力中の判定と行き違ったときに限られる）は、利用者の保存で上書きする。項目は利用者の入力を優先するので、ノートのように保存を拒否して最新を返し、保存し直す往復をしても結果は変わらないため。上書きされたエージェントの変更は change_log に記録済みで（未確認の印も付いたまま）、変更履歴 S-06 で確かめられる。版の番号が無いので、利用者自身の保存（並べ替えや、自動保存の待ち中の完了など）どうしが行き違うこともない。

アプリの停止中は画面での入力がないため、この扱いは起動中にだけ働く。

## 5. 日付の扱い

「その日」はカレンダー日付ではなく、設定した切り替わり時刻（既定 4:00）を基準とした論理日付で扱う。論理日付の算出はコアのみが行い、CLI・MCP も同じ規則に従う。タイムゾーンは端末の設定に従い、日付ごとに記録時のタイムゾーンを保存する。切り替わり時刻を変更した場合は、変更後に作成するデータにだけ適用し、既存の日付は付け直さない。

## 6. データの保存場所

| OS | 既定のデータディレクトリ |
| --- | --- |
| macOS | `~/Library/Application Support/Yunagi/` |
| Windows | `%LOCALAPPDATA%\Yunagi\` |
| Linux | `$XDG_DATA_HOME/yunagi/`（未設定時 `~/.local/share/yunagi/`） |

既定ディレクトリは、アプリ本体の配置先とは別にする（アプリ本体の配置先はビルド・配布手順書 2章）。

設定ファイル `config.json`（保存先 `data_dir` を持つ）、ローカル API の認証トークン、ロックファイル `yunagi.lock`、ソケットは、保存先の設定に関係なく常に上記の既定ディレクトリに置く。保存先（`data_dir`）に置くのはデータベースと `backups/` である。

保存先は設定で変更できる。変更時はデータベースを安全に移動し、移動先を `config.json` に記録する。自動バックアップは保存先の `backups/` に直近7日分を作成する。

保存先を iCloud Drive・Dropbox などのクラウド同期フォルダにする場合は、同時に1台だけで開く場合に限って使える（SQLite のデータベースと WAL のファイルが別々に同期されると壊れうるため）。同期フォルダと判定できる場合は、設定時に警告を表示する。複数端末で使う場合は、Markdown 書き出しまたはバックアップの同期を推奨する。

## 7. OS 連携

| 機能 | macOS | Windows | Linux |
| --- | --- | --- | --- |
| グローバルショートカット | 対応 | 対応 | X11 は対応。Wayland は環境依存のため、デスクトップ環境のショートカット設定から `yunagi show` を呼ぶ方式を案内する |

## 8. 外部ツール連携と同期（MVP 後の有料機能）

外部ツール連携とクラウド同期は、MVP 後の有料機能とする（段階はロードマップ参照）。Linear・Jira 連携はコア内の「コネクタ」として実装し、端末から直接各サービスの API を呼ぶ。クラウド同期はコアに同期モジュールを追加し、エンドツーエンド暗号化したデータだけをサーバーに送る。詳細は future 配下の各仕様書を参照。
