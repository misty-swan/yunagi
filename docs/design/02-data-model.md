# データモデル設計書

## 1. 方針

- 1つの SQLite データベース（`yunagi.db`）に全データを保存する。
- 主キーは時刻順に並ぶ ULID とし、将来のクラウド同期で端末間の衝突を避ける。
- 削除は論理削除（`deleted_at`）とし、変更履歴からの取り消しと同期に備える。
- 日付は論理日付（切り替わり時刻を考慮した `YYYY-MM-DD`）で保持する。
- 時刻は UTC の ISO 8601 で、ミリ秒までの決まった桁数で保持する（例：`2026-11-03T09:15:00.000Z`。文字列の大小が時刻の前後と一致する）。
- 表は SQLite の STRICT テーブルとし、3章の型と違う値を入れさせない。説明に NULL と書いていない列は NOT NULL とする。`kind`・`status` などの値の種類は、検査（CHECK）を付けずにコアで確かめる（値を足すたびに表を作り直さずに済むようにするため）。JSON の列は、正しい JSON であること（agent_client.scopes は配列であること）だけを表で確かめる。
- スキーマはマイグレーション番号で管理し、更新時に自動適用する。適用前に必ずバックアップを取る。適用に失敗した場合は自動でバックアップに戻してデータを変更せず、旧版の再導入方法を案内する（ビルド・配布手順書 5章）。
- `yunagi.db` は保存先（`data_dir`）に置く。保存先そのものは DB ではなく設定ファイル `config.json` に記録する（アーキテクチャ設計書 6章）。

### 1.1 マイグレーションの仕組み（2026-11-02 決定）

- 番号は 1 から連番とし、適用済みの番号を SQLite の `user_version` に記録する（0 は未適用）。一度配布した版に入ったマイグレーションは書き換えず、変更は新しい番号で足す。表の構造を変えなくても、保存する値の種類（item の `status`、agent_client の `scopes` など、3章で列挙した値）を足すときは新しい番号を足す（SQL は空でもよい）。旧版は知らない番号のデータベースを開かずに断るので、旧版を再導入したときに、知らない値を読んで途中で止まらないようにするため（2026-11-03 決定）。
- 起動時、データベースを開いた直後に、記録より大きい番号のものを順に適用する。1つずつ、SQL と番号の記録を同じトランザクションで行う。適用中は外部キーの検査を止め（参照されている表を作り直せるようにするため）、各マイグレーションの確定前に `foreign_key_check` で参照が壊れていないことを確かめ、壊れていれば失敗とする。通常の接続では外部キーの検査を常に有効にする。
- 適用の前に、保存先の `backups/` に `pre-migration-v<適用前の番号>-to-v<適用後の番号>-<UNIX 時刻（秒）>.db` としてバックアップを取る（SQLite のオンラインバックアップ。一時ファイルに書き、`-wal` を伴わない1つのファイルにしてから名前を変える。中断で残った一時ファイルとその横のファイルは次の適用時に消す）。写したものの整合性を確かめ（`integrity_check`）、通らなければマイグレーションを始めずにエラーにする（壊れたバックアップでは、失敗したときに戻せないため。2026-11-03 決定。アーキテクチャ設計書 6.2）。
- 1つでも失敗したら、それより前に成功した分も含めてバックアップの内容に戻す（トランザクションの取り消しだけでは、先に成功した番号の変更が残るため）。
- 成功した後もバックアップは残す（旧版を再導入したときに戻す先になるため）。ただし、適用前の番号が 0 で表も無い（新しく作った）データベースの場合は、戻す意味のあるデータが無いので消す。定期バックアップ（7日分）と同じ一覧に並べて復元に使えるようにし、世代は別に数えて新しいものから3つを残す（2026-11-03 決定。アーキテクチャ設計書 6.2）。
- 記録がアプリの知る最新の番号より大きい（新しい版で作られた）か負のデータベースは、ファイルに書かずにエラーとする（WAL への切り替えより前に確かめる）。
- 同じデータベースを同時にマイグレーションするのは1つのプロセスだけという前提で動く（`yunagi.lock` による。アーキテクチャ設計書 4章）。失敗時の復元はデータベース全体を置き換えるため、ほかのプロセスが同時に書いていると、その書き込みは消える。

## 3. テーブル定義

### day

| 列 | 型 | 説明 |
| --- | --- | --- |
| date | TEXT PK | 論理日付 `YYYY-MM-DD` |
| tz | TEXT | 記録時のタイムゾーン（記録する形は下記） |
| carryover_done_at | TEXT NULL | その日の持ち越し処理を終えた時刻（「選んだものを持ち越す」「すべて持ち越す」「持ち越さない」のいずれかを選んだ時刻） |
| carryover_postponed_at | TEXT NULL | 持ち越しを後回し（Esc）にした時刻 |
| carryover_reshown_at | TEXT NULL | 後回しにした持ち越しを、前面に出したときに自動で再表示した時刻（自動の再表示は1回だけ。画面設計書 5章） |
| created_at | TEXT | 作成時刻（ISO 8601） |

day の行は、その日に最初の書き込み（項目・ノート・振り返りの作成、または持ち越しの状態の記録）が起きたときに作る。表示しただけでは作らない。`tz` は行を作った時点の端末のタイムゾーンとする。

`tz` は、次のうち最初に当てはまる形で記録する（コアの `time_zone_record`）。IANA の名前に zoneinfo の中の別の版のフォルダの接頭辞（`posix/`・`right/`。`/etc/localtime` が `/usr/share/zoneinfo/posix/Asia/Tokyo` へのリンクのときなど）が付いていれば、接頭辞を除いた名前（`Asia/Tokyo`）を記録する（2026-11-03 決定）。接頭辞の付いた名前は、ほかの環境のタイムゾーンデータベース（Windows や、jiff が同梱するもの）に無いことがあり、読み戻せないため。除いた名前がタイムゾーンデータベースに無ければ、名前の無いタイムゾーンデータと同じく、行を作った瞬間の UTC からのずれを記録する。どの形も、コアの読み取り（`parse_time_zone_record`）でタイムゾーンに読み戻せる。ただし IANA の名前は、読み戻す側のタイムゾーンデータベースにその名前が無いと読み戻せない（古いデータベースで、新しくできた名前を読むときなど）。過去や先の日付の行を作るときも、記録するのは作った時点の端末のタイムゾーンである（最後の形なら、作った瞬間のずれ）。

| 端末のタイムゾーン | 記録する値 | 例 | 読み戻したもの |
| --- | --- | --- | --- |
| IANA の名前が取れる | その名前 | `Asia/Tokyo`、`UTC` | 同じタイムゾーン（規則は読み戻す時点のタイムゾーンデータベースによる） |
| POSIX 形式の TZ 指定（環境変数 `TZ=JST-9` など） | その文字列（jiff が整えた形） | `JST-9`、`EST5EDT,M3.2.0,M11.1.0` | 同じ規則 |
| UTC からのずれが固定 | そのずれ | `+09:00`、`-00:44:30` | 同じずれ |
| 名前の無いタイムゾーンデータ（`/etc/localtime` が zoneinfo へのリンクでない、`TZ` が zoneinfo の外のファイルを指す、など） | 行を作った瞬間の UTC からのずれ | `-04:00` | その瞬間のずれだけ。夏時間などの規則は残らない |

上の3つは、読み戻したタイムゾーンで同じ論理日付の計算ができる（IANA の名前は、記録したときと同じ版のタイムゾーンデータベースで読み戻した場合。版が変わって規則が変われば、読み戻した規則も変わる）。最後の形は規則を残せず、読み戻して同じに求まるのは、作った瞬間の壁時計の時刻だけである（その日の始まりから作った瞬間までに夏時間の切り替えがあると、同じ瞬間の論理日付も違って求まりうる）。jiff はこのタイムゾーンを文字列にできず、どの固定のずれでもすべての瞬間の論理日付は再現できないため、作った瞬間の時刻だけは確かに残せるこの形にする。名前の無い TZif の夏時間の規則は残さない（2026-11-03 決定）。TZif の末尾には POSIX 形式の規則があるが、jiff はそれを公開しておらず、読むには jiff と同じ手順（`TZ`・`/etc/localtime`）でどのファイルを読んだかを求め直し、TZif を自分で読む必要がある。切り替わりの時刻から規則を作り直す方法は、「第2日曜」と「8日以降の最初の日曜」のように同じ年に同じ日になる規則を見分けられない。この形の環境は少なく、上のとおり保存済みの日付は規則が残らなくても変わらないため、手間に見合わない。論理日付そのものは `date` に保存してあり、後から付け直さない（アーキテクチャ設計書 5章）ので、規則が残らなくても保存済みの日付は変わらない。

その日の持ち越しを表示するかは、`carryover_done_at` が NULL で、前回の日に未完了の TODO または未解消の障害があるかで判定する。`carryover_postponed_at` が設定済みで `carryover_reshown_at` が NULL なら、次に前面に出したとき1回だけ再表示し、`carryover_reshown_at` を記録する。アプリを再起動しても、この判定は保たれる。

### item

| 列 | 型 | 説明 |
| --- | --- | --- |
| id | TEXT PK | ULID |
| date | TEXT FK→day | 所属する日 |
| kind | TEXT | `todo` / `blocker` |
| text | TEXT | 1行の本文（前後の空白を除いて保存する。MCP・CLI 仕様書 3章） |
| status | TEXT | todo: `open` / `done` / `dropped`、blocker: `open` / `resolved` |
| close_reason | TEXT NULL | `status = dropped` の理由：`dropped`（やめる）/ `split`（分割した）/ `returned_external`（外部ツールへ戻した） |
| sort_key | TEXT | 並び順（分数インデックス） |
| carry_count | INTEGER | 持ち越された回数（0 から。持ち越すたびに元項目の値＋1） |
| carried_from_id | TEXT FK→item NULL | 持ち越し元（前回の日）の項目の id |
| split_from_id | TEXT FK→item NULL | 分割元の項目の id（分割で作った子項目のみ） |
| resolution_note | TEXT NULL | 障害の解消メモ（未解消に戻しても残す。持ち越しで作る項目には写さない。操作仕様書 2章） |
| origin | TEXT | `human` / `agent` / `note`（ノートから送った） / `external` |
| agent_client_id | TEXT FK→agent_client NULL | エージェントが作成した場合の識別 |
| external_ref_id | TEXT NULL | 外部課題との紐付け（external_ref の表は MVP 後に作るため、それまでは外部キーを付けない） |
| completed_at | TEXT NULL | 完了・解消時刻（未完了・未解消に戻すと NULL。すでに完了・解消済みへのやり直しでは変えない。操作仕様書 2章、MCP・CLI 仕様書 3章） |
| created_at / updated_at / deleted_at | TEXT（deleted_at は NULL） | 監査用時刻。deleted_at は論理削除した時刻。何も変えずに成功を返した操作（すでに目的の状態の `complete_todo`・`reopen_todo`・`resolve_blocker`、今と同じ本文の `edit_todo`・`edit_blocker`。MCP・CLI 仕様書 3章）では updated_at を変えない |

持ち越しは「前回の日の項目を移動する」のではなく、「今日に新しい項目を作り、`carried_from_id` で元を指す」方式とする。前回の日とは、今日より前で項目またはノートが存在する直近の日であり、それより前の日は持ち越しの対象にしない。ここで「項目が存在する」は `deleted_at` が NULL の item が1件以上あること、「ノートが存在する」は note の `body` が空白以外の文字を含むことを指す。振り返りだけを書いた日は前回の日に含めない。過去日のボードが当時の状態のまま残り、振り返りと検索の信頼性が保たれる。

- 前回の日の元項目の `status` は変更しない。持ち越し済みかどうかは、`carried_from_id` で元を指す項目をたどって、`deleted_at` が NULL の項目に行き着くかで判定する。たどった先が削除されていれば、その項目を元に指す項目へさらにたどる（A→B→C と持ち越して B を削除しても、A は C へ持ち越し済みのまま）。最初に行き着いた削除されていない項目を `carried_to_id` とする（派生列またはビューで参照する）。行き着く項目が無くなれば（持ち越し先を削除した場合など）、元項目は持ち越し済みでなくなる。行き着く項目は常に1件以下に保つ。持ち越しの画面（S-03）は持ち越し済みの項目を出さず、削除した持ち越し先を Mod+Z で戻すときに、元項目がほかの項目へ持ち越し済みになっていれば戻さない（下記。持ち越し先を削除してその日に項目もノートも無くなると、次の日の「前回の日」が元項目の日になり、元項目がもう一度持ち越されうる）。
- 持ち越し済みの項目は、その日の終わりの状態として残すため、持ち越した後は `status`・`text`・`resolution_note`・`completed_at` を変えない（2026-11-03 決定）。エージェントの書き込みは `conflict`（`reason: carried_over`）で拒み（MCP・CLI 仕様書 3章）、画面でも変えられない（操作仕様書 2章）。削除と並べ替えは通常どおりできる。画面（操作仕様書 2章）と MCP・CLI（MCP・CLI 仕様書 3章）の扱いは、この決まりを正本とする。`agent revert` でこれらの欄を戻すかは未決（MCP・CLI 仕様書 9章）。
- 持ち越し先を削除した後に元項目が変わった（`status`・`text`・`resolution_note`・`completed_at` のどれかが削除の時点と違う）か、ほかの項目へ持ち越し済みになった場合は、持ち越し先の削除を Mod+Z で取り消さない（上部のバーに理由を短時間表示する）。戻すと、元項目と持ち越し先が食い違ったまま、元項目を直せなくなるため。
- 持ち越しの画面（S-03）を表示している間に、エージェントが前回の日の項目を変えた場合は、一覧をその場で更新し、確定の時点の内容で持ち越す（確定の時点で未完了・未解消の項目だけを持ち越し、本文などは確定の時点の値を写す。画面設計書 5章）。
- 見直しで「やめる」を選んだ TODO は、元項目を `status = dropped`、`close_reason = dropped` にする。「外部ツールへ戻す」（外部連携が有効で、外部課題と紐付いた TODO のみ）は `close_reason = returned_external` とする。
- 「分割する」を選んだ場合は、元項目を `status = dropped`、`close_reason = split` にし、今日に作る子項目は `split_from_id` で元を指す（子項目の `carry_count` は 0）。
- 取りやめた TODO（`status = dropped`）は、持ち越し済みの項目と同じく、その日の終わりの状態として残すため、`status`・`close_reason`・`text`・`completed_at` を変えない（2026-11-03 決定）。エージェントの書き込み（`edit_todo`・`complete_todo`・`reopen_todo`。障害の本文を変える `edit_blocker` も、TODO の ID には書き込まない）は `invalid_argument` で拒み（MCP・CLI 仕様書 3章）、画面でも変えられない（操作仕様書 2章）。削除と並べ替えは通常どおりできる。`agent revert` でこれらの欄を戻すかは未決（MCP・CLI 仕様書 9章）。障害には `dropped` が無いため、この決まりは TODO だけに当てはまる。
- 持ち越しで作る障害には、元項目の `resolution_note`（未解消に戻した障害に残っている解消メモ。操作仕様書 2章）を写さない。解消メモは元の日の障害に残る。
- 持ち越した項目は、今日のリストの先頭に、前回の日の順のまま入るよう `sort_key` を付ける。

#### 件数の数え方

画面（凪メーター、サイドバー、ふりかえり）と MCP・CLI で使う件数は、次の定義で数える。どれも `deleted_at` が NULL の項目だけを対象にする。

| 件数 | 定義 |
| --- | --- |
| TODO 数 | その日の `kind = todo` のうち、`status` が `dropped` でないもの |
| 完了数（Done） | その日の `kind = todo` かつ `status = done` |
| 残り（LEFT） | その日の `kind = todo` かつ `status = open` と、`kind = blocker` かつ `status = open` の合計 |
| 解消数（Resolved） | その日の `kind = blocker` かつ `status = resolved` |
| 持ち越し数（Carried） | その日の項目のうち、`carried_from_id` が NULL でないもの（前の日から持ち越してきた数） |

過去の日の項目は持ち越しても `status` を変えないため、過去の日の「残り」には、翌日以降へ持ち越した項目も含まれる（その日の終わりの状態を表す）。

### note / reflection

| 列 | 型 | 説明 |
| --- | --- | --- |
| date | TEXT PK FK→day | 論理日付 |
| body | TEXT | Markdown 風のプレーンテキスト |
| rev | INTEGER | 版の番号。1 から始め、書き込みのたびに＋1。画面の保存とエージェントの変更の行き違いを見つけるために使う（アーキテクチャ設計書 4.1。item は版の番号を持たず、送られた欄だけを書く） |
| updated_at | TEXT | 最終更新時刻 |

ノートの会議区切りは本文中の見出し行（`## 10:00 定例` 形式）で表し、別テーブルは設けない。見出しの一覧は本文から都度抽出する。

本文の扱い（2026-11-03 決定。コアの `domain::note_body`・`domain::text_doc`）：

- 行：本文を改行（LF）で区切ったものを行とし、1行目から数える。改行で終わる本文は最後に空の行があり、空の本文は空の1行とする（エディタの行の数え方と同じ。画面が知らせる守る行と `edit_note` の行番号をそろえるため。アーキテクチャ設計書 4.1）。CR は区切りに数えず、行の文字に含める。
- 時刻付き見出し：行頭の `## `（`#` 2つと半角の空白1つ）に続けて時刻（`H:MM` か `HH:MM`。0:00〜23:59）、その後は行末か、空白（全角の空白を含む）に続く件名、という形の行。`## 良かったこと` のような時刻の無い見出しや `###` の行は当たらない。`get_board` の `headings` は `## ` の後ろの文字（前後の空白を除く。例：`10:00 定例`）。
- 見出しの区間：見出しの次の行から次の時刻付き見出しの前まで（操作仕様書 2章）。最初の見出しより前は、見出しの無い区間（見出しが無ければ本文全体）とする。見出しの行は、その見出しの区間に属する。
- 末尾への追記（`append_note`・`append_reflection`）：最後の行が空ならその行から書き、そうでなければ次の行から書く。追記する本文は改行を LF にそろえ、末尾の空白と改行を除く（標準入力から読んだ本文の末尾の改行や空白だけの行が残らないようにするため）。最後の行が空かは LF の区切りで決め、CR や空白だけの行は空とみなさない。空白と改行だけの本文は `invalid_argument`。`append_note` の `--heading` は、現在時刻（端末のタイムゾーン）の見出し `## HH:MM 件名`（件名が空なら `## HH:MM`）を、最後の行が空ならその行に、そうでなければ空行を1行あけて入れ、次の行から追記する（画面の Mod+Shift+H と同じ。操作仕様書 2章）。件名に改行を含めると `invalid_argument`。
- 行単位の書き換え（`edit_note`）：書き換えは1行を1行にし、書き換えた後の行に改行（LF）を含めると `invalid_argument`（CR は行の文字として受け付ける）（行番号 0、改行を含む `expected_text`、移動先 0 も同じ）。移動（`--move-to M`）は、動かした後の本文で M 行目になるようにする。引数の誤りを先に確かめ、続けて、行 N が本文に無いか `expected_text` と完全に一致しない場合と、移動先 M がいまの行数より大きい場合を `conflict`（`reason: changed`）とする（どれもエージェントが読んだ後に本文が変わったときに起きるため）。まだ書いていない日のノートは空の1行として扱う。
- 版の番号：本文を実際に変えたときだけ版を進める。同じ本文への置き換えや同じ位置への移動、画面からの同じ本文の保存は、書かずに成功とし（エージェントの操作は `updated: false`）、change_log にも記録しない。版が進むと画面が知らせた守る行が古くなるため。まだ書いていない日（行が無い）の版は 0 とし、画面はそれをもとにして保存する。画面の保存の、もとにした版がいまの版と違えば、書かずに最新の本文と版を返す（アーキテクチャ設計書 4.1）。ただし保存する本文がいまの本文と同じなら、版が古くても書かずに成功とし、いまの版を返す（行き違いにすると、画面の取り込みで同じ行が二重になるため）。見出しの時刻は、書き込む日にかかわらず現在時刻（端末のタイムゾーン）とする。
- change_log：エージェント・CLI の書き込みは `note.append`・`reflection.append`・`note.edit` として、本文全体を JSON の文字列で `before` / `after` に入れる。まだ書いていなかった日（行が無い）への書き込みの `before` も空の本文（`""`）とし、NULL にはしない（`get_note` が空の本文を返すのと同じ。取り消しで書き戻す本文を1通りに決めるため）。人の保存は記録しない。本文の書き込み・day の行の作成・change_log の記録は1つのトランザクションで行う。

### note_send

| 列 | 型 | 説明 |
| --- | --- | --- |
| id | TEXT PK | ULID |
| date | TEXT FK→day | ノートの日付 |
| line_text | TEXT | 送った時点の行の本文 |
| line_fingerprint | TEXT | 行の位置変化に追随するための指紋（本文のハッシュと前後の行の情報） |
| item_id | TEXT FK→item | 送り先の項目 |
| created_at | TEXT | 送った時刻 |

送信済みの印は、表示時に本文の各行を `line_fingerprint` と照合して付ける。本文が一致すれば行の位置が変わっても印を保つ。本文を編集して一致しなくなった場合は印を外す（送り先の項目は残る）。この挙動は、人による編集とエージェントの `edit_note` で同じとする。複数行を選んで送った場合は、1行ごとに1件の項目と1件の note_send を作る。

- 送り先の項目は、ノートと同じ日に作る（過去の日のノートから送った場合も、その日に作る）。
- 送り先の項目が削除された（`deleted_at` が設定された）場合は、印を外す。
- 項目がどのノートの行から来たかは、次の順でたどる。まずその項目を `item_id` に持つ note_send を探し、無ければ `carried_from_id`、`split_from_id` で元の項目へさかのぼって同じく探す。持ち越しや分割をした TODO でも、依頼文の書き出し（MCP・CLI 仕様書 5章）で元のノートの行を使えるようにするため。見つかった note_send の行が、いまのノート本文で `line_fingerprint` と一致しない場合は、ノートから来ていないものとして扱う。

### change_log

| 列 | 型 | 説明 |
| --- | --- | --- |
| id | TEXT PK | ULID |
| actor | TEXT | `agent` / `human`（取り消しを人が実行した場合などは `human`） |
| agent_client_id | TEXT FK→agent_client NULL | 操作したエージェント（CLI は `name = cli` の行）。`actor = human` のときは NULL |
| operation | TEXT | `<名詞>.<動詞>` 形式。例：`todo.add`、`todo.complete`、`note.edit`（MCP・CLI 仕様書 3章の命名規則）。取り消しの記録は `agent.revert` |
| target_type / target_id | TEXT | 対象。target_type は `item` / `note` / `reflection`。target_id は、item なら項目の id、note・reflection なら日付（`YYYY-MM-DD`） |
| before / after | TEXT（JSON）NULL | 変更前後のスナップショット。item は、その操作が変えた欄だけを入れる（追加・削除では項目全体）。note・reflection は本文。追加の before のように、無い側は NULL |
| created_at | TEXT | 操作時刻（ミリ秒まで。画面の操作との前後をこの値で比べる。アーキテクチャ設計書 4.1） |
| reverted_at | TEXT NULL | 取り消した時刻 |
| revert_of_id | TEXT FK→change_log NULL | この記録が取り消し操作である場合、取り消した元の記録の id |
| seen_at | TEXT NULL | 利用者が変更履歴画面で確認した時刻 |

記録するのは、実際に何かを変えた操作だけとする。何も変えずに成功を返した操作（解消済みの障害への `resolve_blocker` をやり直した場合、今と同じ本文の `edit_todo`・`edit_blocker` など。MCP・CLI 仕様書 3章）は記録しない。やり直しのたびに同じ記録と未確認の印が増えないようにするため。利用者が画面で項目の状態を変えてから保存されるまでの間に、エージェントが同じ状態にした場合も、利用者の保存の書き込み時に、そのエージェントの記録から状態と完了時刻の欄を外し、何も残らなければ記録を消す（利用者の変更として扱う。アーキテクチャ設計書 4.1）。

取り消しは `before` を書き戻す新しい操作として実行し、取り消し自体も `revert_of_id` 付きで記録する。item では、`before` / `after` に入っている欄だけを書き戻し、ほかの欄には触れない（画面の保存が欄ごとに書くのと合わせるため。アーキテクチャ設計書 4.1）。人による編集は change_log に記録しないため、「対象がその後に人によって変更されている」かは、`after` に入っている欄（note・reflection では本文）の現在の値と、その記録の `after` が一致するかで判定する。一致しない場合は、取り消し前に差分を示して確認を求める。

画面の「エージェントによる未確認の変更」は、`actor = agent` かつ `seen_at` が NULL の記録で表す。上部のバーとサイドバーの件数はその記録の数、項目の行頭の菱形は `target_type = item` でその項目を指す記録があるときに付ける。

### agent_client

| 列 | 型 | 説明 |
| --- | --- | --- |
| id | TEXT PK | ULID |
| name | TEXT UNIQUE | 接続時の識別子（`yunagi mcp --client <name>`）。例：`claude-code`、`codex`、`cli`、`unknown`（識別子のない MCP 接続） |
| scopes | TEXT（JSON） | `read` / `todo` / `blocker` / `append` / `note_edit` の許可。既定はどのクライアントも `read` のみ |
| created_at / last_seen_at | TEXT（last_seen_at は NULL） | 登録・最終接続時刻。まだ接続していなければ last_seen_at は NULL |

`cli` と `unknown` の行は、データベースの作成時（マイグレーション 1）に固定で作る。id は固定の ULID（`cli` が `00000000000000000000000001`、`unknown` が `00000000000000000000000002`）、`scopes` は `["read"]`、`last_seen_at` は NULL とする。そのほかの行は、新しい識別子で初めて接続したときに作る。item・change_log の `agent_client_id` は、この表の `id`（ULID）を指す。

### setting

| 列 | 型 | 説明 |
| --- | --- | --- |
| key | TEXT PK | 設定のキー |
| value | TEXT（JSON） | 値。行が無いキーは既定値を使う |

キーと値（JSON）の組で保持する。主なキー：`day_boundary`（既定 `04:00`）、`layout`、`theme`（`system` / `light` / `dark`。既定 `system`）、`font_size`、`vim_mode`、`shortcuts`、`locale`、`carryover_review_threshold`（既定 3）、`update_check`（更新の自動確認。既定 `true`）、`meter_hours`（凪メーターの時間帯。既定 `09:00-19:00`）、`sidebar`（サイドバーの開閉の状態）、`vim_ime_restore`（挿入モードに入ったとき直前の入力状態に戻す。既定 `true`。操作仕様書 4.4）、`license`（サポーターライセンスのキーと最終確認時刻）。

- バックアップの世代数は設定に持たない。MVP では直近7日分に固定する（アーキテクチャ設計書 6.2）。
- ローカル API は設定で止められるものとはせず、設定画面では状態の表示だけを行う。

保存先（`data_dir`）は DB には持たず、設定ファイル `config.json` で管理する（アーキテクチャ設計書 6章）。エージェントの権限は agent_client テーブルで管理する。

## 4. 全文検索

FTS5 の仮想テーブル `search_index`（種類 kind・元の行 ref_id・日付 date・本文 body。kind・ref_id・date は 4.1 の `search_index_ref` に持つ）を用意し、item・note・reflection の更新時にトリガーで同期する（`deleted_at` が設定された項目は索引から外す）。日本語は単語区切りがないため、trigram トークナイザを採用する。解消済みの障害の解消メモ（item.resolution_note）も、同じ索引の別の列 resolution_note で検索の対象にする（4.1）。trigram は3文字未満の検索語に索引を使えないため、2文字以下の検索語は元テーブル（item.text・解消済みの障害の item.resolution_note、note.body、reflection.body）に対する `LIKE '%語%'` の部分一致検索で扱う。5年分の規模で1秒以内に収まるかはテスト計画書の性能テストで確認する。

### 4.1 索引と検索の決まり（2026-11-03 決定）

- 索引はマイグレーション 2 で作る（YUN-21。解消メモの列はマイグレーション 3 で足した。下記）。マイグレーション 1 はまだ配布していないが、開発中に番号 1 まで適用したデータベースには、1 を書き換えても索引が作られないため、新しい番号で足し、それまでにある行も索引に入れる。
- 形：`search_index` は本文（body）と、解消済みの障害の解消メモ（resolution_note。note・reflection の行では空）の2つの列を索引し、本文の写しを持たない（FTS5 の contentless。`contentless_delete=1` で行番号で消せる）。行ごとの元の行・種類・日付は、普通の表 `search_index_ref(id, source, ref_id, kind, date)` に持つ（`id` は `search_index` の rowid、`source` は `item` / `note` / `reflection`）。`kind` は `todo` / `blocker`（item.kind）・`note`・`reflection`、`ref_id` は item なら item.id、note・reflection なら日付。絞り込み・並べ替え・件数の切り取りはこの表で行い、残った行の本文だけを元の表から読む。本文の写しを持つ形では、ノートの本文（1日 10KB ほど）が一致のたびに読まれ、5年分で約 28MB 大きくなったため。
- 更新のたびに行番号で入れ直す。item は本文・種類・日付・削除の有無と、索引に入れる解消メモ（解消済みかどうかと、解消メモの本文）のどれかが変わったときだけ入れ直す（それ以外の状態の変更では触らない）。note・reflection は本文が変わるたびに入れ直す（自動保存のたびに 10KB を入れ直しても、5年分の索引がある状態で1回あたり p95 約 1.6ms のため、間引かない）。
- 索引はトリガーだけでそろえる。後のマイグレーションで item・note・reflection を作り直す（新しい表に写して元の表を消す）と、元の表のトリガーも消えて、索引が黙って古いままになる。作り直すときは同じマイグレーションでトリガーも作り直す（トリガーがそろっていることはコアの単体テストで確かめる）。
- 検索語は前後の空白を除き、全体を1つの文字列として部分一致で探す（空白で語に分けない）。空なら何も返さない。文字数は Unicode の文字で数える。
- ASCII の英字の大文字・小文字は区別しない。ASCII 以外（全角英字・`Ä` など）は、3文字以上では区別せず（trigram の既定）、2文字以下では区別する（SQLite の `LIKE` が ASCII しかそろえないため）。
- 期間（両端を含む）と種類（複数可）で絞り込める。並びは日付の新しい順、同じ日は TODO・障害・ノート・振り返りの順（画面設計書 6章の種類の英字ラベルの書き順は、並びを決めるものではない）、その中は ref_id の順（項目は作った順。ボードの並び `sort_key` ではない。ボードで並べ替えるたびに索引を書き直さずに済むようにするため）。件数の上限は呼び出し側が渡す。
- 検索の対象は item.text・note.body・reflection.body と、解消済み（`status = resolved`）の障害の解消メモ（item.resolution_note）とする（2026-11-03 決定。要件定義書 F-10 の「障害を横断検索する」に、障害の解消の記録も含めるため）。未解消に戻した障害に残っている解消メモは、画面に出ない（画面設計書 3章）ので探さない。索引はマイグレーション 3 で作り直し（FTS5 は列を足せないため）、それまでにある解消メモも入れる。解消メモは本文とは別の列に入れ、本文と解消メモにまたがる文字列には一致させない（FTS5 の句は列をまたがない。2文字以下の `LIKE` も列ごとに比べる）。解消メモで一致した障害は、種類 `blocker` の結果として出し、結果には本文に加えて解消メモを含める（一致した部分の切り出しは使う側で、本文か解消メモかを見分けて行う）。
- 種類の値（item.kind）にコアの知らない値があると、検索全体を失敗にする（ほかの読み取りと同じ。値を足すときは新しい番号のマイグレーションを足すので、旧版は開かずに断る。1.1）。
- 結果は本文の全体を返し、一致した部分の切り出し（画面の「本文の一部」、画面設計書 6章）は使う側で行う。MCP・CLI の `carried_to_id`・`carried_to_date`（MCP・CLI 仕様書 3章）も、使う側で結果の項目に加える。

## 5. 容量の見積もり

1日あたり TODO・障害 20件、ノート 10KB、振り返り 2KB と仮定すると、5年（約1,800日）で本文は約 25MB、索引を含めて 100MB 未満に収まる見込み。要件の「5年分で検索1秒以内」はこの規模で検証する。

この量の模擬データ（日本語を含む）で測った結果（2026-11-03、YUN-21。Intel Core i7-11850H）は、`yunagi.db` が約 70MB（うち全文検索の索引と search_index_ref が約 31MB）で、見込みの範囲に収まった。検索は最も遅い条件（2文字で一致なし。全件を読む）でも p95 が約 30ms で、1秒以内に収まった（測り方は `crates/core/src/storage/search.rs` の `five_years_of_data_is_searched_within_one_second`）。解消メモを検索の対象に足した後（2026-11-03、YUN-68。障害の半分を解消済みにし、40 バイトほどの解消メモを付けて測った）も、`yunagi.db` が約 71MB（索引が約 31MB）、最も遅い条件の p95 が約 31ms、ノートの保存の p95 が約 1.9ms で、ほぼ変わらなかった。
