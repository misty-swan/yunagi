# サードパーティライセンス表記の方針

## 1. 目的

Yunagi が利用するオープンソースソフトウェア（OSS）のライセンス条件を満たし、著作権表示とライセンス本文を利用者が確認できるようにする。

## 2. 方針

1. Rust の依存は `cargo-about` 等、JavaScript の依存はライセンス収集ツールで、ライセンス本文と著作権表示を自動収集する。
2. 収集結果は `THIRD_PARTY_LICENSES.md` としてリリースごとに CI で生成し（ビルド・配布手順書 3章）、アプリの「設定 → このアプリについて」から表示する。収集は Rust が `cargo-about`（`about.toml`）、JavaScript が `pnpm licenses`（配布物に入る依存だけ）。生成物は配布物に同梱した（表示する画面は、まだ無い）。
3. 許可するライセンスの一覧を定め（MIT、Apache-2.0、BSD-2-Clause、BSD-3-Clause、ISC、Zlib、MPL-2.0、BSL-1.0、CDLA-Permissive-2.0、Unicode-3.0。`scripts/release/license-policy.json` の `allowed`）、それ以外が混入した場合は CI で検出して止める（ビルド・配布手順書 3.1）。後ろの 3 つは、MIT・Apache-2.0 と同じ寛容なライセンスとして、2026-11-06 に加えた（YUN-96）。BSL-1.0（Boost）は Windows のクリップボードの依存 `clipboard-win`・`error-code`、CDLA-Permissive-2.0（Mozilla の CA 証明書の一覧の使用許諾）は自動更新が連れてくる `webpki-root-certs`（2026-11-06 時点では、配布する 6 組の target の依存に入らないので、`THIRD_PARTY_LICENSES.md` には載らない。入るようになれば、載せる）、Unicode-3.0 は文字の表を持つ依存が使う。BSL-1.0 を外すと Windows のクリップボードが動かなくなる。CDLA-Permissive-2.0 は、自動更新の依存を将来どの target でも使えるように、先に許可しておく。最終の法的確認は、法務文書の確定版（YUN-106）でまとめて受ける。新しい依存が一覧に無いライセンスを連れてきたときは、オーナーが決めるまで `pending` に置く（ふだんは空。検出は止まる）。決まったら、許可するものを `allowed` へ移し、許可しないものは依存を外して `pending` から消す。
4. GPL・AGPL 系のライセンスを持つ依存は、配布形態への影響を確認するまで採用しない。
5. 同梱するフォント（Inter、UDEV Gothic HS。デザインガイド 4章）のライセンス（SIL OFL）も同じ表記に含める。フォントは依存のパッケージとしてではなくファイルとして同梱する（デザインガイド 4章）。1 の収集ツールと 3 の検出の対象にならないため、同梱してよいフォントはデザインガイド 4章に書いたもの（いずれも OFL-1.1。ファイルと SHA-256 もそこに書く）に限り、CI でファイルとライセンス文書を確かめる（ビルド・配布手順書 3章）。増やすときはデザインガイドに書いてから入れる。表記には、フォントと同じ場所に置いたライセンス文書（著作権表示と OFL の本文）を、生成の際に加える。UDEV Gothic HS は、元になった JetBrains Mono と BIZ UDゴシックの著作権表示も含める（デザインガイド 4章「ノートの等幅」）。

## 3. 本体ソースの公開とライセンス（2026-11-06 決定。YUN-103）

- Yunagi 本体のソースコードは、今のリポジトリ `misty-swan/yunagi` を、ソースごとそのまま公開する。配布・Issue・脆弱性報告用のリポジトリも同じもの（ビルド・配布手順書 1章）。
- 本体のライセンスは **MIT と Apache-2.0 のデュアル**（利用する人が、どちらか好きなほうを選べる）。2 章 3 の許可するライセンスの一覧にも、この 2 つがある。
- LICENSE ファイルの置き場所と書き方は次のとおり（2026-11-06 決定。YUN-109）。
  - リポジトリ直下に **`LICENSE-MIT` と `LICENSE-APACHE` の 2 ファイル**を置く（Rust のプロジェクトの慣例。GitHub は 2 つのライセンスを認識して表示する）。本文は各ライセンスの標準の全文。著作権者の表記は `Copyright (c) 2026 misty-swan`（MIT の 1 行目。Apache の付録の例にも同じ名前と年を入れる）。年は最初の公開の年で、毎年は書き換えない。
  - `Cargo.toml` の `[workspace.package]` に `license = "MIT OR Apache-2.0"`（SPDX の式）を書き、4 つのクレートは `license.workspace = true` で使う。`package.json` にも同じ `license` を書く。どちらも `publish = false`・`private` のままなので、crates.io や npm には出ない。`about.toml` の `private = { ignore = true }` により、自分たちのクレートは第三者ライセンスの収集に数えられない（2 章 3 の許可と矛盾しない）。
  - **ソースの各ファイルの先頭には、ライセンスや著作権の表記を書かない。** 直下の 2 ファイルと README の「ライセンス」の節で足りる（Rust の主要なプロジェクトと同じ）。
  - README に「ライセンス」の節を置き、デュアルであること、貢献の扱い（提出された変更も同じ条件。CONTRIBUTING.md）、本体の対象外のもの（同梱フォント、依存、`experiments/`・`prototype/`）を書く。
  - 名前とアイコンは、ソースのライセンスと別に扱う（Apache-2.0 の 6 条は商標を許諾しない）。商標の登録はしていない（2026-11-06 時点。J-PlatPat の確認のみ）。
  - 配布物（`.app.tar.gz`・AppImage・NSIS）に `LICENSE-MIT`・`LICENSE-APACHE` を含めるか、`THIRD_PARTY_LICENSES.md` の先頭に本体のライセンスを載せるかは、Release に添付する課題 YUN-101 で決める（Release には両方のファイルも添付する。YUN-101 の完了の条件に書いた）。
- 公開前に、`docs/` と `prototype/` の中で公開してよくないもの（価格の検討・法務の叩き台・個人の情報など）がないかを点検する（YUN-109）。点検の対象は、いまのファイルだけでなく、**git の履歴全体**（過去のコミットのファイル・コミットの文面）と、作業管理や AI エージェントの設定のファイル（`.claude/`、Linear の課題への参照など）を含む。公開すると履歴も見えるので、最新のコミットでファイルを消しても、過去のコミットから読める。見つかったら、履歴を書き換えてから公開するか、きれいな履歴で新しいリポジトリとして公開するかを、YUN-109 で決める。
- 「そのまま公開する」は、何も点検せずに全部出すという意味ではない。`docs/future/`（価格の検討など）、`docs/legal/` の弁護士確認前の叩き台、`CLAUDE.md`、`prototype/` のように、公開するか迷うものは、YUN-109 で**公開するものを一覧にして決めた**（2026-11-06。ビルド・配布手順書 8.1）。結果：`docs/legal/` の弁護士確認前の 3 文書（利用規約・プライバシーポリシー・特定商取引法の表記）だけを公開しない（非公開のリポジトリへ移す。同 8.3）。ほかは公開する。履歴全体と PR の点検の結果は同 8.2。決めていないものは、公開前にリポジトリから外す（既定は「外す」）。また、既存の PR の説明・コメントは、リポジトリを公開すると一緒に読めるようになり、履歴の書き換えでは消えない。中に Linear の課題や社内の判断が書かれていないかも、公開前に見る（書き換えたい場合は、新しいリポジトリとして公開する案を選ぶ）。同梱するフォントなど、本体と別のライセンスのファイルは、本体のライセンスの対象にしない（2 章 5）。
