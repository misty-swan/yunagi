# サポート・障害対応手順

## 1. 窓口

| 種類 | 窓口 | 目標応答時間 |
| --- | --- | --- |
| 不具合報告・要望 | 公開リポジトリの GitHub Issues（テンプレートあり）。アカウントが無い場合は support@<公式ドメイン> | 3 営業日以内に初回反応 |
| 購入・ライセンス | support@<公式ドメイン>（TBD） | 2 営業日以内 |
| 個人情報の開示等の請求 | support@<公式ドメイン>（TBD） | 〔法令に沿った期限〕 |
| 脆弱性 | release/SECURITY.md の窓口 | 3 営業日以内 |

## 2. 不具合報告テンプレート（Issue）

- Yunagi の版（`yunagi --version`）
- OS と版、CPU（Apple Silicon / Intel / x86_64 / arm64）
- 日本語入力の種類（該当する場合）
- Vimモードの有効・無効
- 再現手順、期待した動作、実際の動作
- 診断情報（`yunagi doctor` の出力。業務データの内容は含まない）

## 3. 重大度

| 重大度 | 例 | 対応 |
| --- | --- | --- |
| 高 | データ損失、起動不能、更新失敗による利用不能、セキュリティ問題、IME による誤操作（変換確定の Enter で項目が追加される等） | 当日中に調査開始。修正版を最優先で公開 |
| 中 | 主要機能の誤動作 | 次の修正版で対応 |

本表が重大度の正本である。テスト計画書のリリース判定もこの定義に従う。
| 低 | 表示の乱れ、文言の誤り | 計画的に対応 |

## 4. よくある対応

### 4.1 起動しない（macOS）

1. `~/Applications/Yunagi.app`（Homebrew で導入した場合は `/Applications/Yunagi.app`）にあるか確認する。
2. ブラウザでダウンロードした場合や Homebrew（Cask）で導入した場合は隔離属性が付き、起動できないことがある。`xattr -dr com.apple.quarantine <Yunagi.app のパス>` を案内するか、インストールスクリプトでの再導入を案内する。
3. 解決しない場合は `yunagi doctor` の出力を依頼する。

### 4.2 データが見当たらない

1. 設定 →「データ」で保存先を確認する。
2. 論理日付の切り替わり時刻（既定 4:00）により、深夜の記録が前日に入っていないか確認する。
3. `backups/` から復元できることを案内する（設定 →「データ」→「バックアップから復元」）。

### 4.3 起動時に「データベースが見つかりません」「開けませんでした」と出る

起動時の画面（画面設計書 10.1）の見出しと「詳しい情報」（版とログ用の文）を送ってもらう。

1. 「見つかりません」：保存先（画面の「探した場所」）が外付けのドライブ・同期フォルダなら、繋ぐ・同期を待ってから「やり直す」を案内する。データベースのある別のフォルダが分かれば「保存先を選び直す」、無ければ「バックアップから戻す」を案内する。「新しく作る」は、元のデータが無いと確かめてからにする。
2. 「更新後の準備に失敗しました」（マイグレーションの失敗）：データは更新前のまま。前の版を入れ直してもらい（`YUNAGI_VERSION=<旧版>` を付けてインストールスクリプトを実行）、ログ用の文から失敗したマイグレーションを調べる。重大度は高（3章）。
3. 「新しい版の Yunagi で作られています」：旧版を入れ直したか、新しい版を使う別の端末と同期している。新しい版を入れてもらう。
4. 「壊れているため、開けませんでした」：「バックアップから戻す」を案内する。壊れていたものは保存先の `backups/damaged-<秒>.db`（と横のファイル）に残るので、調べるときは送ってもらう（業務データを含むため、受け取る前に了承を得る）。更新の直後なら、前の版ではそのまま開けることがある。
5. 「更新後の準備に失敗し、元に戻せませんでした」：ファイルを動かさないよう伝える。画面に示した更新前のバックアップ（`backups/pre-migration-*.db`）が戻す先になる。重大度は高。

### 4.4 エージェントから操作できない

1. `yunagi agent permissions` で権限を確認する。
2. `yunagi agent setup` を再実行して登録状態を確認する。
3. アプリ起動中にローカル API の接続に失敗する場合は、アプリを再起動する。エラーが `busy`（終了コード 7）なら、ローカル API にもつながらず、データを使うロックも 5 秒の間に取れなかったということ（アプリが起動してデータベースを開くのに時間がかかっている、待ち受けが動いていない、ほかの CLI・MCP の操作が長引いている）。少し待って同じ操作をやり直し、続くときはアプリを再起動する。`api_error` は、待ち受けはあるが使えない（`reason` が `auth_failed` ならアプリを再起動、`version_mismatch` ならアプリと CLI の版をそろえる）。`yunagi doctor` でローカル API の状態を確かめられる（MCP・CLI 仕様書 3.1）。

## 5. 障害発生時（配布・更新の問題）

1. 不正な配布物や更新が疑われる場合は、直ちに Release を取り下げ、`https://<公式サイト>/latest.json` を前の版に戻す。
2. 公式サイトと GitHub で状況を告知する。
3. 更新署名鍵の漏えいが疑われる場合は、ビルド・配布手順書 6章の手順に従う。
4. 利用者への影響と対処を CHANGELOG の Security または Fixed に記載し、原因と再発防止策は本書 6章の記録に残す。

## 6. 記録

対応した問い合わせは、種類・原因・対応・所要時間を記録し、月に一度見直してドキュメントや機能の改善につなげる。
